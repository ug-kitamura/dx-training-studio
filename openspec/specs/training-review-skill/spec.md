## Requirements
### Requirement: 起動時確認は範囲と深さを1回だけ聞く
スキルは実行冒頭で、対象シリーズ（複数選択可）とレビューの深さを確認しなければならない（MUST）。確認は冒頭の1回のみとし、実行中に聞き直してはならない（MUST NOT）。深さは2択で提示し、文言は内部構造（層の名称）ではなく使う場面で表現しなければならない（MUST）。既定・推奨は整合チェックとする。

検査の言語をユーザーに聞いてはならない（MUST NOT）——対象範囲に英語版（`contents.en.md`・`_en` フィールド・`changelog.en.md`）が存在すれば自動で検査対象に含め、対象確定時に英語版の件数と検査時間が伸びる旨を伝える（MUST）。深さの2択に言語の選択肢を足してはならない（MUST NOT）。

#### Scenario: 深さの2択提示
- **WHEN** スキルが起動され対象シリーズが確定した
- **THEN** 「整合チェック（推奨・短時間）— コースの追加・並び替え・改名のあとの確認に」「公開前レビュー（時間がかかる）— 受講者にリリースする前の総点検に」の趣旨の2択が提示され、18項目の個別選択メニューは提示されない

#### Scenario: 英語版は聞かずに含める
- **WHEN** 対象シリーズに `contents.en.md` を持つレッスンが3件ある
- **THEN** 言語の質問は無く、「英語版 3件も検査します」の趣旨が伝えられて検査対象に含まれる

#### Scenario: 実行中は聞き直さない
- **WHEN** レビュー実行中に判断の分かれる箇所が見つかった
- **THEN** その場でユーザに質問せず、指摘ファイルに advisory として記録して続行する

### Requirement: 整合チェックの検査項目
整合チェックは次を実行しなければならない（MUST）: (1) 機械検証 — 名前整合（ディレクトリ名 ⇔ 計画書、旧名残存）、レッスン `.meta.json` の機械検査（author 記入・status・tags 形式）、画像スロット未消化（プロンプトコメントのみで画像未挿入の節）、社内データの空欄記法残存と `context-outbox.json` の未処理、出典の形式（斜体1行・リンク埋め込み）、リンク生存確認。(2) 次・前参照の整合。(3) 受講者ペルソナによる心の声ウォークスルー。レッスン本文の品質精査を含んではならない（MUST NOT）。

英語版が存在する範囲では、次の英語系検査も実行しなければならない（MUST）:

- **`name_en` の重複** — 同一階層内で同じ `name_en` が2つ以上あれば **blocking**（サイドバー・曼陀羅で区別が消える。別々に訳した名前が英語で潰れる事故は訳文単体からは見えない）
- **`name_en` の長さ** — シリーズ・コース・レッスンの `name_en` が**翻訳契約の名前の上限**を超えていれば **blocking**——曼陀羅ノードは名前を折り返して全体を見せる設計で、ノードの寸法と行数の上限は契約の上限が収まるよう実測で決めてあるため、超えた分は黙って隠れる。上限の字数は `contracts/translation-contract.md` を読んで使い、review 側に別の目安を持たない（MUST NOT）
- **鮮度の整合と欠落** — `en_source_hash` と実ハッシュの不一致・未訳ユニット・欠落 `_en` フィールドの一覧。判定はスキル同梱ではなく `dx-training-translate` の走査スクリプト（`scan-freshness.mts`。正本 lib を import 済み）の実行で得なければならず（MUST）、判定ロジックや階層→キー対応を review 側の文書に書き写してはならない（MUST NOT）
- **訳文側の機械検査** — `contents.en.md` の画像パス・出典の形式・リンク生存・次・前参照の整合を日本語側と同じ規則で検査する

未訳ユニットと欠落フィールドは advisory としなければならない（MUST）——公開サイトは未訳を `Coming soon`＋日本語版リンクとして設計どおり扱うため「受講者に届いたら実害」に該当しない。`slug` が `name_en` と一致しないことを指摘してはならない（MUST NOT）——slug は構造キーで翻訳の対象外である。

#### Scenario: 改名後の旧名残存を検出する
- **WHEN** シリーズ名が改名された後の原稿に旧シリーズ名への言及が残っている
- **THEN** 対象ファイル・位置・旧名と現名を添えた指摘が出力される

#### Scenario: 画像スロットの未消化を検出する
- **WHEN** 原稿にプロンプトコメントがあり、対応する `![…](images/…)` の挿入が無い
- **THEN** 該当節が「画像未挿入」として指摘される

#### Scenario: name_en の重複を検出する
- **WHEN** 同じシリーズ内の2コースが同じ `name_en` を持つ
- **THEN** 両ユニットと日本語名を並べた blocking の指摘が出力される

#### Scenario: name_en の長さ超過を検出する
- **WHEN** 契約の上限を 1 字超えるコース `name_en` がある
- **THEN** そのユニットと実際の字数を添えた blocking の指摘が出力される
- **AND** 上限ちょうどの名前は指摘されない

### Requirement: 次・前参照は抽出と局所照合で判定する
スキルは原稿本文から「シリーズ」「コース」「レッスン」の統制語彙と「次の/前の」等のパターンで参照文を抽出し、参照ごとに `.meta.json` から解決した実際の前後関係（タイトル・description）だけを文脈として整合を判定しなければならない（MUST）。全コーパスを単一文脈に載せて判定してはならない（MUST NOT）。

#### Scenario: 順序変更で無効になった相対参照を検出する
- **WHEN** レッスンの order が入れ替わり、本文の「前のレッスンで作った練習リポジトリを使う」が実際の前のレッスンと合わなくなった
- **THEN** 該当文と実際の前レッスン名を並べた指摘が blocking として出力される

### Requirement: 心の声ウォークスルーは本文を読まない
心の声ウォークスルーはサブエージェントで実行し、入力はシリーズ→コース→レッスンのタイトル階層・各レッスンの `.meta.json` のメタ（description・estimated_minutes）とコースの `target`・`.meta.json` の受講順のみとしなければならない（MUST）。レッスン本文を入力に含めてはならない（MUST NOT）。出力は受講者ペルソナが受講順に歩いたときの心の声の時系列であり、順序の不自然さとストーリーの断絶を表面化させる。

#### Scenario: 供給前の要求が心の声として現れる
- **WHEN** 未導入の概念を前提とするタイトル・description のレッスンが先に並んでいる
- **THEN** ウォークスルー出力に受講者の戸惑いが時系列で現れ、該当位置が指摘に変換される

### Requirement: 公開前レビューはレッスン単位の品質チェックを追加する

公開前レビューは整合チェックの全項目に加えて、レッスンごとに独立した文脈で、誤字脱字・トンマナとですますの統一・文章量の妥当性・所要時間と description の妥当性・受講対象との整合・内容品質を検査し、コース内メタファーの統一を横断で検査しなければならない（MUST）。手順型レッスンでは、画面が変わる操作ステップに対して画像（挿入済みの画像・画像スロット・`> **社内画像**:` 空欄のいずれか）が足りているかを検査しなければならない（MUST）。内容品質の基準は `dx-training-create/references/design-principles.md` を参照する。ファクトチェック（Web 照合による事実検証)を行ってはならない（MUST NOT）。

あわせて、**初出の専門用語の説明有無**を検査しなければならない（MUST）: レッスン本文から受講対象（`target`）が知らない前提の語を抽出し、そのレッスンに説明があるか、無ければ受講順で前のコース（同じシリーズの前のコース・`cross_series_prev` の相手）に説明があるかを見る。前のコースにも当該レッスンにも説明が無い語を advisory として指摘し、説明を足す案を添える（MUST）。前のコースに説明があり参照の一言が無い場合は、参照を足す提案を advisory で添えてよい。受講順の引き方は整合チェックの受講順検査（H）と同じ正本（`.meta.json` の `order` / `cross_series_prev`）を使い、review 側に複製しない（MUST NOT）。指摘には、その語を専門用語とみなした理由を1文添える（MUST）。この検査は心の声ウォークスルー（本文を渡さない）とは別に行う。

英語版が存在する範囲では、次の英語系検査も実行しなければならない（MUST）:

- **受講者目線の通し読み** — レッスンごとにサブエージェントへ `contents.en.md` **だけ**を渡し、本文の順の心の声で読みづらさ・不自然さを出させる。原文（`contents.md`）・`contracts/translation-contract.md`・用語集を渡してはならない（MUST NOT）——原文を知った読者は「原文がこうだからこの英語で正しい」と読めてしまい、不自然さに気づけない。この検査の指摘は読みづらさの候補であり、用語集と矛盾する場合は用語集が勝つ
- **訳文のトンマナ・誤字** — 英文の文体の一貫性・スペル・表記ゆれ（トンマナ基準の導出規則は日本語と同じ——実行時に導出し定義ファイルを作らない）
- **メタの妥当性** — `description_en` / `catch_en` / `target_en` が中身を表しているか
- **用語のゆれとメタ⇔本文の一致（横断）** — 同じ概念の英訳の揺れ、`name_en`・`catch_en` と本文中の呼称の食い違いをコース/シリーズ横断で検査する。この検査では用語集（`translation-contract.md`）を参照してよい
- **初出の専門用語の説明有無（訳文）** — 日本語と同じ規則を `contents.en.md` に通す。訳語の判断が混ざるため用語集を参照してよい
- **`changelog.en.md` の文体・誤字**

#### Scenario: 公開前レビューの追加検査

- **WHEN** 公開前レビューを実行する
- **THEN** 整合チェックの指摘に加えて、レッスンごとの誤字脱字・トンマナ・分量・メタ妥当性・受講対象整合・内容品質の指摘と、コース横断のメタファー統一の指摘が出力される

#### Scenario: 前のコースで説明済みの語は指摘しない

- **WHEN** Git基礎シリーズのレッスンで「曼陀羅」が説明なしに使われ、受講順で前の はじめにシリーズ に説明がある
- **THEN** 説明不足としては指摘されない（参照の一言を足す提案が advisory で出ることはある）

#### Scenario: どこにも説明の無い語を指摘する

- **WHEN** レッスン本文に、当該レッスンにも受講順で前のコースにも説明の無い専門用語がある
- **THEN** その語・位置・専門用語とみなした理由・説明を足す案を添えた advisory が出力される


### Requirement: キャッチの通し整合を全件横断で検査する

公開前レビューは、シリーズ・コースの `catch` を**受講順に並べたときの獲得の物語の矛盾**を検査しなければならない（MUST）。判定する事象は 1 つに限る（MUST）: **受講順で前にあるキャッチが獲得・完了を宣言したものを、後のキャッチが未獲得の前提で語っていないか**。

検査の対象は、レビューの指定範囲によらず `contents/**/.meta.json` の `catch` **全件**としなければならない（MUST）——キャッチは全体で数十件に収まり、本文検査と違って全件を 1 つの文脈に載せられるため、範囲を絞ると衝突の相手側が見えなくなる。受講順の引き方は整合チェックの受講順検査（H）と同じ正本（`.meta.json` の `order` / `cross_series_prev` / `cross_series_next`）を使い、review 側に複製してはならない（MUST NOT）。

指摘の重さは **advisory 固定**としなければならない（MUST）——キャッチは受講者の感情のフックであり、リリースを止める対象ではない。指摘には、**どのキャッチとどのキャッチが、受講順のどの関係で矛盾しているか**と、寄せ方の案を添えなければならない（MUST）。決めるのは人とする。

この検査は次を行ってはならない（MUST NOT）:

- 語彙の台帳・メタファーの定義ファイルを新設すること、および既存のメタファーを規範として参照すること——メタファーを機械に先回りさせると、run ごとの創造性が失われる
- 同じ語が複数のものを指していることだけを理由に指摘すること——`セーブ` や `手に入れる` のような語の再利用そのものは問題ではない。縛るのは獲得の時制だけとする
- シリーズ `catch` とコース `catch` の抽象度の勾配を判定すること——メタファーそれ自体が高度な抽象化であり、勾配を縛るとメタファーが使えなくなる

#### Scenario: 獲得済みのものを未獲得として語るキャッチを指摘する

- **WHEN** 受講順で前にあるコースの `catch` が獲得の完了を宣言しており（例: `道具をそろえる`）、その `cross_series_next` の相手コースの `catch` が同じものを未獲得の前提で語っている
- **THEN** 2 件のキャッチと受講順の関係を示した advisory が出力され、寄せ方の案が添えられる

#### Scenario: 語の再利用だけでは指摘しない

- **WHEN** 受講順で前にあるコースの `catch` が `地図を手に入れる`、後のコースの `catch` が `共有保管庫の鍵を手に入れる` である
- **THEN** 同じ動詞を使っていても、獲得の対象が別であり矛盾しないため指摘されない

#### Scenario: 指定範囲外のキャッチも読む

- **WHEN** Git基礎シリーズだけを対象に公開前レビューを実行する
- **THEN** はじめにシリーズを含む全シリーズ・全コースの `catch` が読み込まれたうえで、Git基礎シリーズのキャッチに対する矛盾が判定される

#### Scenario: リリースは止めない

- **WHEN** キャッチの通し整合で矛盾が検出される
- **THEN** その指摘は advisory として出力され、リリース可否の判定を blocking にしない

### Requirement: トンマナ基準は実行時に導出し定義ファイルを作らない
トンマナ・ですますの採点基準は、`dx-training-create/references/model-answer/` が存在すればそこから読み取った基準とレビュー対象コーパスの自己一貫性、存在しなければ自己一貫性のみから実行時に導出しなければならない（MUST）。スキルはトンマナの細則を定義するファイルを新設してはならない（MUST NOT）。負の制約（誹謗中傷等の禁止事項）は例外とし、`design-principles.md` の明文を基準に含める。

#### Scenario: 模範解答が無い状態でも動作する
- **WHEN** `references/model-answer/` が存在しない状態で公開前レビューを実行した
- **THEN** エラーにならず、コーパス内自己一貫性のみを基準としてトンマナ検査が行われる

### Requirement: 受講順の正は `.meta.json` とする
受講順・接続の判定の正本は `contents/**/.meta.json`（order および cross_series_prev / cross_series_next）としなければならない（MUST）。計画書第3章の曼陀羅とのずれはエラーではなく advisory の指摘として報告し、`.meta.json` 側を誤りと断定してはならない（MUST NOT）。

#### Scenario: 人が張り替えた辺と計画書のずれ
- **WHEN** 人が Studio 上で計画書と異なるシリーズ間の辺を張っている
- **THEN** ずれの内容が advisory として報告され、blocking にはならない

### Requirement: 指摘は run ディレクトリにファイル出力し修正は行わない
指摘は `contents-work/runs/<yyyymmdd>-review/` に、対象ファイル・位置・項目（コードと名称の併記）・指摘内容・修正案・blocking / advisory の別を付けてファイル出力しなければならない（MUST）。日本語と英語の指摘は区別できる形で出力しなければならない（MUST）。サマリは blocking 件数とリリース可否を**言語別**に示さなければならない（MUST）——日本語が通過で英語が見送り、という判定は正常な結果である。スキルは `contents/`・計画書・既存スキル・`contracts/` を変更してはならず（MUST NOT）、指摘の反映は人が判断する（英語版の修正は Studio の英語ビューでの手編集——手編集は `en_source_hash` を触らないため鮮度を壊さない）。レビュー役は根本的なやり直しを提案してはならない（MUST NOT）。

#### Scenario: レビュー完了時の成果物
- **WHEN** レビューが完了した
- **THEN** run ディレクトリに指摘ファイルとサマリが存在し、`contents/` 配下に変更が無い

#### Scenario: リリース可否が言語別に出る
- **WHEN** 日本語の blocking が 0 件・英語の blocking が 2 件の状態でレビューが完了した
- **THEN** サマリに「日本語: 通過／英語: 見送り（blocking 2件）」の趣旨が言語別の行で示される

#### Scenario: 項目コードは名称を併記する
- **WHEN** 指摘が出力される
- **THEN** 「c: 次・前参照の整合」のようにコード単体ではなく名称併記で分類が示される

### Requirement: リンク生存確認の失敗は advisory に留める
リンク生存確認は短いタイムアウトで行い、到達失敗は「要再確認」の advisory として報告しなければならない（MUST）。ネットワーク到達性を理由に blocking を出してはならない（MUST NOT）。blocking にできるのは出典の形式違反のみとする。

#### Scenario: 一時的なネットワーク障害
- **WHEN** 出典 URL への到達が一時的に失敗した
- **THEN** 該当リンクは「要再確認」の advisory として報告され、リリース可否の blocking 集計に含まれない

### Requirement: コースの受講形態の未設定を検出する

整合チェックの機械検証は、**コース `.meta.json` の `style`（受講形態）が未設定であることを検出しなければならない**（MUST）。検出対象は、キーが無い場合と、値が受講形態の語彙（`self-study` / `lecture` / `hands-on`）に無い場合の両方とする（MUST）。

指摘は **blocking** としなければならない（MUST）——受講形態は曼陀羅のノードに出る受講者向けの情報であり、未設定のコースはラベルが黙って消える。原稿を読んでも気づけず、曼陀羅を開いて初めてわかる。

語彙は `studio/lib/schema.ts` の `COURSE_STYLES` を正本としなければならない（MUST）。review 側の文書に語彙を書き写して独自の一覧を持ってはならない（MUST NOT）——語彙が増えたときに二重管理になる。

#### Scenario: style の無いコースを検出する

- **WHEN** レビュー範囲のコース `.meta.json` に `style` キーが無い
- **THEN** そのコースを挙げた blocking の指摘が出力される

#### Scenario: 語彙外の値を検出する

- **WHEN** コース `.meta.json` の `style` が `workshop` のような語彙外の値である
- **THEN** そのコースと実際の値を添えた blocking の指摘が出力される
