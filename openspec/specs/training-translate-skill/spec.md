# training-translate-skill Specification

## Purpose

dx-training-translate スキル（教材の一括英訳）の要件。範囲指定・鮮度レポート（参考情報としての位置づけと最新ユニットの扱いの確認）・正本 lib 経由のハッシュ計算・翻訳契約の参照・差分翻訳・書き込み対象と不可侵領域・changelog 追訳・規約候補の報告と規約の変更禁止を定める。
## Requirements
### Requirement: 起動時確認は範囲を1回だけ聞く

スキルは起動時に翻訳範囲（全体／シリーズ指定／コース指定／レッスン指定。いずれもメタ含む）を確認しなければならない（SHALL）。依頼文から範囲が明確な場合は聞き直さない（SHALL NOT）。範囲に関わらず changelog は鮮度チェックの対象に含めなければならない（SHALL）。

#### Scenario: コース指定の実行

- **WHEN** 「Git三大エリアコースを英訳して」と依頼される
- **THEN** 範囲の聞き直しをせず、コースメタ＋配下レッスン（メタ＋本文）＋changelog を対象に進む

### Requirement: 鮮度レポートを提示し処理対象を決める

スキルは翻訳の前に、範囲指定に関わらず `contents/` **全体**の鮮度（`translation-freshness` の3状態）を走査し、進捗レポートを提示しなければならない（SHALL）。レポートは以下を含む:

- **全体の集計**: 本文・メタ・changelog を**別の行**で数えた「未翻訳 n・翻訳が古い m・最新 k」。本文とメタの状態を合算した数を提示してはならない（SHALL NOT）——作業量が桁違いのものを混ぜた数は見積もりに使えない
- **今回の範囲の集計**: 範囲指定がある場合、同じ形式で範囲内のぶんを併記する
- **フィールド単位の欠落**: 翻訳済み扱いのユニットでも、未設定の `_en` フィールド（`translation-freshness` の欠落判定による）があればユニット別に列挙する
- **注記**: 未完成（open / in_progress）のレッスンも分母に含まれていることを1行添える

範囲指定は**処理対象の限定**であり、走査を絞ってはならない（SHALL NOT）——全体の分母が見えなくなる。範囲外のユニットは報告に含めるだけで、翻訳してはならない（SHALL NOT）。未完成（open / in_progress）のレッスンも対象に含める（SHALL）——status で絞らない。

鮮度は**処理対象を決めるゲートではなく参考情報**である。範囲内の未翻訳・古いユニットは常に処理対象とする（SHALL）。範囲内に**最新（翻訳済み）のユニットがある場合**、スキルはそれらを処理対象に含めるかを**1回だけ**確認しなければならない（SHALL）——選択肢は「未翻訳＋古いだけ」「最新も含めて現行の契約で再点検・更新」「ユニットを選ぶ」。既定は「未翻訳＋古いだけ」とし、範囲内に最新ユニットが無いとき・依頼文で扱いが明示されているときは確認しない（SHALL NOT）。

#### Scenario: コース指定でも全体の進捗が見える

- **WHEN** コース1つを範囲指定してスキルを実行する
- **THEN** レポートに全体の集計（本文・メタ・changelog 別）と、今回の範囲の集計が並ぶ
- **AND** 範囲内の未翻訳・古いユニットは確認なしに処理対象になる

#### Scenario: 部分的に欠けたメタが列挙される

- **WHEN** `name_en` だけ記入済みで `target_en` が空のコースを含む範囲で実行する
- **THEN** レポートの欠落一覧にそのコースと `target_en` が載る

#### Scenario: 最新ユニットを含めるかを1回だけ聞く

- **WHEN** 範囲内に最新のユニットが 3 本あり、依頼文に扱いの指定が無い
- **THEN** レポートの末尾で「最新 3 本を含めるか」を1回だけ確認し、回答に従って処理対象を決める
- **AND** 「未翻訳＋古いだけ」を選んだ場合、最新の 3 本は1ファイルも変更されない

#### Scenario: 最新ユニットが無ければ聞かない

- **WHEN** 範囲内のユニットがすべて未翻訳または古い
- **THEN** 確認の問いは出ず、そのまま処理に入る

### Requirement: 鮮度判定とハッシュは正本 lib を import したスクリプトで計算する

鮮度の判定と、翻訳後に書くハッシュ値（本文ハッシュ・メタハッシュ）は、スキル同梱の走査スクリプトが Studio の正本実装（`studio/lib/translation/freshness.ts`）を import して計算しなければならない（SHALL）。スキルの文書やその場のコードに判定・ハッシュ計算のロジックを複製してはならない（SHALL NOT）。

#### Scenario: 走査スクリプトの出力

- **WHEN** 走査スクリプトを範囲付きで実行する
- **THEN** ユニットごとの状態（本文/メタ）と、翻訳時に書くべきハッシュ値が出力される

### Requirement: 翻訳は契約を読み既訳を活かす差分翻訳で行う

スキルは翻訳の前に `contracts/translation-contract.md` を読み、その規則・用語集に従わなければならない（SHALL）——規則をスキル側に複製しない。既訳が存在するユニットでは既訳を読み取り、原文の変更に対応する箇所と、**現行の契約（用語集・名前の形式と長さ・トーン・英訳するもの／変えないもの）に違反する箇所**だけを更新しなければならない（SHALL）——変わっていない段落の訳文は変えない。最新（翻訳済み）のユニットを処理対象に含めた場合も同じ規則で扱い、訳し直してはならない（SHALL NOT）。

#### Scenario: 古い翻訳の更新

- **WHEN** 原文に1節だけ追記されたレッスンを処理する
- **THEN** 既訳の他の段落は一語も変わらず、追記部分の訳だけが加わる

#### Scenario: 最新の翻訳を現行の契約で再点検する

- **WHEN** 契約に名前の形式（Title Case・階層語）が追加された後、最新のユニットを含めて処理する
- **THEN** 本文中のコース名の表記だけが契約に合わせて直り、他の段落は変わらない
- **AND** ハッシュ行は走査出力の値のままである

### Requirement: 書き込みの対象と作法

書き込みは次に限定しなければならない（SHALL）: (1) `contents.en.md`——1行目に原文ハッシュ行（`translation-freshness` の書式）を持つ全文 (2) `.meta.json` の `_en` フィールド（レッスンは `name_en` / `description_en`、コースは `target_en` を含む）と `en_source_hash`——既存 JSON を読み、対象キーだけを差し替えて書き戻す (3) `changelog.en.md`。次に触れてはならない（SHALL NOT）: `author` / `author_en`・`id` / `order` / `slug` / `cross_series_prev` / `cross_series_next` / `is_start` / `is_goal`・`contents.md`（日本語正本）・画像ファイル。コミットしてはならない（SHALL NOT）——差分レビューと採否は人が行う。

#### Scenario: メタ書き込みの保全

- **WHEN** コース `.meta.json` の `name_en` / `target_en` / `en_source_hash` を書く
- **THEN** `id` / `order` / `slug` / `cross_series_*` / `style` / 日本語フィールドは1文字も変わらない

#### Scenario: author は書かない

- **WHEN** `author_en` が空のレッスンを翻訳する
- **THEN** `author_en` は空のままである

### Requirement: changelog 追訳は不足エントリの先頭挿入に限る

`changelog.en.md` が存在する場合、英語側の先頭エントリより新しい日本語エントリだけを訳し、既存エントリの前（ヘッダー直後）に挿入しなければならない（SHALL）。既存の英訳エントリを変更してはならない（SHALL NOT）。`changelog.en.md` が無ければ全文を翻訳して作成する（SHALL）。ハッシュ行は書かない（SHALL NOT）——changelog の鮮度は日付比較が正本。

changelog の訳文も `contracts/translation-contract.md` の「既存の英語表記に合わせる」に従わなければならない（SHALL）——シリーズ名・コース名・レッスン名は各 `.meta.json` の `name_en` の表記をそのまま使う。スキルは規則の内容を書き写してはならず（SHALL NOT）、契約への参照だけを持たなければならない（SHALL）。

#### Scenario: 追訳の挿入位置

- **WHEN** ja に新エントリが1件増えた状態で処理する
- **THEN** その英訳が `changelog.en.md` の既存エントリ群の前に挿入され、既存部分は不変である

#### Scenario: changelog のシリーズ名が正本と一致する

- **WHEN** 日本語エントリ「ツール開発実践シリーズを公開しました。」を訳す
- **THEN** 英訳のシリーズ名は当該シリーズの `.meta.json` の `name_en`（`Tool Development Practice Series`）と一字一句一致する
- **AND** スキル側に固有名の規則が書き写されていない

### Requirement: 完了報告は差分の見どころを示す

スキルは処理の最後に、書き込んだユニットの一覧（新規翻訳／更新の別）と、レビューの見どころ（訳注コメントを残した箇所・整合の自己点検で気づいたこと）を報告しなければならない（SHALL）。あわせて**実行前後の進捗比較**を報告しなければならない（SHALL）——フェーズ3の走査結果と完了時の再走査結果を同じ形式（本文・メタ・changelog 別）で並べ、今回進んだ量と残量を示す。

**名前を上限に収めるために短縮した、という報告項目を置いてはならない**（MUST NOT）——契約は上限だけを示し、短縮という手順を持たないため、報告する対象が存在しない。

最新（翻訳済み）のユニットを処理した場合、ユニットごとの**変更量**（変更行数の目安）を報告しなければならない（SHALL）——人が「今回の意図を超えて差分が膨らんでいないか」を見るため。閾値による判定はしない。

翻訳品質の最終判断は人の差分レビューに委ねる。

#### Scenario: 完了報告

- **WHEN** コース1つ分の翻訳が終わる
- **THEN** 書いたファイルの一覧と訳注を残した箇所が報告され、コミットはされていない
- **AND** 実行前後の集計が並び、今回進んだ量と全体の残量が読み取れる

#### Scenario: 短縮した名前の報告が無い

- **WHEN** 36 字に収まる英語名を新しく付けたユニットを含む翻訳が終わる
- **THEN** 完了報告に「短縮した名前」の項目は含まれない

#### Scenario: 既訳の変更量が見える

- **WHEN** 最新のユニット 2 本を含めて処理し、うち 1 本だけ用語の修正が入った
- **THEN** 報告に 2 本それぞれの変更行数の目安が並び、修正の無かった 1 本は 0 行である

### Requirement: 自己点検は訳文の受講者読みを含む

スキルは自己点検（機械的な照合）の後に、処理したレッスン本文ごとに受講者役のサブエージェントへ `contents.en.md` **だけ**を渡し、本文の順の心の声で読みづらさ・不自然さを出させなければならない（SHALL）。原文・`contracts/translation-contract.md`・用語集を渡してはならない（MUST NOT）——原文を知った読者は不自然さに気づけない。心の声の方法論は `dx-training-review` の記述を参照し、スキル側に複製してはならない（SHALL NOT）。

受講者読みの指摘は提案であり、採否は訳者が決める（SHALL）——サブエージェントに訳文を修正させてはならない（MUST NOT）。**今回処理しなかったユニット**への指摘は訳文に適用してはならず（MUST NOT）、完了報告に参考として載せる（SHALL）——適用すると差分が今回の変更を超えて膨らみ、人のレビューで「今回何が変わったか」が読めなくなる。処理対象に含めたユニットは、古い翻訳の更新でも最新の再点検でも、その本文全体が採否の対象である。

#### Scenario: 訳した直後に受講者読みが走る

- **WHEN** レッスン1本の翻訳を書き終えて自己点検に入る
- **THEN** 機械照合の後、`contents.en.md` だけを入力とするサブエージェントが本文の順の心の声を出す
- **AND** 訳者が指摘を採否し、採用分だけを訳文に反映する

#### Scenario: 処理しなかったユニットへの指摘は適用されない

- **WHEN** 確認で「未翻訳＋古いだけ」を選び、処理しなかった最新ユニットを参照する段落に受講者読みの指摘が出た
- **THEN** そのユニットの訳文は変更されず、指摘は完了報告に参考として記載される

### Requirement: 規約候補は抽象化して報告に載せるだけ

スキルは受講者読みで**採用した**指摘のうち、他のレッスンや将来の翻訳にも効くものを抽出し、個別具体の修正ではなく**抽象度の高い規則案**にまとめて完了報告に「規約候補」として載せなければならない（SHALL）。抽出は次の3条件で絞る: (1) そのレッスン固有でないこと (2) 既存の契約・用語集で既に言えていないこと (3) 読者の反応であって規範の誤りではないもの（用語集どおりの語への「唐突」等）を除くこと。候補は run あたり最大 3 件とし、0 件のときは「規約候補: なし」の一行で終える（SHALL）。

各候補には、種別（訳す規則／用語／書く規則／検査する規則）・宛先（`contracts/translation-contract.md`・`dx-training-create`・`dx-training-review` のいずれか）・規則案・根拠（具体例）を添える（SHALL）。宛先が翻訳契約でない候補も同じ形で報告に載せる——どこへも書かない。

#### Scenario: 候補が抽象化されて報告に載る

- **WHEN** 受講者読みで「`save` が Ctrl+S と commit の両方を指す」指摘を採用した
- **THEN** 完了報告の規約候補に「原文で同じ語が一般動作と用語の両方に使われるとき、英語では訳し分ける」が、宛先＝翻訳契約・根拠＝該当レッスンとともに載る
- **AND** `contracts/translation-contract.md` は変更されていない

#### Scenario: 検査の規則は review 宛てとして載る

- **WHEN** 採用した指摘が「用語が説明なしに初出する」で、原文にも説明が無い
- **THEN** 候補は種別＝検査する規則・宛先＝`dx-training-review` として報告に載り、review スキルの文書は変更されていない

#### Scenario: 候補が無い

- **WHEN** 採用した指摘がすべてレッスン固有の言い回しだった
- **THEN** 完了報告に「規約候補: なし」の一行だけが載る

### Requirement: 実行スキルは契約とスキル文書を変更しない

スキルは実行中に `contracts/` 配下の契約、自身の `SKILL.md` と `references/`、他スキルの文書を変更してはならない（MUST NOT）——自動で書き換わる規約は実行結果を run ごとにぶれさせる。これらの更新は、スキル更新専用スキル（creating-skills）と、人が explore／grill-me で横断的に見直す経路に限る。

#### Scenario: 契約は run の前後で不変

- **WHEN** 規約候補が 2 件出る run が完了する
- **THEN** `contracts/translation-contract.md` と `.claude/skills/**` の内容は run の開始時と同一である
