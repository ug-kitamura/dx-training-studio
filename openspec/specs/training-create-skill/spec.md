# training-create-skill Specification

## Purpose

レッスン草稿生成スキル（`dx-training-create`）のパッケージ構成と参照ドキュメントを定義する。計画書が決めた構成を入力として、レッスン本文の草稿を生成するスキルの側の規約を扱う。構成そのものの設計は `training-plan-skill` の担当領域。
## Requirements
### Requirement: 執筆原則ドキュメントの配置

`dx-training-create` スキルの執筆原則は `.claude/skills/dx-training-create/references/design-principles.md` として、独立した Markdown ファイルで存在しなければならない（SHALL）。スキルは `SKILL.md` を持ち、スキルとしてロード可能でなければならない（SHALL）。`SKILL.md` は references の内容を重複させてはならない（SHALL NOT）——参照先を書くに留める。

#### Scenario: references が独立したファイルとして存在する

- **WHEN** 開発者が `.claude/skills/dx-training-create/references/` を見る
- **THEN** `design-principles.md` が存在する
- **AND** `lesson-template.md` が存在する

#### Scenario: スキルとしてロードできる

- **WHEN** `.claude/skills/dx-training-create/` を見る
- **THEN** `SKILL.md` が存在する
- **AND** frontmatter に `name` と `description` を持つ

#### Scenario: SKILL.md が references を重複させない

- **WHEN** `SKILL.md` を読む
- **THEN** 執筆原則の本文もレッスンの型の本文も書かれておらず、参照先が示されている

### Requirement: 抽出元と網羅

原則は `ads-lecture/` の講義文字起こしから抽出しなければならない（SHALL）。全11回すべてに当たらなければならない（SHALL）。拾うものが無い回が存在してよく、その場合に無理に項目を作ってはならない（SHALL NOT）。

#### Scenario: 全11回に当たる

- **WHEN** 抽出作業を行う
- **THEN** 第1回から第11回までのすべての文字起こしを読む

#### Scenario: 収穫のない回を許容する

- **WHEN** ある回に本文執筆の判断を変える知見が含まれていない
- **THEN** その回からは何も抽出しない
- **AND** 項目数を揃えるための水増しをしない

### Requirement: 抽出の判定基準

抽出対象は、**レッスン本文を書くときの判断を変えるもの**に限定しなければならない（SHALL）。具体的には説明の順序、図解の使いどころ、たとえの作り方、演習の組み立て、つまずきの扱いを含む。次に該当するものは抽出してはならない（SHALL NOT）: 講義の運営・受講者管理、シリーズ/コース/レッスンの構成設計（`dx-training-plan` の担当領域）、特定ツール固有の事情。

#### Scenario: 本文執筆の判断を変える知見を拾う

- **WHEN** 講義に「概念より先に手を動かさせると定着する」といった記述がある
- **THEN** 本文の構成順に影響するため抽出する

#### Scenario: 構成設計の知見は拾わない

- **WHEN** 講義にコースの並べ方や前提関係に関する記述がある
- **THEN** `dx-training-plan` の担当領域として抽出しない

#### Scenario: 運営の知見は拾わない

- **WHEN** 講義に受講者の募集・出欠・進捗管理に関する記述がある
- **THEN** 抽出しない

#### Scenario: ツール固有の事情は拾わない

- **WHEN** 講義に特定ツールのバージョン差異や設定手順が含まれる
- **THEN** 原則ではなく個別事情として抽出しない

### Requirement: 講義に無い原則を創作しない

`design-principles.md` に記載する原則は、講義文字起こしに根拠があるものだけでなければならない（SHALL）。一般論として尤もらしいだけの原則を追加してはならない（SHALL NOT）。

#### Scenario: 根拠のない原則を追加しない

- **WHEN** 執筆上よく言われる原則を思いついたが、講義に該当する記述がない
- **THEN** その原則は記載しない

### Requirement: dx-training-plan 版との関係

`design-principles.md` は単体で読んで意味が通らなければならない（SHALL）。`dx-training-plan/references/design-principles.md` に既にある原則と重なった場合、原則の説明文を書き写してはならない（SHALL NOT）。見出しと要点を短く示したうえで、**草稿への落とし方**を `dx-training-create` の視点で書かなければならない（SHALL）。`dx-training-plan` 側の references を変更してはならない（SHALL NOT）。

#### Scenario: 重複した原則の扱い

- **WHEN** 抽出した原則が `dx-training-plan` 版に既に存在する
- **THEN** 原則の説明文を複製せず、見出しと要点のみを短く示す
- **AND** 草稿への落とし方だけを新たに書く

#### Scenario: 単体で読める

- **WHEN** `dx-training-plan` 版を読んでいない者が `dx-training-create` 版を読む
- **THEN** 各項目の意味が通じる

#### Scenario: plan 側を変更しない

- **WHEN** 差分を確認する
- **THEN** `.claude/skills/dx-training-plan/` 配下に変更がない

### Requirement: 体裁

`design-principles.md` は既存の `dx-training-plan/references/design-principles.md` と同じ体裁でなければならない（SHALL）。各項目は「原則の見出し」「なぜそうするか」「草稿への落とし方」を対にしなければならない（SHALL）。冒頭に目次を置かなければならない（SHALL）。

#### Scenario: 原則と落とし方が対になっている

- **WHEN** `design-principles.md` の任意の項目を読む
- **THEN** 原則の理由と、草稿に落とすときの具体的な指針の両方が書かれている

#### Scenario: 目次を持つ

- **WHEN** ファイル冒頭を読む
- **THEN** 収録されている原則の分類が一覧できる

### Requirement: 生成範囲と執筆単位を分ける

スキルは生成範囲を**シリーズ / コース / レッスン**の3段階から選べなければならない（SHALL）。既定はコース単位でなければならない（SHALL）。**複数シリーズをまとめて生成する範囲を提示してはならない**（SHALL NOT）。シリーズ単位が選ばれたときは、**所要時間の見積もりを添えた警告を提示しなければならない**（SHALL）。警告はユーザーの選択を妨げてはならない（SHALL NOT）。

範囲がどれであっても、**執筆は1レッスンずつ順次行い、1レッスン書き終えるごとにファイルへ書き出さなければならない**（SHALL）。複数レッスンをまとめて生成してはならない（SHALL NOT）。

#### Scenario: コース単位を選んで3レッスンを書く

- **WHEN** ユーザーがコース単位を選び、そのコースに3レッスンある
- **THEN** 設計メモはコース単位で1本作られる
- **AND** 執筆は1レッスンずつ順に行われ、各レッスンの `contents.md` が書き終えるたびに保存される

#### Scenario: 途中で中断しても再開できる

- **WHEN** コース単位の執筆が2レッスン目で中断される
- **THEN** 1レッスン目の `contents.md` は保存されている
- **AND** 設計メモが残っているため、どこまで書いたかが分かる

#### Scenario: シリーズ単位を選ぶと警告が出る

- **WHEN** ユーザーが生成範囲としてシリーズ単位を選ぶ
- **THEN** そのシリーズのコース数から見積もった所要時間を添えた警告が提示される
- **AND** ユーザーが続行を選べばシリーズ単位で処理が進む

#### Scenario: 複数シリーズ一括は選べない

- **WHEN** スキルが生成範囲の選択肢を提示する
- **THEN** 選択肢はシリーズ / コース / レッスンの3つであり、複数シリーズをまとめて扱う範囲は含まれない

### Requirement: 出力先とディレクトリ命名

生成物は `contents/<シリーズ名>/<コース名>/<レッスン名>/contents.md` に出力しなければならない（SHALL）。ディレクトリ名は**計画書に書かれた名前をそのまま使わなければならない**（SHALL）。slug をディレクトリ名に使ってはならない（SHALL NOT）。既存の `contents/` 配下を変更・削除してはならない（SHALL NOT）。

名前に含まれる禁止文字が置換されることを前提にした記述を持ってはならない（SHALL NOT）——「置換されるので本文の見出しは元の名前でよい」という扱いは、フォルダ名が表示名を兼ねる以上、受講者に見える名前と本文の見出しがずれた状態を容認することになる。名前は `training-plan-skill` の命名規則（禁止文字を使わない）に従っている前提で扱わなければならない（SHALL）。計画書の名前に禁止文字が含まれていた場合は、名前確認ゲートで指摘し、計画書側の修正案を提案しなければならない（SHALL）——スキルが名前を自ら変更してはならない（SHALL NOT）。

#### Scenario: 計画書の名前でディレクトリを作る

- **WHEN** 計画書にシリーズ「はじめに」、コース「DX入門」、レッスン「トレーニングの進め方」とある
- **THEN** `contents/はじめに/DX入門/トレーニングの進め方/contents.md` が作られる

#### Scenario: 名前が衝突する

- **WHEN** 出力先に同名のディレクトリが既に存在する
- **THEN** 衝突する対象を一覧で提示する
- **AND** ユーザーの確認を得るまで書き込まない

#### Scenario: 計画書の名前に禁止文字がある

- **WHEN** 計画書のレッスン名が `リポジトリを作る / clone` である
- **THEN** 名前確認ゲートで禁止文字を含む旨を指摘し、計画書側の修正案（例: `リポジトリを作る／clone`）を提案する
- **AND** スキルが名前を書き換えてディレクトリを作ることはない

### Requirement: 計画書の入力とユーザーによる選択

スキルは計画書を `contents-work/plans/` 配下から読み込まなければならない（SHALL）。複数の計画書が存在する場合、**どれを使うかをユーザーに選ばせなければならない**（SHALL）。最新の 1 本を自動的に選んではならない（SHALL NOT）。

#### Scenario: 計画書を選ばせる

- **WHEN** `contents-work/plans/` に複数の計画書が存在する状態でスキルが起動する
- **THEN** 候補が一覧で提示され、ユーザーが 1 本を選ぶまで先に進まない

#### Scenario: 計画書が 1 本しかない

- **WHEN** `contents-work/plans/` に計画書が 1 本だけ存在する
- **THEN** その 1 本を対象として確認を取る

#### Scenario: 計画書が存在しない

- **WHEN** `contents-work/plans/` に計画書が存在しない
- **THEN** 計画書がない旨を報告し、`dx-training-plan` の実行を促す

### Requirement: フェーズ1で名前と slug の確認ゲートを通す

スキルは生成範囲の確定直後、**その範囲で作られるシリーズ・コース・レッスンの名前を計画書から読み取って一覧提示し、ユーザーの確認を得なければならない**（SHALL）。確認を得るまで後続フェーズへ進んではならない（SHALL NOT）。提示は**範囲内のエントリのみ・一括1回**とし、エンティティごとの都度確認を行ってはならない（SHALL NOT）。

一覧には計画書（第5章・第6章）で定義された **slug** を添えて表示しなければならない（SHALL）。計画書から slug が読み取れない場合はエラーにせず、名前のみを提示しなければならない（SHALL）。

一覧のコース行には、計画書から読み取った **`style`（受講形態）も添えて表示しなければならない**（SHALL）。ここでは表示のみとし、計画書に `style` があるコースについて改めて問うてはならない（SHALL NOT）——計画書に書いてあることを聞き返さない原則に従う。計画書から `style` が読み取れないコースは、その旨がわかる表示（「未設定」等）にしなければならない（SHALL）。

ユーザーが名前を否認した場合、スキルは**実行を止め、計画書側の修正案を提案しなければならない**（SHALL）。スキルが計画書やディレクトリ名を自ら変更してはならない（SHALL NOT）——命名は `dx-training-plan` の守備範囲のまま維持する。

#### Scenario: 名前を承認して進む

- **WHEN** ユーザーがコース単位の範囲を選ぶ
- **THEN** そのコースが属するシリーズ名・コース名・範囲内のレッスン名が slug 付きで一覧提示される
- **AND** コース行には計画書の受講形態が添えられる
- **AND** ユーザーが承認すると後続フェーズへ進む

#### Scenario: 名前を否認すると停止して提案する

- **WHEN** 一覧提示に対しユーザーが「シリーズ名を変えたい」と答える
- **THEN** スキルは実行を止め、計画書側の修正案を提案する
- **AND** ディレクトリは1つも作られていない

#### Scenario: 範囲外の名前は提示しない

- **WHEN** レッスン単位の範囲を選ぶ
- **THEN** 提示されるのはそのレッスンと親のコース・シリーズの名前のみで、計画書の他のシリーズは含まれない

#### Scenario: slug の無い計画書でもエラーにしない

- **WHEN** 選んだ計画書に slug の定義が無い
- **THEN** 名前のみの一覧が提示され、確認ゲートは通常どおり機能する

#### Scenario: 計画書に受講形態があるコースは聞かれない

- **WHEN** 範囲内の全コースに計画書の受講形態がある
- **THEN** 一覧にその受講形態が表示され、受講形態を問う質問は出ない

### Requirement: 計画書に受講形態が無いコースは実行時に確定する

計画書から `style`（受講形態）を読み取れないコースが生成範囲にあるとき、スキルはフェーズ1で**その値をユーザーに確認して確定させなければならない**（SHALL）。確認を得ずに `style` を省略してコースを作ってはならない（SHALL NOT）。

確認は**執筆者（`author`）の確認とは別の問いとしなければならない**（SHALL）。両者を1つの問いにまとめてはならない（SHALL NOT）——`author` は run に1つで答えが1語、`style` はコースごとに変わりうる値であり、回答の形が異なる。問う順序は `author` の**後**とする（SHALL）。

問いは**1回にまとめなければならない**（SHALL）。受講形態が読み取れないコースが複数あってもコースごとに問いを分けてはならない（SHALL NOT）。問いには対象コースを列挙し、各コースに既定値として **`self-study`** を添えて提示しなければならない（SHALL）——コース単位で異なる指定を受け取れる形にする（SHALL）。

確定した値は当該コースの `.meta.json` の `style` に書かなければならない（SHALL）。計画書を書き換えてはならない（SHALL NOT）——命名と計画の修正は `dx-training-plan` の守備範囲である。ただし確定した値は**実行のふりかえりで計画書への反映を提案しなければならない**（SHALL）。

#### Scenario: 受講形態が読み取れないコースがある

- **WHEN** 生成範囲の2コースについて計画書に受講形態の記載が無い
- **THEN** 執筆者を問うた後に、その2コースを列挙し既定 `self-study` を添えた問いが1回だけ出る

#### Scenario: コースごとに違う受講形態を指定できる

- **WHEN** 上記の問いに対しユーザーが1コースだけ `lecture` を指定する
- **THEN** そのコースの `.meta.json` の `style` は `lecture`、もう1コースは `self-study` になる

#### Scenario: 既定のまま進める

- **WHEN** 上記の問いに対しユーザーが既定を承認する
- **THEN** 対象コースすべての `.meta.json` の `style` が `self-study` になる

#### Scenario: 執筆者の問いとまとめない

- **WHEN** 計画書に受講形態が無いコースがある run を実行する
- **THEN** 執筆者を問うメッセージと受講形態を問うメッセージは別々に出る

#### Scenario: 全コースに記載があれば問わない

- **WHEN** 生成範囲の全コースに計画書の受講形態がある
- **THEN** 受講形態を問う質問は出ず、計画書の値がそのまま `.meta.json` に書かれる

### Requirement: 設計メモの出力

執筆の前に設計メモを出力し、ユーザーの承認を得なければならない（SHALL）。設計メモは `contents-work/runs/<yyyymmdd>-<slug>/design-note.md` に出力しなければならない（SHALL）。範囲（全体 / シリーズ / コース / レッスン）に応じてファイル名を変えてはならない（SHALL NOT）——範囲と対象は run ディレクトリ名が表す（`contents-work-layout` を参照）。設計メモは**要求と供給の突き合わせを兼ねなければならない**（SHALL）。

`contents-work/runs/` は git の追跡対象外である。設計メモに書かれた社内素材の作業リストを別の環境へ渡す手段は問わないが、**チャットに流して済ませてはならない**（SHALL NOT）——ファイルとして残らなければ届かない。

> **2026-08-11 の変更**: 旧要件は出力先を `docs/<yyyymmdd>/` とし、範囲別に4種のファイル名（`overall.md` / `{シリーズslug}.md` / `{シリーズslug}-{コースslug}.md` / `{シリーズslug}-{コースslug}-{レッスンslug}.md`）を使い分け、同日再実行時に既存の最大連番+1 を付けることを求めていた。識別子を run ディレクトリ名が持つ方式に変更したため、いずれも不要となり削除した。経緯は archive の `adopt-contents-plan-layout/design.md` D2 を参照。

#### Scenario: 設計メモを出力して承認を得る

- **WHEN** 情報収集フェーズが終わる
- **THEN** 設計メモ案が提示される
- **AND** ユーザーが承認するまで本文の執筆に進まない
- **AND** 承認された設計メモは `contents-work/runs/<yyyymmdd>-<slug>/design-note.md` に書き出される

#### Scenario: 範囲によらず同じファイル名を使う

- **WHEN** 生成範囲にシリーズ単位を選ぶ
- **THEN** 設計メモのファイル名は `design-note.md` であり、範囲によって変わらない

#### Scenario: 同日に再実行する

- **WHEN** `contents-work/runs/20260806-start-setup/` が既に存在する状態で同じコースを再実行する
- **THEN** 別の run ディレクトリが作られ、その中に `design-note.md` が出力される
- **AND** 既存の run ディレクトリの `design-note.md` は上書きされない

#### Scenario: 要求と供給を突き合わせる

- **WHEN** 設計メモを読む
- **THEN** そのレッスンが前提とする知識（要求）と、どのレッスンでそれが供給されるかが対応づけられている

### Requirement: 社内コンテキストを3段梯子で解決する

スキルは設計メモの作成時に、**社内データが必要な箇所を全列挙し、3段の梯子で解決しなければならない**（SHALL）。解決は承認ゲートの前に完了しなければならない（SHALL）。執筆フェーズ中にユーザーへ社内データを都度質問してはならない（SHALL NOT）。

- **段1（DB 検索）**: 実行環境から届く社内コンテキストのバックエンドを検索する。`local-db/context-items.json` が存在すれば読んで走査し、`DATABASE_URL` が利用できれば Neon を検索する。両方届く場合は結果をマージする（SHALL）。運用中の保存先モードの判定を試みてはならない（SHALL NOT）——読み取りのマージは無害であり、判定材料はスキルから参照できない
- **段2（一括問合せ)**: 段1で解決しなかった箇所を、**まとめて1回**ユーザーに問い合わせる（SHALL）。聞き取る項目は**本文・ソースURL・ソース最終更新日（任意）** の3点に限る（SHALL）。title・tags・本文の整形はスキルが自動で行わなければならない（SHALL）
- **段3（空欄）**: 段2でも解決しなかった箇所を空欄として設計する（SHALL）

設計メモには**社内データの解決表**を含めなければならない（SHALL）——箇所ごとに、どの段で解決したかを記録する。段1で解決した箇所には使用したアイテム（id・title・source_url）と使い先を記さなければならない（SHALL）。段1・段2の解決内容は既存の承認ゲートで確認され、新しい確認ゲートを追加してはならない（SHALL NOT）。

#### Scenario: 段1でヒットして本文素材になる

- **WHEN** 設計メモ作成時に社内の運用ルールが必要な箇所があり、`local-db/context-items.json` に該当アイテムが存在する
- **THEN** その箇所は空欄ではなく本文素材として設計される
- **AND** 解決表に使用アイテムの id・title・source_url と使い先が記録される

#### Scenario: バックエンドに届かず段2へ降格する

- **WHEN** `local-db/context-items.json` が存在せず、`DATABASE_URL` も利用できない
- **THEN** 段1はスキップされ、社内データが必要な箇所はまとめて段2の問合せに回る

#### Scenario: 段2で回答が得られず空欄になる

- **WHEN** 段2の問合せに対しユーザーが「今は出せない」と答える
- **THEN** その箇所は段3として空欄に設計される
- **AND** 空欄の記法は従来の3種別に従う

#### Scenario: 両バックエンドを併読する

- **WHEN** `local-db/context-items.json` が存在し、かつ `DATABASE_URL` も利用できる
- **THEN** 両方を検索して結果をマージする
- **AND** どちらが運用中の正本かの判定は行わない

#### Scenario: 承認ゲート前に解決が完了している

- **WHEN** ユーザーが承認ゲートで設計メモを確認する
- **THEN** すべての社内データ必要箇所が段1〜3のいずれかに解決済みで、解決表から空欄の量が読み取れる

### Requirement: 社内コンテキストの店に書き込まない

スキルは社内コンテキストのバックエンド（`local-db/context-items.json`・Neon）に対して**読み取り専用**でなければならない（SHALL）。いかなる場合も正本へ直接書き込んではならない（MUST NOT）——スキルは運用中の正本を判定できず、直接書き込みは影の正本を生む。

段2で聞き取った内容は、run ディレクトリの **`context-outbox.json`** に退避しなければならない（SHALL）。形式は登録 API（`POST /api/context/items`）の入力スキーマに一致する配列でなければならない（SHALL）: `title` / `body` / `tags` / `source_url` / `source_last_updated_at`（null 可）。**`id` を書いてはならない**（SHALL NOT）——バックエンドごとに独立採番のため、登録は必ず新規作成を通す。

outbox を書き出した時点と run の終了時に、**dx-training-studio で正規の保存先へ登録するようメッセージで促さなければならない**（SHALL）。登録工程そのものはスキルの責任範囲外とする。

#### Scenario: 段2の回答を outbox に退避する

- **WHEN** 段2でユーザーが本文・ソースURL・最終更新日を提出する
- **THEN** スキルが title と tags を自動生成し、登録スキーマ準拠の要素として `context-outbox.json` に追記する
- **AND** `local-db/context-items.json` にも Neon にも書き込まない

#### Scenario: outbox に id を書かない

- **WHEN** `context-outbox.json` を読む
- **THEN** どの要素にも `id` フィールドが存在しない

#### Scenario: 登録を促すメッセージ

- **WHEN** outbox に1件以上の要素がある状態で run が終了する
- **THEN** outbox 書き出し時と run 終了時の計2回、dx-training-studio での登録を促すメッセージが出ている

### Requirement: 社内コンテキスト由来の出典表記

社内コンテキスト DB のアイテムを本文素材に使った箇所には、Web 出典と同じ**斜体1行・タイトルにリンクを埋め込む形式**で出典を添えなければならない（SHALL）。リンク先は当該アイテムの `source_url` とする（SHALL）。括弧内の日付は取得日ではなく**ソース最終更新日**（`source_last_updated_at`）を「YYYY年M月D日更新」の形で書かなければならない（SHALL）。最終更新日が無い場合は日付の括弧ごと省略しなければならない（SHALL）。

#### Scenario: 最終更新日があるアイテム

- **WHEN** `source_last_updated_at` が `2026-08-01` のアイテムを本文に使う
- **THEN** 出典は `*出典: [タイトル](ソースURL)（2026年8月1日更新）*` の形式で書かれる

#### Scenario: 最終更新日がないアイテム

- **WHEN** `source_last_updated_at` が null のアイテムを本文に使う
- **THEN** 出典は `*出典: [タイトル](ソースURL)*` となり、日付の括弧が現れない

### Requirement: 模範解答が無い状態を正常として扱う

`references/model-answer/` が存在しない、または空である状態をエラーとして扱ってはならない（SHALL NOT）。模範解答が無い場合は `lesson-template.md` と `design-principles.md` だけで執筆しなければならない（SHALL）。実行の最後に、生成した草稿を模範解答へ昇格させるかをユーザーに問わなければならない（SHALL）。

#### Scenario: 模範解答が無い状態で実行する

- **WHEN** `references/model-answer/` が存在しない状態でスキルを実行する
- **THEN** エラーにならず、型はテンプレート、質は執筆原則が支える形で執筆が進む

#### Scenario: 昇格を促す

- **WHEN** 執筆と曼陀羅フェーズが終わる
- **THEN** 出来の良い草稿を模範解答に昇格させるかをユーザーに問う

### Requirement: 曼陀羅フェーズを最後に固定する

曼陀羅（コース間のつながり）に関する作業は、生成範囲に関わらず**最後のフェーズとして実行しなければならない**（SHALL）。同一シリーズ内の順序は `.meta.json` の `order` で表現しなければならない（SHALL）。シリーズをまたぐ分岐・合流は**提案に留めなければならない**（SHALL）——`cross_series_prev/next` を書き込んではならない（SHALL NOT）。

曼陀羅案は当該実行の run ディレクトリに `mandala.md` として保存しなければならない（SHALL）。

`mandala.md` には**曼陀羅フローのアスキーアートを含めなければならない**（SHALL）。図には、シリーズ内のコースの並びと、シリーズをまたぐ辺の両方を含めなければならない（SHALL）。**`.meta.json` に反映済みの辺と、提案に留まる未書き込みの辺を描き分け**（実線／破線など）、凡例を添えなければならない（SHALL）。**今回の run で作った範囲を図の中で明示しなければならない**（SHALL）。

図法は `dx-training-plan/references/mandala-guide.md` と計画書第3章の型に従うものとし、`dx-training-create` 側で独自の図法を定義してはならない（SHALL NOT）。

#### Scenario: レッスン単位でも曼陀羅フェーズを通る

- **WHEN** 生成範囲にレッスン単位を選ぶ
- **THEN** 執筆後に曼陀羅フェーズが実行される
- **AND** そのレッスンがコース内のどの位置に入るかが確認される

#### Scenario: シリーズまたぎは提案に留める

- **WHEN** 別シリーズとの接続が必要だと判断する
- **THEN** 接続案を提示する
- **AND** `.meta.json` の `cross_series_prev` / `cross_series_next` は書き換えない

#### Scenario: 曼陀羅案をファイルに残す

- **WHEN** 曼陀羅フェーズが完了する
- **THEN** run ディレクトリに `mandala.md` が保存される

#### Scenario: 確定した辺と提案の辺が図で区別できる

- **WHEN** 接続先のコースが未作成のため辺を書き込めない
- **THEN** `mandala.md` の図でその辺が未書き込みと分かる記法（破線など）で描かれる
- **AND** `.meta.json` の `order` で表現済みのコースの並びは確定した記法で描かれる
- **AND** 図に凡例が添えられている

### Requirement: 自己レビュー

執筆した草稿に対し、**フレッシュな文脈でのレビューを行わなければならない**（SHALL）。レビュー役に修正させてはならない（SHALL NOT）——指摘のみを受け取り、反映は執筆側が判断する。レビューは全体評価だけでなく、**読者が頭から読んだときの反応を時系列で出させなければならない**（SHALL）。

レビュー結果は当該実行の run ディレクトリの **`reviews/<レッスン名>.md`** として保存しなければならない（SHALL）。レビュー結果をチャットに出力するだけで済ませてはならない（SHALL NOT）。

#### Scenario: 時系列のレビューを行う

- **WHEN** 1レッスンの草稿が書き終わる
- **THEN** 初学者が頭から読んだときの反応が、本文の順に沿って出力される
- **AND** 全体をまとめた評価だけでは終わらない

#### Scenario: レビュー役に修正させない

- **WHEN** レビューで指摘が出る
- **THEN** レビュー役は改善案を出すに留まり、本文を書き換えない

#### Scenario: レビュー結果をファイルに残す

- **WHEN** コース単位の実行で 3 レッスンを執筆しレビューする
- **THEN** run ディレクトリの `reviews/` に 3 本の `<レッスン名>.md` が保存される
- **AND** run 直下のファイルは `design-note.md` と `mandala.md` のままである

### Requirement: run の最初に執筆者を確認する

スキルはフェーズ1で、その run の**執筆者（`author`）を1回だけユーザーに確認しなければならない**（SHALL）。レッスンごとに繰り返し確認してはならない（SHALL NOT）。確認した値はその run で出力する全レッスンに適用しなければならない（SHALL）。

#### Scenario: 執筆者を1回だけ聞く

- **WHEN** ユーザーが計画書を選び、生成範囲を決める
- **THEN** スキルは執筆者名を1度だけ問う
- **AND** 以降のレッスン執筆中に執筆者名を再度問わない

### Requirement: 同一シリーズの用語とたとえを run をまたいで引き継ぐ

設計メモを作る際、スキルは `contents-work/runs/` 配下の**同一シリーズを対象とした過去の設計メモを探して読まなければならない**（SHALL）。見つかった場合、そこで固定された用語の呼び名とたとえの体系を**引き継がなければならない**（SHALL）。引き継いだ内容は今回の設計メモにも記さなければならない（SHALL）。

過去の設計メモが存在しない場合は、引き継ぎを行わずに進めなければならない（SHALL）。これを異常として扱ってはならない（SHALL NOT）。

#### Scenario: 同シリーズの2コース目を書く

- **WHEN** 同じシリーズの別コースを過去の run で作成済みである
- **AND** その設計メモで「コミット＝セーブポイント」というたとえが固定されている
- **THEN** 今回の設計メモでも同じたとえが使われる
- **AND** 同じ概念に別のたとえを新しく作らない

#### Scenario: そのシリーズの初回実行

- **WHEN** `contents-work/runs/` に同一シリーズを対象とした設計メモが存在しない
- **THEN** 引き継ぎを行わずに設計メモを作成する

### Requirement: 1レッスンごとに設計メモと突き合わせる

スキルは**1レッスンを書き終えるごとに、そのレッスンに対応する設計メモの記載と本文を突き合わせなければならない**（SHALL）。突き合わせの対象は、用語の呼び名・空欄の一覧・画像計画を含まなければならない（SHALL）。ずれを見つけた場合、自己レビューに回す前に解消しなければならない（SHALL）。

#### Scenario: 設計メモの空欄が本文に反映されていない

- **WHEN** 設計メモが特定の箇所を社内の空欄とする計画である
- **AND** 書き上げた本文がその箇所を空欄を介さない断定文で書いている
- **THEN** 突き合わせでずれが検出され、自己レビューの前に解消される

#### Scenario: 用語の呼び名が設計メモとずれている

- **WHEN** 設計メモの用語表が「操作」と定めている概念を、本文が「動詞」と呼んでいる
- **THEN** 突き合わせでずれが検出され、設計メモの呼び名に揃えられる

### Requirement: 実行の最後にふりかえりを行う

スキルは実行の最後に、**その run で得た改善候補を列挙し、`references/` へ反映するかをユーザーに問わなければならない**（SHALL）。ユーザーが承認した項目のみを `references/` に反映しなければならない（SHALL）。

ふりかえりの結果を run ディレクトリその他に**蓄積用のファイルとして書き出してはならない**（SHALL NOT）——学びの受け皿は `references/` と模範解答であり、run ごとの蓄積は重複と矛盾を生む。

#### Scenario: 改善候補を提示する

- **WHEN** 執筆・自己レビュー・曼陀羅のフェーズが完了する
- **THEN** その run で気づいた改善候補が列挙され、`references/` へ反映するかがユーザーに問われる

#### Scenario: 承認されなかった候補は反映しない

- **WHEN** 提示した改善候補のうち一部をユーザーが却下する
- **THEN** 却下された候補は `references/` に反映されない
- **AND** 却下された候補を別ファイルに保存しない

### Requirement: 受講者の前提を固定する

本文は、受講者が**社内の業務環境で学ぶこと**を前提に書かなければならない（SHALL）。私物 PC・社外の共有フォルダ・個人所有の資料を代替手段として提示してはならない（SHALL NOT）。

本文は、受講者が**基礎的な英語を読めること**を前提に書かなければならない（SHALL）。短い英語の画面表示やメッセージについて「英語を読める必要はない」といった記述をしてはならない（SHALL NOT）。

#### Scenario: 演習の対象が手元に無い場合の案内

- **WHEN** 演習が業務フォルダを対象とする
- **AND** 対象が見つからない受講者への代替案を書く
- **THEN** 代替案は業務環境の中で完結し、私物 PC を持ち出さない

#### Scenario: 英語表示への言及

- **WHEN** 本文がツールの短い英語表示に言及する
- **THEN** 「英語を読める必要はない」といった前置きを置かず、表示の意味を説明する

### Requirement: 本文の記法

本文の記法は次に従わなければならない（SHALL）。

- 前後のレッスンへの参照は**記述的に**行う（「前のレッスンで」「三大エリアのレッスンで」）。`L06` のような**レッスン番号を読者向け本文に書いてはならない**（SHALL NOT）
- コマンド一覧・比較・利点と欠点の整理など、項目と属性が対応づく情報は**表で示す**（SHALL）
- 補足・ヒント・重要事項・警告・危険は、必要に応じて **GitHub アラート**（`[!NOTE]` / `[!TIP]` / `[!IMPORTANT]` / `[!WARNING]` / `[!CAUTION]`）で示してよい（MAY）
- コードフェンスには**言語を指定しなければならない**（SHALL）。差分を示す場面では `diff` フェンスを用いなければならない（SHALL）
- 出典は**タイトル文字列にリンクを埋め込む形式**で書かなければならない（SHALL）。URL を本文にそのまま書き下してはならない（SHALL NOT）
- 単純化した説明を書いたと自覚した箇所には、**厳密には異なる旨の断りをその場に1行足さなければならない**（SHALL）

#### Scenario: 前のレッスンを参照する

- **WHEN** 本文が既習の内容に言及する
- **THEN** 「前のレッスンで」のように記述的に参照する
- **AND** `L06` のようなレッスン番号は本文に現れない

#### Scenario: コマンドの一覧を示す

- **WHEN** 複数のコマンドとその役割を並べて示す
- **THEN** 箇条書きではなく表で示す

#### Scenario: 出典の書式

- **WHEN** Web で調べた事実に出典を添える
- **THEN** 出典はタイトル文字列にリンクを埋め込んだ形式で書かれる
- **AND** 生の URL が本文に露出しない

#### Scenario: 差分を見せる

- **WHEN** 変更前後の差分をコードブロックで示す
- **THEN** フェンスの言語は `diff` である

### Requirement: 確認問題は本文で確認できる形に限る

確認問題は、**本文を読み返せば受講者が自分で答えを確認できる問い**に限らなければならない（SHALL）。計算や複数選択など、解答が無いと正誤を判断できない問いを出してはならない（SHALL NOT）。確認問題に解答を付けてはならない（SHALL NOT）。

#### Scenario: 言い換えを求める問い

- **WHEN** レッスンの確認問題を作る
- **THEN** 学んだ概念を自分の言葉で言い換えさせる、または学んだ枠組みで分類させる問いになる
- **AND** 解答は本文に書かれていない

### Requirement: 実在アプリの画面を求める画像スロットに代替手段を書き添える

VSCode・GitHub のような**実在するアプリの画面**を求める画像スロットには、**生成品質が悪い場合にスクリーンショットで代用してよい旨の注意書き**をプロンプトのコメントに含めなければならない（SHALL）。生成の難易度をスキルが事前に判定して書き分けてはならない（SHALL NOT）。注意書きは `contracts/image-slot-contract.md` が定める書式を逸脱してはならない（SHALL NOT）。

さらに、実在アプリの画面を求めるプロンプトは**純再現かラベル付きかを明示しなければならない**（SHALL）。

- **純再現**: 画面の再現のみを求め、**実際の画面に表示されない説明ラベル・ヒント・タイトルを加えない旨をプロンプトに明記する**（SHALL）
- **ラベル付き**: 欲しい注釈（対応ラベル等）を**明示的に列挙し**、列挙外の注釈を足させない（SHALL）

どちらのモードでもスクリーンショット代用の注意書きは維持する（SHALL）。

#### Scenario: VSCode の画面を求めるスロット

- **WHEN** 本文に VSCode の実行画面を求める画像コメントを置く
- **THEN** コメントに、品質が悪ければスクリーンショットで代用する旨の注意書きが含まれる

#### Scenario: 純再現のスロット

- **WHEN** 説明を混ぜない画面再現だけが欲しいスロットのプロンプトを書く
- **THEN** プロンプトに「画面の再現のみ。実際の画面に表示されない説明ラベル・ヒント・タイトルを加えない」の趣旨が明記される

#### Scenario: ラベル付きのスロット

- **WHEN** 画面に操作とコマンドの対応（例:「＋ ＝ git add」）を添えたいスロットのプロンプトを書く
- **THEN** 欲しいラベルがプロンプトに列挙され、それ以外の注釈を足さない趣旨が読み取れる

#### Scenario: 概念図のスロット

- **WHEN** 本文に実在アプリの画面ではない概念図を求める画像コメントを置く
- **THEN** 代替手段の注意書きも純再現/ラベル付きの指定も付けない

### Requirement: コマンド出力を検証する

手順型のレッスンでコマンドの実行結果を本文に書く場合、**コマンドを実行できる環境ではコマンドを実際に実行して出力を確認しなければならない**（SHALL）。実行できない環境ではその旨を認識し、出力の記述を推測で断定してはならない（SHALL NOT）。

出力を簡略化して載せる場合、**要点だけを抜き出している旨を明示しなければならない**（SHALL）。

#### Scenario: 実行できる環境でコマンド出力を書く

- **WHEN** コマンド実行ツールが利用できる環境で手順型レッスンを執筆する
- **AND** 本文に `git diff` の出力例を載せる
- **THEN** 実際に実行した結果と照合してから記述する

#### Scenario: 出力を簡略化する

- **WHEN** 実際の出力から一部を抜き出して本文に載せる
- **THEN** 要点だけを抜き出している旨が本文に明示される

### Requirement: 画像を置く節にはプロンプトコメントを必ず出力する

スキルが画像を置くと判断した節（本文や見出しが画像の存在を前提にする節を含む）には、`contracts/image-slot-contract.md` の書式に従う **HTML コメントのプロンプトを必ず出力しなければならない**（SHALL）。画像を前提にした本文だけを書き、プロンプトコメントを省略してはならない（SHALL NOT）。フェーズ5の設計メモ突き合わせでは、画像計画に対する**コメントの実在**を確認しなければならない（SHALL）。

⚠ プロンプトコメントの効用を説明する際、特定ホストの画面上の位置（ペイン番号）を書いてはならない（SHALL NOT）——`skill-host-independence` capability の規則に従う。

#### Scenario: 実在アプリの画面を紹介する節

- **WHEN** 「VSCode ではこう見える」のような、画面を見せることを前提にした節を書く
- **THEN** その節にプロンプトコメントが置かれ、作者はコメントの内容をそのまま画像生成に渡せる

#### Scenario: 画像不要と判断した節

- **WHEN** アスキーアートや本文だけで足りるとスキルが判断した節を書く
- **THEN** プロンプトコメントは置かれず、画像の存在を前提にした記述も本文に現れない

### Requirement: 執筆原則に禁止事項の節を持つ

`references/design-principles.md` は「書いてはいけないもの」の節を持ち、次の5項目を含まなければならない（SHALL）。

1. 誹謗・中傷・愚痴をしない — 特定の人物や組織に対する誹謗・中傷・愚痴は一切禁止。文脈上どうしても必要な場合はポジティブな言葉に置き換える
2. 実在の個人名・顧客名・取引先名・未公開の社内情報を本文やたとえに使わない — 社内情報は3段梯子（DB 検索 → 問合せ → 空欄）の正規ルートのみ
3. 職種・年齢・性別・人種で人物像を型に当てはめるたとえを使わない
4. 政治・宗教・災害・病気・事故、および人種・人事評価・ハラスメントを想起する題材を、たとえ話に使わない
5. 損失フレームで学習動機を作らない — 「やらないと置いていかれる」「覚えたものが無駄になる」のような失う怖さで受講を促す書き方をしない。動機づけは目的・ゴール・得られるものの提示で行う

この節は負の制約（模範解答から読み取れないもの）に限定し、トンマナ等の正の基準を追加してはならない（SHALL NOT）。

#### Scenario: たとえ話の生成時に禁止題材を避ける

- **WHEN** スキルが概念のたとえ話を生成する
- **THEN** 職種・年齢・性別・人種で型に当てはめた人物像や、政治・宗教・災害・病気・事故・人種・人事評価・ハラスメントを想起する題材は使われない

#### Scenario: 節が負の制約に限定されている

- **WHEN** 開発者が「書いてはいけないもの」の節を読む
- **THEN** 禁止事項のみが列挙され、文体・語調などの正の基準は含まれていない

#### Scenario: 損失フレームを使わない

- **WHEN** レッスン冒頭で受講の動機づけを書く
- **THEN** 「技術に置いていかれる」のような失う怖さの文は使われず、修了時に得られるものの提示で動機づけられる

### Requirement: 埋められない箇所を空欄として残す

3段梯子で解決できなかった箇所（段3）は、本文に**空欄**として残さなければならない（SHALL）。空欄は3種類を使い分けなければならない（SHALL）: `> **社内**:`（社内情報のテキスト）、`> **社内画像**:`（社内画面の撮影・録画）、`> **素材**:`（一般だが人手が要る画像）。画像生成用の HTML コメントの書式を変更してはならない（SHALL NOT）。

社内情報の空欄には、**答えるべき問いを箇条書きで具体的に書かなければならない**（SHALL）。あわせて期待する形式と分量を指定しなければならない（SHALL）。空欄は後工程で空欄を埋める作業者がこの実行の文脈なしで埋められるよう**自己完結していなければならない**（SHALL）。空欄の周囲に一般論を書いてはならない（SHALL NOT）——導入文と次への接続文のみを書く。

#### Scenario: 社内手順の空欄を残す

- **WHEN** 社内システムからの申請手順が必要な箇所が、段1・段2で解決しなかった
- **THEN** `> **社内**:` の blockquote が置かれる
- **AND** システムの呼称・画面の経路・必須入力項目・通知先・リードタイムといった答えるべき問いが箇条書きで書かれている
- **AND** 「番号付き手順3〜5ステップ / 200〜300字」のような形式と分量が指定されている

#### Scenario: 一般論で埋めない

- **WHEN** 社内手順が分からない箇所を書く
- **THEN** 一般的な手順を書いて「社内向けに直せ」と注記することはしない
- **AND** 導入文と次の段落への接続文だけを書く

#### Scenario: 画像コメントの書式を変えない

- **WHEN** AI 生成で埋まる画像の枠を置く
- **THEN** `contracts/image-slot-contract.md` の定める HTML コメント（プロンプト本文のみ）で書く
- **AND** 印や接頭辞を付けない

### Requirement: 執筆中に見つけた空欄を承認なしに追加しない

執筆中に設計メモに無い社内データの必要箇所が判明した場合、**まず段1（DB 検索）で解決を試みなければならない**（SHALL）。段2（ユーザーへの問合せ）を執筆中に行ってはならない（SHALL NOT）——執筆フローを細切れにしない。段1で解決しない場合は空欄（段3）とし、本文に書き込む前にユーザーに提示して承認を得なければならない（SHALL）。承認後、**設計メモと本文を同時に更新しなければならない**（SHALL）。設計メモを承認なしに更新してはならない（SHALL NOT）。

#### Scenario: 執筆中の発見はまず DB を検索する

- **WHEN** 執筆中に、設計メモに載っていない社内情報が必要だと判明する
- **AND** 段1の検索で該当アイテムが見つかる
- **THEN** ユーザーへの問合せは発生せず、本文素材として使う承認を空欄の追加提案と同じ手順で得る
- **AND** 承認後に設計メモの解決表と本文の両方へ反映する

#### Scenario: 新しい空欄を見つける

- **WHEN** 執筆中に、設計メモに載っていない社内情報が必要だと判明する
- **AND** 段1の検索で解決しない
- **THEN** その空欄の内容をユーザーに提示して承認を求める
- **AND** 承認後に設計メモと本文の両方へ反映する

#### Scenario: メモと本文がずれない

- **WHEN** 執筆が終わる
- **THEN** 本文にあるすべての空欄が設計メモの作業リストに載っている

### Requirement: レッスンの型に情緒の3段レベルを持つ

`references/lesson-template.md` は、レッスンの位置に応じた情緒表現の3段レベルを定義しなければならない（SHALL）。

- **Lv0（全レッスン共通）**: 冒頭と結びに気の利いた声かけを一言ずつ置く（SHALL）。本文中の節に情緒表現を足してはならない（SHALL NOT）
- **Lv1（シリーズの最初 / 最後のレッスン）**: 声かけは定型構造に従わなければならない（SHALL）。開き=①このシリーズで学ぶこと＋②終了時に手にするもの / 閉じ=①ねぎらい＋②手にした武器＋③解放される次の行き先。穴は計画書のコース仕様（学習目標）と曼陀羅の辺から埋めなければならず（SHALL）、創作してはならない（SHALL NOT）。閉じの「次の行き先」は解放フレーム（「□□が解放されました」等）で書き、辺が複数あるとき一本道の順序として指定してはならない（SHALL NOT）
- **Lv2（計画書が集合（F2F）と定めたコースのレッスン。コースの `format` で判定する）**: 情緒を声かけに留めず本文の骨格に組み込む（SHALL）。キックオフでは目的・ゴール・修了時に得られるものを冒頭で明示し、最終レッスンでは称えと完結を扱う

定型の文言をテンプレートに固定してはならない（SHALL NOT）——規定するのは構造のみ。計画書が全体フレーム（比喩の世界観）を指定する場合、その語彙は説明なしで通じる最小セットに限り、声かけと情緒ビートにだけ使わなければならない（SHALL）。既存コンテンツへの遡及適用を要求してはならない（SHALL NOT）。

#### Scenario: 中間レッスンの情緒は声かけ2箇所のみ

- **WHEN** シリーズの最初でも最後でもない self-study レッスンを執筆する
- **THEN** 冒頭と結びに声かけが一言ずつ置かれる
- **AND** 本文中の節に情緒表現・全体フレームの語彙が現れない

#### Scenario: シリーズ最後のレッスンの閉じ

- **WHEN** シリーズ最後のレッスンの結びを書く
- **THEN** ねぎらい・このシリーズで手にした武器・解放される次の行き先が含まれる
- **AND** 手にした武器は計画書の学習目標から、次の行き先は曼陀羅の辺から取られている
- **AND** 辺が複数ある場合も「次は□□へ進め」という一本道の指定にならない

#### Scenario: F2F キックオフのレッスン

- **WHEN** 計画書が集合（F2F）と定めたキックオフレッスンを執筆する
- **THEN** トレーニングの目的・ゴール・修了時に得られるものが冒頭で明示される
- **AND** 損失フレーム（置いていかれる等）で受講動機を作らない

#### Scenario: 既存コンテンツに遡及しない

- **WHEN** 情緒レベル導入前に生成されたレッスンが `contents/` に存在する
- **THEN** スキルはそれらへの声かけ追加を要求せず、レビューの前提にもしない

### Requirement: 手順型レッスンの画像密度

手順型レッスンでは、スキルが画面遷移を知っている操作手順（公開ツールのインストール・設定等）について、**画面が変わる操作ステップごとに画像スロットを置かなければならない**（SHALL）。ステップの粒度は題材に応じて判断してよい（MAY）が、画面が変わるのに画像スロットの無い操作ステップを連続させてはならない（SHALL NOT）。

社内システムの操作手順では、スキルが必要な画像の枚数を確定してはならない（SHALL NOT）。`> **社内画像**:` の空欄に、差し込みの方針（「画面が変わるごとに1枚を目安」等）と対象の手順範囲を書かなければならない（SHALL）。実際の差し込みは人が行う。

#### Scenario: 公開ツールのインストール手順

- **WHEN** VSCode のインストールのような、スキルが画面遷移を知っている手順を7ステップで書く
- **THEN** 画面が変わる各ステップに画像スロット（プロンプトコメントまたは実在アプリ画面の指定）が置かれる

#### Scenario: 社内システムの申請手順

- **WHEN** 社内 Portal での申請のような、スキルが画面を知らない手順を書く
- **THEN** スキルは画像スロットの枚数を決めず、`> **社内画像**:` 空欄に「画面が変わるごとに1枚を目安に差し込む」等の方針と対象範囲が書かれる

#### Scenario: 画面が変わらないステップ

- **WHEN** 同一画面内の入力だけが続くステップ群を書く
- **THEN** ステップごとの画像スロットは要求されない

### Requirement: レッスンメタは `.meta.json` に書く

スキルはレッスンの `contents.md` を markdown 本文のみで出力しなければならない（SHALL）——frontmatter を書いてはならない（SHALL NOT）。レッスンメタはレッスンフォルダの `.meta.json` に書かなければならない（SHALL）: `slug`（計画書第6章のレッスン slug を転記。読み取れない場合はフェーズ1の確認ゲートでユーザーに確認する）・`status`（**`in_progress`**——本文を書いた時点で未着手ではない）・`description`・`tags`・`estimated_minutes`・`author`（**フェーズ1でユーザーに確認した値**。空のまま出力してはならない（SHALL NOT））。

レッスン `.meta.json` に `id` を書いてはならない（SHALL NOT）——ID はシリーズ・コースと同様、loader が自動採番して書き戻す（`stable-entity-ids` を参照）。

#### Scenario: レッスン本文に frontmatter が無い

- **WHEN** スキルがレッスンの `contents.md` を出力する
- **THEN** ファイルは Markdown 本文のみで、`---` で始まる frontmatter を含まない

#### Scenario: レッスンの `.meta.json` を書く

- **WHEN** 計画書にレッスン slug `what-is-version-control` が定義されたレッスンを生成する
- **THEN** レッスンフォルダの `.meta.json` に `slug: "what-is-version-control"`・`status: "in_progress"`・`description`・`tags`・`estimated_minutes`・`author` が書かれる
- **AND** `id` は書かれていない

#### Scenario: author が埋まっている

- **WHEN** フェーズ1でユーザーが執筆者名を答えている
- **AND** その run で3レッスンを出力する
- **THEN** 3本ともレッスン `.meta.json` の `author` に同じ値が書かれている

#### Scenario: 計画書に slug が無い場合は確認ゲートで補完する

- **WHEN** 選んだ計画書にレッスン slug の定義が無い
- **THEN** フェーズ1の名前確認ゲートで slug の案が提示され、ユーザーの確認を経て確定する
- **AND** 確定した slug がレッスン `.meta.json` に書かれる

### Requirement: コース・シリーズの `.meta.json` を書く

コースの `.meta.json` には `order` と `target` に加えて、`slug`（計画書のコース slug）・`description`（コースの概要文）・`catch`（キャッチコピー）・`style`（受講形態）を書かなければならない（SHALL）。シリーズを新規に作成する run では、シリーズ `.meta.json` にも `slug` / `description` / `catch` を書かなければならない（SHALL）。`description` と `catch` は計画書のコース仕様（学習目標・受講対象）から生成し、設計メモの承認ゲートで確認できるようにしなければならない（SHALL）。

`style` の値は**計画書を正とし**、計画書のコース仕様（第5章の表・第3章のツリー）から読み取らなければならない（SHALL）。読み取れないコースがある場合の扱いは「計画書に受講形態が無いコースは実行時に確定する」に従う（SHALL）。`style` を書かずにコースを作ってはならない（SHALL NOT）——受講形態は曼陀羅のノードに出る受講者向けの情報であり、抜けは公開後に気づく。

`.meta.json` に `id` を書いてはならない（SHALL NOT）——シリーズ・コースの ID は loader が自動採番して書き戻す。`cross_series_prev` および `cross_series_next` を書いてはならない（SHALL NOT）——曼陀羅の辺は計画側の責任。

#### Scenario: コースの .meta.json を書く

- **WHEN** コース単位で生成する
- **THEN** そのコースの `.meta.json` に `order`（レッスン名の配列）と `target`（計画書の受講対象）と `slug` / `description` / `catch` / `style` が書かれる
- **AND** `id` と `cross_series_prev` と `cross_series_next` は書かれていない

#### Scenario: 計画書の受講形態がそのまま書かれる

- **WHEN** 計画書のコース仕様に `self-study` と書かれたコースを生成する
- **THEN** そのコースの `.meta.json` の `style` は `self-study` になる

#### Scenario: 順序が計画書どおりになる

- **WHEN** 計画書のレッスン順が名前の昇順と一致しない
- **THEN** `.meta.json` の `order` によって計画書どおりの順序が保たれる

### Requirement: 初出の専門用語は説明するか前のコースへ参照する

レッスンの型（`lesson-template.md`）は、本文中の専門用語の扱いを定めなければならない（SHALL）: 受講対象（コースの `target`）が知らない前提の語は、そのレッスンでの初出で短く説明する。受講順で**前のコース**（同じシリーズの前のコース、または `cross_series_prev` の相手コース）に説明がある語は、説明を繰り返さず参照の一言（「〜で見た」等）で足りる（SHALL）。同じコース内の前のレッスンでの説明は、既存の「前後のレッスンへの参照」の作法に従う。この作法は `design-principles.md` に書いてはならない（SHALL NOT）——講義に根拠の無い原則を創作しない要件に反する。

#### Scenario: 前のコースで説明済みの語

- **WHEN** Git基礎シリーズのレッスンで「曼陀羅」を使う（説明は はじめにシリーズ にある）
- **THEN** 説明を繰り返さず、参照の一言で使ってよい

#### Scenario: どこにも説明が無い語

- **WHEN** 受講順で前のどのコースにも説明の無い専門用語を初めて使う
- **THEN** そのレッスンの初出で短く説明する
