# training-plan-skill Specification

## Purpose

目的から逆算してトレーニング構成をゼロから設計し、シリーズ / コース / レッスンの構成と仕様を計画書として出力する `dx-training-plan` Agent スキルの要件を規定する。対話フェーズの順序、トレーニング構成と曼陀羅構成の優先順位、計画書の章立て、`references/` の役割分担を定める。あわせて、要求と供給の突き合わせ・変更に伴う再チェック・計画書の自己レビューという検証の責任も定める。
## Requirements
### Requirement: 計画スキルの存在とパッケージ構成
`dx-training-plan` スキルが `dx-training-studio/.claude/skills/dx-training-plan/SKILL.md` に存在しなければならない（SHALL）。スキルは `SKILL.md` と `references/` からなる標準構成を取らなければならず（SHALL）、`references/` には設計原則・曼陀羅ガイド・計画書テンプレート・検証手順を配置しなければならない（SHALL）。`SKILL.md` は各 `references/` への参照に留め、参照先の内容を重複して記述してはならない（SHALL NOT）。

#### Scenario: スキルが読み込める
- **WHEN** スキルローダーが `dx-training-studio/.claude/skills/` を走査する
- **THEN** `dx-training-plan` が `name` と `description` を伴って一覧に含まれる

#### Scenario: references が独立したファイルとして存在する
- **WHEN** `dx-training-plan/references/` を確認する
- **THEN** `design-principles.md` / `mandala-guide.md` / `plan-template.md` / `verification.md` が存在する

#### Scenario: SKILL.md が references の内容を重複させない
- **WHEN** `SKILL.md` に検証手順・曼陀羅の規則・計画書の章立てが必要になる
- **THEN** 該当する `references/` のファイルを参照させ、内容そのものは `SKILL.md` に書かない

### Requirement: 対話フェーズの順序
スキルは対話をフェーズ0からフェーズ5までに分けて進行しなければならない（SHALL）。フェーズ0で既存計画書からの引き継ぎを確認し、フェーズ1で上流の前提を1問ずつ確認し、フェーズ2でトレーニング構成を決め、フェーズ3で曼陀羅構成に写し、フェーズ4で計画書を出力し、フェーズ5で自己レビューを行う。フェーズ1では複数の問いをまとめて提示してはならない（SHALL NOT）。各問いには推奨案とその理由を添えなければならない（SHALL）。

#### Scenario: 上流は1問ずつ確認する
- **WHEN** スキルがフェーズ1を開始する
- **THEN** 目的・受講者像・ゴール・環境と制約・総量・題材の分割・集合形式の有無・運営体制を、1問ずつ推奨案つきで確認する

#### Scenario: 環境と制約を確認する
- **WHEN** スキルがフェーズ1で環境と制約を問う
- **THEN** 社内固有のシステムやルール、環境のセットアップ方法、申請手順とリードタイム、セキュリティ上の制約、コスト上の制約を観点として提示し、事実を挙げてもらう

#### Scenario: 運営体制を確認する
- **WHEN** スキルがフェーズ1で運営体制を問う
- **THEN** 受講者を支える体制、質問の受け口、改善提案の集め方を確認する

#### Scenario: 下流は案を提示して判定を仰ぐ
- **WHEN** フェーズ1の上流が確定してフェーズ2に入る
- **THEN** コース分割・レッスン割り・時間配分を案として提示し、1問ずつの確認には戻らない

#### Scenario: ユーザーが打ち切りを宣言する
- **WHEN** ユーザーがフェーズ1の途中で「もう十分」と伝える
- **THEN** 残りの問いを打ち切ってフェーズ2へ進む

### Requirement: トレーニング構成が曼陀羅構成に優先する
スキルはフェーズ2でトレーニング構成を決める間、曼陀羅の制約を参照してはならない（SHALL NOT）。構成が曼陀羅で表現できない場合、まず曼陀羅側の表現を妥協しなければならない（SHALL）。トレーニング構成を変更する場合は、教育上の理由を示したうえでユーザーの承認を得なければならない（SHALL）。曼陀羅の制約のみを理由に構成を変更してはならない（SHALL NOT）。

#### Scenario: 構成設計中は曼陀羅を見ない
- **WHEN** スキルがフェーズ2でシリーズ・コース・レッスンの構成を設計する
- **THEN** 目的とゴールからの逆算のみで構成を決め、曼陀羅の分岐・合流の制約を判断材料にしない

#### Scenario: 曼陀羅で表現できない構成に遭遇する
- **WHEN** フェーズ3で、決めた構成が曼陀羅の制約では表現できないと判明する
- **THEN** 曼陀羅の表現を妥協する案を先に提示し、構成変更を既定の解決策にしない

#### Scenario: 構成変更が避けられない
- **WHEN** 曼陀羅側の妥協では解決できず、構成の変更が必要になる
- **THEN** 教育上の理由を明示したうえで、ユーザーに変更の可否を確認する

### Requirement: 曼陀羅ガイドの参照タイミング
スキルはフェーズ3に入る前に `references/mandala-guide.md` を読まなければならない（SHALL）。読む前に曼陀羅の分岐・合流を提案してはならない（SHALL NOT）。

#### Scenario: ガイドを読んでから辺を設計する
- **WHEN** スキルがフェーズ2を終えてフェーズ3に入る
- **THEN** `references/mandala-guide.md` を読み、その内容に基づいて分岐・合流を設計する

#### Scenario: ガイド未読で辺を提案しない
- **WHEN** フェーズ1またはフェーズ2の途中である
- **THEN** 曼陀羅の分岐・合流の具体案を提示しない

### Requirement: 既存構成の把握
スキルは既存のトレーニング構成を `contents/` 配下のファイルを読んで把握しなければならない（SHALL）。既存の計画書（`contents-work/plans/` 配下）が存在する場合はそれも読まなければならない（SHALL）。Studio 固有の変数注入機構に依存してはならない（SHALL NOT）。新しい計画が既存構成とどう並ぶか、またはどこを置き換えるかを検討しなければならない（SHALL）。

既存計画書を土台にする場合、スキルはフェーズ0として、フェーズ1の各項目が既存計画書で埋まっているかを判定しなければならない（SHALL）。**埋まっている項目を黙って引き継いではならない（SHALL NOT）。** 引き継ぐ内容を要約して提示し、確認を取らなければならない（SHALL）。空の項目はフェーズ1の作法で個別に問わなければならない（SHALL）。

#### Scenario: 既存構成を読み取る
- **WHEN** スキルが起動し、`contents/` が存在する
- **THEN** 配下のディレクトリと `.meta.json` を読んで既存のシリーズ・コース・レッスン構成を把握する

#### Scenario: 既存計画書を読み取る
- **WHEN** スキルが起動し、`contents-work/plans/` に既存の計画書が存在する
- **THEN** その計画書を読み、フェーズ1の各項目に対応する記述の有無を判定する

#### Scenario: 引き継ぐ前提の確認を取る
- **WHEN** 既存計画書にフェーズ1の項目が記載されている
- **THEN** 目的・受講者像・ゴール・分量方針などの引き継ぎ内容を要約して提示し、変更したい項目がないかを1ターンで確認する

#### Scenario: 欠けている項目を個別に問う
- **WHEN** 既存計画書にフェーズ1の項目のうち記載のないものがある
- **THEN** その項目のみをフェーズ1の作法（1問ずつ・推奨案つき）で確認する

#### Scenario: 既存構成が存在しない
- **WHEN** `contents/` が存在しない、または読み取れない
- **THEN** ユーザーに既存構成の有無を確認し、対話を継続する

### Requirement: 既存コンテンツを変更しない
スキルは既存のコンテンツ・ファイル・UI を変更してはならない（SHALL NOT）。変更が必要と判断した場合は、実行せず提案に留めなければならない（SHALL）。

#### Scenario: 既存コンテンツの整理が必要と判断する
- **WHEN** 新しい計画に伴い既存のシリーズやコースの整理が必要とスキルが判断する
- **THEN** 変更を実行せず、提案として提示する

### Requirement: 計画書の出力
スキルは合意された構成を計画書として markdown で出力しなければならない（SHALL）。計画書は `contents-work/plans/<yyyymmdd>-<slug>.md` に出力しなければならない（SHALL）。計画書は `references/plan-template.md` が定める章立てに従わなければならない（SHALL）。時間予算の集計と、決定の根拠および却下した案を省略してはならない（SHALL NOT）。構成はアスキーアートで示さなければならない（SHALL）。

レッスン仕様には、画像素材が AI 生成・フリー素材で用意できるものか、人手による撮影または録画が必要なものかの区別を記さなければならない（SHALL）。人手が必要なレッスンの本数を制作体制の章で積算しなければならない（SHALL）。個々の画像の指示内容を計画書に記述してはならない（SHALL NOT）。

#### Scenario: 計画書を出力する
- **WHEN** ユーザーがフェーズ3の内容を承認する
- **THEN** `references/plan-template.md` の章立てに従った計画書を markdown で出力する
- **AND** 出力先は `contents-work/plans/<yyyymmdd>-<slug>.md` である

#### Scenario: 構成を図で示す
- **WHEN** 計画書に全体構造と曼陀羅構成を記載する
- **THEN** シリーズ → コース → レッスンのツリーと依存グラフをアスキーアートで示す

#### Scenario: 時間予算を集計する
- **WHEN** 計画書を出力する
- **THEN** シリーズ別の時間集計と総計を含め、目標時間に収まっているかを明記する

#### Scenario: 却下した案を残す
- **WHEN** 対話の中で複数案から1つを選ぶ判断があった
- **THEN** 採用案・却下案・却下理由を計画書に記載する

#### Scenario: 人手が必要な画像素材を区別する
- **WHEN** レッスンが社内ツールの画面や動作を扱う
- **THEN** 撮影または録画が必要である旨をレッスン仕様に記し、制作体制の章で該当本数を積算する

#### Scenario: 画像の指示内容は書かない
- **WHEN** 計画書のレッスン仕様に画像素材の区別を記す
- **THEN** 素材の種別のみを記し、構図やプロンプトなどの指示内容は記述しない

### Requirement: 既定方針
スキルは既定方針を持ち、ユーザーが明示的に変更を求めた場合のみ変更しなければならない（SHALL）。既定方針を毎回の問いとして提示してはならない（SHALL NOT）。

#### Scenario: 既定方針を問い直さない
- **WHEN** スキルがフェーズ1の上流を確認する
- **THEN** 1レッスンの長さ・演習の有無・学習形態の保持粒度といった既定方針は問わず、受講者像やゴールなど今回固有の事項のみ問う

#### Scenario: ユーザーが既定方針の変更を求める
- **WHEN** ユーザーが既定方針と異なる方針を明示する
- **THEN** その方針を採用し、計画書に反映する

### Requirement: 責任範囲の限定
スキルは id の採番、曼陀羅の厳密な検証、レッスン本文・演習・画像の作り込みを行ってはならない（SHALL NOT）。曼陀羅については案の提示と最低限のチェックに留めなければならない（SHALL）。

一方で、**内容から導かれる依存に基づいて学習順路を提案することは責任範囲に含まれる**（SHALL）。どのコース・レッスンをどの順で進めるべきかの判断は、曼陀羅の文法検証とは別に行わなければならない（SHALL）。

行き止まり（出口の辺を持たず、ゴールでもないコース）については、**存在の有無ではなく意図的かどうか**を確認しなければならない（SHALL）。行き止まりの存在自体を欠陥として扱ってはならない（SHALL NOT）。意図的な行き止まりは、任意コースである旨を計画書に明記しなければならない（SHALL）。

#### Scenario: 最低限のチェックのみ行う
- **WHEN** フェーズ3で曼陀羅構成を提示する
- **THEN** 循環の有無・ゴールへの到達可能性・行き止まりが意図的かどうかを確認し、結果を計画書に記載する

#### Scenario: 意図的な行き止まりを任意コースとして扱う
- **WHEN** シリーズ末尾のコースが出口の辺を持たず、それが上級者向けなど任意の位置づけである
- **THEN** 欠陥として指摘せず、任意コースである旨と、そう設計した理由を計画書に記載する

#### Scenario: 意図しない行き止まりを指摘する
- **WHEN** 必須として設計したコースが出口の辺を持たない
- **THEN** そのコースを飛ばして修了できてしまうことを示し、辺を足すか位置を変えるかをユーザーに問う

#### Scenario: 内容から順路を提案する
- **WHEN** あるコースの内容が、別のコースで供給される環境やスキルを要求している
- **THEN** 要求を満たすコースを前に置く順路を提案し、その根拠を計画書に記載する

#### Scenario: レッスンの中身に踏み込まない
- **WHEN** 計画書のレッスン仕様を記述する
- **THEN** 学習目標と演習の要旨および目安時間までを書き、本文や解答の中身は書かない

### Requirement: 要求と供給の突き合わせ
スキルはフェーズ2で、各レッスンおよび各コースが**供給するもの**（習得済みになるスキル、利用可能になるツールや状態）と**要求するもの**（実行に必要な前提）を突き合わせなければならない（SHALL）。受講者像を初期供給として突き合わせに含めなければならない（SHALL）。突き合わせの結果、供給元が存在しない要求、供給より前に位置する要求、既に供給済みのものを再度供給する冗長を検出した場合、ユーザーに提示しなければならない（SHALL）。

この突き合わせは学習上の依存に基づくものであり、曼陀羅の表現上の制約とは区別しなければならない（SHALL）。フェーズ2で曼陀羅の制約を参照してはならないという規定は、この突き合わせを妨げない。

#### Scenario: 供給元のない要求を検出する
- **WHEN** あるレッスンが前提とするスキルやツールが、他のどのレッスンでも供給されず、受講者像にも含まれていない
- **THEN** そのレッスンと不足している前提を示し、供給するレッスンを追加するか受講者像を見直すかをユーザーに問う

#### Scenario: 供給より前にある要求を検出する
- **WHEN** あるレッスンが要求する前提を供給するレッスンが、そのレッスンより後ろに位置している
- **THEN** 順序が逆転している箇所を示し、入れ替えを提案する

#### Scenario: 受講者像との冗長を検出する
- **WHEN** 受講者像が既に習得済みとしている内容を、レッスンが改めて教えている
- **THEN** 矛盾する箇所を示し、受講者像とレッスンのどちらを修正するかをユーザーに問う

#### Scenario: フェーズ3で同じ突き合わせを再利用する
- **WHEN** スキルがフェーズ3でシリーズ間の辺の起点を決める
- **THEN** フェーズ2で作った要求と供給の対応を再利用し、要求を満たすコースから辺を張る

### Requirement: 変更に伴う再チェック
スキルは対話の途中で決定が変わった場合、その変更が波及する範囲を再チェックしなければならない（SHALL）。再チェックの対象は `references/verification.md` が定める変更波及の対応に従わなければならない（SHALL）。構成が変わったにもかかわらず時間予算や曼陀羅を据え置いてはならない（SHALL NOT）。

#### Scenario: レッスンの増減が起きる
- **WHEN** レッスンを追加または削除する決定がなされる
- **THEN** 時間予算を再集計し、目標時間と調整枠に対する影響をユーザーに示す

#### Scenario: コースの追加・分割が起きる
- **WHEN** コースを追加、分割、または統合する決定がなされる
- **THEN** 曼陀羅の辺、学習形態の一貫性、時間予算を再チェックする

#### Scenario: 完成物や技術スタックが変わる
- **WHEN** ハンズオンの題材、完成物、または使用する技術が変わる
- **THEN** 要求と供給の突き合わせをやり直し、必要なスキルの供給元が揃っているかを再確認する

### Requirement: 計画書の自己レビュー
スキルは計画書を出力した後、フェーズ5として自己レビューを一度実行しなければならない（SHALL）。レビュー結果はユーザーに報告しなければならない（SHALL）。**スキルはレビュー結果に基づいて計画書を自動的に修正してはならない（SHALL NOT）。** 修正するかどうかはユーザーが判断する。

設計原則については、原則に従っているかではなく、**原則から逸脱している箇所に理由が書かれているか**を確認しなければならない（SHALL）。理由が明記された意図的な逸脱を指摘してはならない（SHALL NOT）。

#### Scenario: レビューを実行して報告する
- **WHEN** フェーズ4で計画書を出力し終える
- **THEN** `references/verification.md` のレビュー観点を計画書に当て、指摘事項と確認できた項目を一覧で報告する

#### Scenario: 指摘があっても修正しない
- **WHEN** 自己レビューで指摘事項が見つかる
- **THEN** 指摘内容を報告するに留め、計画書を書き換えずにユーザーの判断を待つ

#### Scenario: 理由のある逸脱は指摘しない
- **WHEN** 設計原則から外れた判断が計画書に含まれ、その理由が決定の根拠の章に記載されている
- **THEN** それを指摘事項として挙げない

#### Scenario: 理由のない逸脱を指摘する
- **WHEN** 設計原則から外れた判断が計画書に含まれ、理由がどこにも記載されていない
- **THEN** 逸脱している箇所と、対応する設計原則を示して報告する

### Requirement: エンティティの命名規則

計画書が定めるシリーズ名・コース名・レッスン名は、次の規則に従わなければならない（SHALL）。

- シリーズ名は「シリーズ」で終わらなければならない（SHALL）
- コース名は「コース」で終わらなければならない（SHALL）
- レッスン名は「レッスン」で終わってはならない（SHALL NOT）
- 題材が特定のツール・技術であるとき、シリーズ名にその題材名を含めなければならない（SHALL）
- 同じ場合、コース名には題材名を含めることが望ましい（SHOULD）。題材名が文脈から自明なコースでは省いてよい（MAY）
- シリーズ名・コース名・レッスン名は、受講者が一覧で見て内容を想起でき、選ぶ動機になる名前でなければならない（SHALL）。レッスン名には接尾辞その他の形式上の制約を課してはならない（SHALL NOT）
- **フォルダ名として安全でない文字を使ってはならない**（SHALL NOT）——`content-structure-sync` の「名前にファイル名として使えない文字を使わない」に従う。名前はそのままフォルダ名になり、置換されれば受講者に見える名前が変わるため。区切りには全角スラッシュ `／` または中黒 `・` を使う（SHALL）

命名規則の本文は `references/plan-template.md` に置かなければならない（SHALL）。`SKILL.md` に規則の内容を書き写してはならない（SHALL NOT）。

#### Scenario: Git を題材にした構成の命名

- **WHEN** スキルが Git を題材にしたシリーズとコースの名前を決める
- **THEN** シリーズ名は「シリーズ」で終わり、かつ「Git」を含む（例: `Git完全マスターシリーズ`）
- **AND** コース名は「コース」で終わる（例: `Git概念マスターコース`）
- **AND** レッスン名は「レッスン」で終わらない

#### Scenario: 題材名が自明なコース

- **WHEN** シリーズ名で題材が示されており、コースの主題が題材名を含めなくても通じる
- **THEN** コース名から題材名を省いてよい（例: `チーム開発コース`）
- **AND** コース名は「コース」で終わる

#### Scenario: 素っ気ない名前を採用しない

- **WHEN** スキルがコース名の候補として `概念` のような一語の名前を検討する
- **THEN** その名前は採用されず、内容を想起できる名前（例: `Git概念マスターコース`）に置き換えられる

#### Scenario: 区切りに禁止文字を使わない

- **WHEN** スキルが「リポジトリを作る」と「clone」を1つのレッスン名で並べようとする
- **THEN** 名前は `リポジトリを作る／clone` になり、半角スラッシュを含む `リポジトリを作る / clone` は採用されない

#### Scenario: 規則の記述場所

- **WHEN** 開発者が命名規則の内容を確認する
- **THEN** 規則の本文は `references/plan-template.md` にあり、`SKILL.md` にはその参照のみがある
- **AND** 禁止文字の規則も `references/plan-template.md` にある

### Requirement: 命名の責任は計画側にある

シリーズ名・コース名・レッスン名を決める責任は本スキルが負わなければならない（SHALL）。レッスン草稿作成スキルが計画書の名前を変換・修飾して出力先の名前を作ることを前提としてはならない（SHALL NOT）。

#### Scenario: 草稿作成スキルは名前を作り変えない

- **WHEN** レッスン草稿作成スキルが計画書をもとに `contents/` へ出力する
- **THEN** 出力先のシリーズ名・コース名・レッスン名は計画書の記載と一致する

### Requirement: キックオフの受講者ニーズを1問で確認する

フェーズ1で集合形式（キックオフ）が有ると確定した場合、スキルは受講者がキックオフに求めるもの——トレーニングの目的・ゴール・修了時に得られるものへの期待、および進め方への不安・疑問——を確認しなければならない（SHALL）。この確認は典型候補を提示してユーザーが選択・追記する形式の1問で行わなければならず（SHALL）、複数の問いに分割してはならない（SHALL NOT）。確認結果はキックオフ型レッスンの仕様（計画書のレッスン仕様）に反映しなければならない（SHALL）。集合形式が無い場合、この問いを出してはならない（SHALL NOT）。

#### Scenario: 集合形式ありのトレーニング

- **WHEN** フェーズ1で「キックオフを集合で行う」と確定する
- **THEN** 受講者がキックオフに求めるものを、典型候補つきの1問で確認する
- **AND** 回答がキックオフ型レッスンの仕様セルに反映される

#### Scenario: 集合形式なしのトレーニング

- **WHEN** フェーズ1で集合形式を行わないと確定する
- **THEN** 受講者ニーズの問いは出されず、フェーズ1の質問数は増えない

### Requirement: 計画書テンプレートのコース受講形態は style と表記する

`references/plan-template.md` がコースの受講形態（self-study / lecture / hands-on）を示す箇所は、コース `.meta.json` の実フィールド名に合わせて `style` と表記しなければならない（SHALL）。旧表記 `format` を用いてはならない（SHALL NOT）——計画書が実装と違うフィールド名を書くと、草稿作成時に読み替えが要る。

#### Scenario: テンプレートの表記が実装と一致する

- **WHEN** `references/plan-template.md` の章立て・凡例・コース仕様の列名を読む
- **THEN** 受講形態は `style` と表記され、`format` は現れない

### Requirement: 計画書の検証は全コースの受講形態の記載を確認する

`references/verification.md` のレビュー観点は、**計画書のすべてのコースに `style`（受講形態）が書かれていること**の確認を含まなければならない（SHALL）。抜けているコースがある場合は、コース名を挙げて指摘しなければならない（SHALL）。

`style` が抜けたまま計画書が確定すると、`dx-training-create` は実行時にユーザーへ問い返すことになる。計画側で埋めておけば、その問いは起きない。

指摘に留め、スキルが `style` を自動的に補ってはならない（SHALL NOT）——計画書の自己レビューは修正を行わない既存の要件に従う。

#### Scenario: 受講形態の抜けを指摘する

- **WHEN** 計画書のコース仕様表に、`style` の欄が空のコースが1つある
- **THEN** 自己レビューの報告に、そのコース名を添えた指摘が現れる

#### Scenario: すべて埋まっていれば指摘しない

- **WHEN** 計画書の全コースに `style` が書かれている
- **THEN** 受講形態に関する指摘は出ない

#### Scenario: 指摘しても書き換えない

- **WHEN** 受講形態の抜けが見つかる
- **THEN** 計画書は書き換えられず、指摘の報告に留まる
