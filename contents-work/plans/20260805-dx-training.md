## 1. 前提

### 1.1 目的

システム・ソフトのメンバにツール開発を促し、業務効率を上げる。

### 1.2 受講者像

エンジニアリング部署の新入社員・中途採用社員。

| 項目 | 前提 |
|---|---|
| プログラミング | 多少の知識はある（他言語での経験など）。ただし**Python の文法は変数・型から一通り扱う** |
| Python | 初心者 |
| Git / GitHub | 初心者 |
| AI | 社内チャットツールや ChatGPT で調べ物をしたことがある程度 |
| エディタ | VSCode を使ったことがない前提（部門正規の導入手順から扱う） |
| Markdown | 前提としない（読めれば足りる範囲でのみ扱う） |

### 1.3 ゴールの定義

**2時間（1h × 2回）で、必ず動くツールが1つ完成する体験**を全員に届ける。

加えて、ハンズオンでは以下の2点を成立させる。

- **AI を使ってよい。ただし発表で自分のコードを自分で説明できること。** AI に丸投げして理解せずに済ませる導線を、運用ルールで塞ぐ
- **応用課題の手法は教えない。** 各自が数日かけて工夫する。運営は解法を配らない

> **前版からの変更**: 「入力データだけ受講者自身の業務データを使い、自分事として取り組めるようにする」を削除した。理由は 11.2 を参照。

### 1.4 分量方針

| 項目 | 値 |
|---|---|
| 総レッスン数 | 28（集合 1 ＋ 自己学習 25 ＋ ハンズオン 2） |
| 1レッスン | 10〜15分 |
| 自己学習の総量 | 355分（5時間55分。上限6時間） |
| 自己学習期間 | 3週間 |
| 集合回 | **3回** — キックオフ（L01）＋ ハンズオン2日 |
| キックオフ | **30分**（説明10分 ＋ Q&A 20分。質問がなければ早めに切り上げる） |
| ハンズオン | 1h × 2回、間隔 3〜4日（自己学習時間には含めない）。**実施は10月中旬の見込み** |
| ハンズオン定員 | 8人（4組） |

- 必須／任意の2層分けはしない。自己学習26レッスンすべてが必須
- ハンズオンで直接使わない基礎・概念・セットアップも厚くカバーする
- **全レッスンに5分以内の「やってみる」演習を入れる**
- **手順の説明にはスクリーンショットや図を載せる。** 文章だけで済ませない
- **小演習には折りたたんだ解答例を1行つける。** 完成コード一式を渡すのはハンズオンのみ

解答例は `<details>` で折りたたみ、受講者が自分のタイミングで答え合わせできるようにする。

```markdown
### やってみる
（課題）

<details>
<summary>解答例</summary>

（1行の解答例）

</details>
```

### 1.5 設計原則: シリーズ内で完結させる

**あるシリーズのトピックは、たとえリードタイムがかかっても、そのシリーズ内で完結させる。**

社内では Git のインストール、社内 GitHub のアカウント、chocolatey のいずれも申請が必要で、承認まで日数がかかる。これらを「時間がかかるから」という理由で先頭のシリーズに集めない。

| 申請 | 置き場所 | リードタイム | 根拠 |
|---|---|---|---|
| **chocolatey** | **① はじめにシリーズ / L02** | 1日 | **VSCode も uv もここから入る。どのシリーズにも属さない配布基盤** |
| Git のインストール | ③ Git基礎シリーズ / L07 | 1日 | Git のトピック。**社内インストールシステムからのみ**（chocolatey 経由ではない） |
| 社内 GitHub のアカウント | ④ GitHub基礎シリーズ / L12 | **3日** | GitHub のトピック |

**chocolatey 経由で入るもの（申請不要・数分）**

| ツール | 置き場所 |
|---|---|
| VSCode（部門向けカスタマイズ版） | ① はじめにシリーズ / L03 |
| uv | ⑤ Python基礎シリーズ / L19 |

chocolatey だけが例外的に「はじめにシリーズ」に置かれるのは、**横断的な配布基盤**だからであって、リードタイムが長いからではない。実際、**最も長いのは社内 GitHub アカウントの3日**であり、それは GitHub基礎シリーズに置いている。

**キックオフで3件すべての申請を促せば、最長3日で全部そろう。** 自己学習期間3週間の頭で消化できる。

**リードタイムへの対処は、レッスン配置ではなく F2F キックアップの口頭案内で行う。**「いつ動くべきか」は口頭が向き、「どう操作するか」はレッスンが向く（→ 11.10）。

### 3.3 チェック結果

`references/mandala-guide.md` のチェック項目に対する判定。

| 規則 | 判定 |
|---|---|
| 循環がないか | ✓ `start → {ai, git, python} → github → build` の一方向のみ。逆流する辺がない |
| ゴールに到達できるか | ✓ 全6シリーズが辺をたどって `build/workshop` に至る。Git は GitHub 経由、他は直接 |
| 行き止まりが意図的か | ✓ **本計画に任意コースは置いていない**ため、行き止まりはゼロが正。ゴール以外の全コースが出口の辺を持つ（開発環境準備コースは Git概念と Python概要への辺を持つ） |
| 到達不能なコースがないか | ✓ 起点 `start/intro` 以外の全コースが入口の辺を持つ（シリーズ内の直列鎖を含む） |
| 辺の重複がないか | ✓ 7本すべて異なるシリーズペア。`start→ai` は DX入門から、`start→git` と `start→python` は環境準備から出るが、**ペアが異なるので重複ではない** |
| シリーズ内は直列鎖のみか | ✓ 全6シリーズがコース並び順の一本道。**はじめにシリーズも `DX入門 → 環境準備` の直列** |
| 1コースから同一ターゲットへ複数辺を出していないか | ✓ 環境準備が出す2本（Git・Python）は宛先シリーズが異なる。build/prep への3本も送り元シリーズが全て異なる |

**経由による暗黙の必須化**: Git基礎シリーズは build への直接の辺を持たないが、`Git基本操作 → GitHub入門` を経由するため**全Gitコースが build の前提として必須**になる。辺1本制約の下で辺を増やさずに必須化できている。

**開発環境準備コースは Git と Python の両方の前提**なので、飛ばして修了することはできない。AI だけが環境準備を必要としないが、build に入るには合流する3本すべての元コースが完了している必要があるため、AI だけ進めても先へは行けない。

**AI完全マスターシリーズの位置づけ変更**: 前版では AI基礎 → build の辺は「おまけを飛ばさせないための辺」だった。本版ではハンズオンで AI 使用可と決めたため、**この辺は実質的な前提**になった。辺そのものは変更していないが、意味づけが強くなっている。

### 3.4 進行ルール

- あるコースに入るには、そこへ合流する**全ての辺の元コースが完了済み**である必要がある
- その範囲内であれば、受講者はどのブランチから進めても構わない（順序は受講者に任せる）
- 全ブランチの完了を求めるが、**ハンズオン参加の強制ゲートにはしない**。未完了でも希望者は参加でき、その時点でできる限りのことをしてもらう

### 3.5 chocolatey の承認待ちに何ができるか

chocolatey は社内インストールシステムでの申請が必要で、**承認に1日かかる**。VSCode も uv もそこから入るため、開発環境準備コースが Git と Python の両方のゲートになる。

```
キックオフ（L01・F2F）当日に3件すべて申請
   chocolatey / Git / 社内GitHubアカウント
                    │
                    │  〜 chocolatey 承認待ち（1日）〜
   ② AI完全マスターシリーズ 15分 │  ← この間に進められるのはここだけ
                    ▼
   ① 開発環境準備コース（chocolatey → VSCode）
                    ├────→ ③ Git基礎シリーズ → ④ GitHub基礎シリーズ
                    └────→ ⑤ Python基礎シリーズ
```

**待ち時間に進めるのは AI の15分だけ**になる。VSCode を chocolatey 経由の部門正規手順に切り替えた代償で、Python も環境準備の後ろへ回ったため（→ 11.19）。

ただし**待ちは1日**であり、3週間の学習期間の初日に収まる。同日に Git（1日）と社内GitHubアカウント（3日）の申請も並行して進むため、期間全体としてのロスは小さい。

**申請が3件に減ったことは正味の改善。** 前案では VSCode と chocolatey を別々に申請していた（2件）。正規手順では chocolatey 1件から VSCode と uv の両方が入る。

## 4. シリーズ仕様

### ① はじめにシリーズ `start`

| 項目 | 内容 |
|---|---|
| ゴール | 曼陀羅の見方と進め方を理解し、自分が取り組む順番を決められる／chocolatey と VSCode が使える状態になる |
| 対象 | 受講者全員（最初に必ず通る） |
| コース数 / レッスン数 / 時間 | 2 / 3 / 35分 |
| 前提 | なし |
| 分岐 | **DX入門コースから AI へ。開発環境準備コースから Git・Python へ**（→ 3.2、3.5） |

**コースを2つに分けた理由**: L01 はトレーナーが F2F で説明する `lecture`、L02・L03（chocolatey・VSCode）は自己学習。**学習形態はコース単位で一貫させる**という既定方針に従い、形態が違うものを同じコースに同居させない。

**VSCode は部門の正規手順（chocolatey 経由）で入れる**（→ 11.19）。そのため chocolatey が先に来る。chocolatey は VSCode だけでなく **uv の供給元でもある**ため、Python シリーズもこのコースを前提とする。

**L01 はトレーナーが F2F で説明する（30分。説明10分 ＋ Q&A 20分。質問がなければ早めに切り上げる）。** その場で伝えるのは3点。

**(1) トレーニングの進め方と曼陀羅の見方** — レッスン本文の内容。

**(2) 各種申請を早めに済ませること** — **chocolatey・Git・社内GitHubアカウントの3件**を当日中に出させる。同時に出せば承認は並行して進み、最長3日でそろう（→ 1.5）。

**(3) トレーナー側のサポート体制** — 専用 Teams チャンネルを用意し、質問できる場があることを伝える（→ 9章「サポート体制」）。

**(2) の案内はレッスン本文には書かない。** Git の話は Git基礎シリーズ、Python の話は Python基礎シリーズで扱う。L01 に各シリーズの事前準備を並べると、**進め方のレッスンが環境構築の目次になってしまう**（→ 1.5、11.10）。

**chocolatey と VSCode だけが例外的にここに置かれる。** Git にも Python にも効く横断的な配布基盤とエディタで、どのシリーズにも属さないため。

### ② AI完全マスターシリーズ `ai`

| 項目 | 内容 |
|---|---|
| ゴール | 社内AIチャットツールの基本操作ができ、詰まったときに聞ける |
| 位置づけ | **ハンズオンの前提**（前版では「おまけ」） |
| レッスン数 / 時間 | 1 / 15分 |
| 前提 | DX入門コース（**開発環境準備コースは不要**） |
| 今後 | コンテンツを育てていく想定。シリーズを独立させたのはそのため |

**環境準備を前提にしない。** 社内AIチャットはブラウザで完結する。**VSCode + GitHub Copilot はゆくゆく扱いたいが、現時点では踏み込まない。** 将来このシリーズを育てるときに、`start→ai` の辺を DX入門から開発環境準備コースへ張り替える（→ 10章「将来の拡張」）。

**3方向のうち AI だけが環境準備を飛ばせる**ので、chocolatey の承認待ちに進められる唯一のシリーズになっている（→ 3.5）。

**設計意図の更新**: ハンズオンの応用課題は手法を教えず、数日間の自主考察に委ねる。その間の主要な調べ手段が AI になるため、**AI に聞けることが応用課題の前提条件**になった。レッスン数は1本のままだが、役割は前版より重い。

### ③ Git基礎シリーズ `git`

| 項目 | 内容 |
|---|---|
| ゴール | ローカルで変更を記録・確認・取り消しでき、生成物をコミットから除外できる |
| レッスン数 / 時間 | 6 / 85分 |
| 前提 | **開発環境準備コース（VSCode が必要）** |
| 範囲外 | ブランチ（GitHub基礎シリーズで扱う）／SourceTree の使い方 |

**設計意図**: ほとんどの操作は結局 GitHub とセットで行うため、Git基礎シリーズは**ローカル操作の基礎に絞って軽くする**。

**教え方**: **CLI を主とし、同じ操作を VSCode でどうやるかを併記する。** 実務では VSCode から Git を操作することが多いが、コマンドを先に見せないと三大エリア（L06）の概念と操作が対応しない（→ 11.12）。

**Git は社内インストールシステムからのみ入る。** chocolatey 経由では入らないため、開発環境準備コースとは別に申請が要る（1日）。

**インストール時に SourceTree を同梱するか選べる。** 便利なので同梱を推奨するが、**トレーニングでは選択肢があるとコメントするに留め、使い方は扱わない**。Git 操作のメインは VSCode に統一する（→ 11.12）。教える GUI を2つに増やすと、詰まったときの切り分けが難しくなる。

**本版での追加**: ハンズオンの成果物は Python スクリプトであり、**スクリプトが生成する JSON はコミットしない**方針にした。これを実行するには `.gitignore` が必要になるため、L08「最初のコミット」に含めた。

### ④ GitHub基礎シリーズ `github`

| 項目 | 内容 |
|---|---|
| ゴール | ブランチを切って PR を出し、レビューを経てマージできる |
| レッスン数 / 時間 | 7 / 95分 |
| 前提 | Git基本操作コース（commit できないと push できないため） |

**設計意図**: 「ブランチを切る → push → PR → マージ」が1コース内で地続きになるよう、ブランチをこのシリーズに置いた。

**入門コースは「準備」、GitHubリモート連携コースは「実操作」に分けた。** 入門で GitHub の役割を理解しアカウントを取り、リモート連携で「リポジトリを作る → clone → push → pull」を一続きに扱う。clone は push/pull と同じ「ローカルとリモートをつなぐ」操作なので、GitHubリモート連携コースに置くほうが筋が通る。

**本版での役割強化**: ハンズオンの進行そのものに PR → レビュー → 承認 → マージ を組み込んだため、L15〜L17 は**当日の必須スキル**になった。前版では成果物を「置く」だけだったが、本版では**ペア相互レビューの手段**として使う。

**社内 GitHub のアカウント申請は L12 に置く**（→ 1.5）。承認までのリードタイムが特に長いため、キックオフで早めの申請を口頭案内する。

### ⑤ Python基礎シリーズ `python`

| 項目 | 内容 |
|---|---|
| ゴール | ファイルを読んで加工し、結果を別形式で出力するスクリプトを書ける |
| レッスン数 / 時間 | 9 / 125分 |
| 前提 | **開発環境準備コース（chocolatey が必要）** |

**開発環境準備コースを前提にする。** **uv は chocolatey 経由でしか入らない**ため。エディタとしての VSCode は「あると便利」に留まり、レッスンの手順は特定のエディタに縛らないが、chocolatey は避けられない依存になる。

**環境構築は uv を使う。** Anaconda は2026年末まで社内で使用できるが、**主流が uv に移りつつある**ため、本トレーニングでは uv に統一する（→ 11.13）。chocolatey が済んでいれば **uv 本体の導入は5分**なので、L19 は10分に収めている。

**設計意図**: 中級コースの3本は、ハンズオンの完成物から逆算した構成にしている。

| レッスン | ハンズオンでの用途 |
|---|---|
| L24 関数とモジュール分割 | 読み込み・除外・組分け・出力を関数に切る |
| L25 ファイル読み書き（CSV / JSON） | 入力CSVを読み、結果を JSON で書き出す |
| L26 外部ライブラリを使う（pandas） | CSV の読み込みと集計を pandas でも書ける（任意） |

### ⑥ ツール開発実践シリーズ `build` ☆

| 項目 | 内容 |
|---|---|
| ゴール | 課題を解決する Python スクリプトを1つ完成させ、PR とレビューを経て自分のリポジトリにマージする |
| レッスン数 / 時間 | 3 / 10分（事前）＋ 60分×2（当日） |
| 前提 | AI基礎コース・GitHubブランチ・PRコース・Python中級コース の3本が合流 |
| 定員 | 8人（4組） |

**命名の意図**: 「卒業試験」等ではなく **「ツール開発実践」**。ゴールは「作れた実感」であって評価ではないため、試験という含意を避けた。

#### 6.1 ハンズオンの題材

**課の10人を週ごとに3組に分ける組分けスクリプト。**

| Part | 内容 | 実施 |
|---|---|---|
| Part 1 | 休暇予定CSVを読み、休暇者を除いて3組に分け、JSON で出力する | 1日目 |
| Part 2 | 4週分を生成し、前週と同じペアが出ないようにする | 2日目（間に3〜4日の自主考察） |

**Part 2 の想定解法**は「シャッフルして、条件を満たすまでやり直す」。最適化アルゴリズムではなく、**評価関数を書いて満たすまで試す**という考え方を身につけさせる。リトライ上限を入れないと無限ループになるため、「条件を厳しくすると解が存在しなくなる」ことを実地で知る場面になる。

ただし **解法は指定しない。** 手法はレッスンで扱わず、各自の工夫に委ねる。高等数学を使う解も、素朴なリトライ解も認める。解法が発散することが、全員発表の価値を作る。

**課題は1日目の開始まで伏せる。** リポジトリには骨組み（README とサンプルCSV）のみを置き、課題文は当日配布する。

#### 6.2 ハンズオンの進め方

**ペアは当日その場で決める。** 運営が用意した**ペア決めスクリプトを冒頭で実行してデモ**し、その結果でペアを確定する。講師が恣意的に決めるより納得感があり、**今日作るのと同じ種類のツールが、その場の実データ（参加者名簿）で動く**ところを見せられる。

**このスクリプトは受講者に配布する。ただし範囲を絞る。**

| 要素 | 配布物に含む | Part 1 |
|---|:---:|---|
| シャッフルして分割する | ○ | 発想を参考にできる |
| CSV を読む | — | 自力（L25） |
| 条件で除外する | — | 自力（L22） |
| JSON で出力する | — | 自力（L25） |
| リトライで条件を満たす | — | **Part 2。一切漏れない** |

CSV読込・除外・JSON出力は**ペア決めには本来不要**なので、無理なく排除できる。Part 2 の想定解法（評価関数を書いて満たすまで試す）は一回きりのペア決めに要らないため、本当の課題は守られる。

**2人一組。ただしペアは「相互レビューの相手」であり、共同で実装はしない。** 各自が自分の個人リポジトリを持ち、**相方を collaborator に招待してレビューできるようにする**。

```
Aさんのリポジトリ                    Bさんのリポジトリ
  feature ブランチ                     feature ブランチ
      │ PR                                 │ PR
      ▼                                    ▼
   B がレビュー・承認                   A がレビュー・承認
      │                                    │
      ▼ A がマージ                         ▼ B がマージ
    main                                 main
```

レビュー時、**相方は「なぜこう書いたか」を1つ質問し、答えられたら承認する。** これが「自分のコードを自分で説明できる」ことの検証になり、発表のリハーサルにもなる。

**承認は仕組みで強制しない。branch protection は使わない。** 設定の説明に当日の時間を取られるうえ、レビューを飛ばす動機が受講者側にない。運用ルールとして伝えるだけで足りる。

**招待は collaborator で行う。** 個人リポジトリの collaborator は write 権限になり、相方も自分のリポジトリに push できる状態になる。ただし相互レビューの相手として招く関係なので実害はなく、権限を read に絞るためだけに org 配下へ移す等の手間はかけない。

**招待は当日、Part 1 の実装時間の中で行う。** ペアが当日決まるため事前には送れない。操作は Settings → Collaborators から username で追加するだけで、当日その場で説明する。**招待の往復（送信 → 相手が承認）は28分の実装時間に吸収され**、PR レビュー（38分〜）には間に合う。

#### 6.3 ハンズオンの時間割

```
1日目 60分  ─────────────────────────────────────────────
00-10  課題公開・骨組み説明
       ペア決めスクリプトのデモ（実行してペア確定）→ スクリプトを配布
       collaborator 招待のやり方を説明
10-38  Part 1 実装（各自）  CSV読込 → 休暇者除外 → 3組に分ける → JSON出力
       ※ この時間内に相方を collaborator に招待し、承認まで済ませておく
38-50  PR 作成 → 相方がレビュー（「なぜこう書いたか」を1つ質問）→ 承認 → マージ
50-55  main で動作確認 ── ここで動くツールが完成
55-60  応用課題（Part 2）の説明

        〜 3〜4日 〜  仲間と相談OK / AIに聞くのもOK / 解法は配らない

2日目 60分  ─────────────────────────────────────────────
00-05  進捗確認
05-30  Part 2 実装（25分）
30-38  PR → レビュー → 承認 → マージ
38-54  発表  各自2分 × 8人（自分のコードを自分で説明する）
54-60  まとめ
```

**Part 1 まで到達すれば動くツールが完成する。** Part 2 は上積みなので、応用に届かなかった人も手ぶらでは帰らない。

**発表は未完成でも構わない。** できたところまでを話し、何に詰まったかを共有する。設計原則の「未完成での参加を許容することを明示する」（第11回）に沿う運用で、**詰まった箇所の共有そのものが他の参加者の学びになる**。

## 6. レッスン仕様

各レッスンは「学習目標 → 本文 → やってみる（5分以内） → まとめ → 確認問題」で構成する。
以下は**大まかな構成まで**（詳細な本文設計・必要画像の洗い出しはレッスン草稿作成スキルの担当）。

**全体を貫く比喩は RPG** — レベルアップ・クエスト・解放といった、説明なしで通じる語だけを使う。曼陀羅は進める先が枝分かれし、手前を終えると次が解放される構造なので、一本道のすごろくより RPG のほうが実態に合う。**使うのは冒頭と結びの声かけだけ**で、本文の説明には持ち込まない（レベルごとの分量はレッスン草稿作成スキルの「声かけ」に従う）。レッスン個別のたとえ（「コミットはセーブポイント」など）は従来どおり題材ごとに決めてよく、この比喩に揃える必要はない。

**画像素材の印**（→ 9章で積算）

| 印 | 意味 |
|---|---|
| `【撮】` | 社内固有の画面。**スクリーンショットの撮影が要る**（AI 生成では埋まらない） |
| `【録】` | 社内ツールの一連の操作。**短い画面録画が要る** |
| （印なし） | 概念図・作業フロー・一般ツールの画面・抽象概念。AI 生成またはフリー素材で埋まる |

### ① はじめにシリーズ

| ID | レッスン | slug | 時間 | 学習目標 | やってみる |
|---|---|---|---|---|---|
| L01 | トレーニングの進め方 【撮】 ☆ | `start/intro/how-to-learn` | 10分 | **このトレーニングの目的・ゴールと、修了時に何を手にするかが分かる**／曼陀羅の見方と進め方が分かる／**教わるのではなく自ら学ぶ姿勢で臨むことを理解する** | 曼陀羅を見て、自分が取り組む順番を決める |
| L02 | chocolatey のセットアップ 【撮】 | `start/setup/chocolatey` | 10分 | **社内インストールシステムから chocolatey を導入できる**／これが VSCode と uv の供給元だと分かる | 申請を出す →（承認後）`choco --version` を実行する |

## 9. 制作体制と進め方

1. 本計画書の構成に沿って、**レッスン草稿作成スキル（`dx-training-create`）で全レッスンの草稿を生成**する
2. 生成された草稿を人が磨く（技術検証・社内事情の追記・画像の差し込み）
3. 静的サイトへ変換して公開する

26レッスンを手書きすると、1本2時間として52時間かかる。同じ8月にツール開発・画像用意も並行するため、草稿生成を前提にしないと締切に届かない。

### 画像素材の積算

第6章の印から集計する。**社内固有の画面は AI 生成で埋まらず、人手の作業になる。**

| 印 | 本数 | 対象レッスン |
|---|---:|---|
| `【撮】` スクリーンショット | 9 | L01 曼陀羅／L02・L07 申請システム／L04 社内AIチャット／L12・L13・L14・L16 社内GitHub／L27 テンプレートリポジトリ |
| `【録】` 画面録画 | 1 | L17 レビュー→承認→マージの流れ |
| **人手が要る 計** | **10** | うち L01 は集合回の資料 |
| 印なし（AI・フリー素材で埋まる） | 19 | 概念図・作業フロー・一般ツールの画面 |

**29レッスン中10本が草稿生成だけでは完成しない。** 素材の撮影・録画は運営の作業として別途見積もる必要がある。とくに社内GitHub 関連が4本（L12〜L16）に集中しており、アカウント承認後でないと撮影できない。

> GitHub入門の分割で L11「GitHubとは」は一般の概念を扱う印なしレッスンになり、`【撮】` は L12「アカウント申請とサインイン」に寄った。**分割しても撮影の本数は増えていない**（印の精度が上がっただけ）。

### 模範解答の用意

分量方針で決めた通り、小演習には解答例を1行、ハンズオンには完成コード一式を用意する。

小演習26本分の解答例は草稿と同時に生成できるが、**動作検証は人手**になる。ハンズオンの完成コードは Part 1 / Part 2 の両方を用意する必要がある。

**ただし Part 2 の解法は配らない。** 手法を教えない方針のため、運営が用意するのは「解けることの確認用」であって配布物ではない。配布するのは Part 1 の完成コードのみ。

### ペア決めスクリプト

当日のペア決めに使い、デモした後に受講者へ配布する（→ 6.2）。**シャッフルと分割だけに絞る**ため分量は10行程度だが、**受講者の目の前で実データを処理する唯一のコード**になるので、読みやすさと説明しやすさを優先して書く。

### F2F キックオフ

L01 はトレーナーが集合で説明する。**曼陀羅の外にある運営イベントではなく、`lecture` フォーマットのコースとして曼陀羅に載せる**（→ 11.11）。枠は30分（説明10分＋Q&A 20分）。当日伝える3点は 4章 ① を参照。

### サポート体制

**専用の Teams チャンネルを用意し、受講者がいつでも質問できる場を作る。** キックオフで案内する。

自己学習は一人で進めるため、詰まったまま止まるとそのままフェードアウトする。設計原則の「やる気だけで学び続けられる人はほとんどいない。**意志ではなく環境で続けさせる**」に対応する仕組み。

**チャンネルが担う役割**

| 役割 | 内容 |
|---|---|
| 資料の補足 | 分かりづらい箇所をトレーナーが補う |
| 進め方の疑問への回答 | 曼陀羅の進み方、申請、環境まわり |
| **改善案の受け取り** | 資料やトレーニングの進め方への提案を集める |

**答えないもの**

- **検索すれば分かること、AI に聞けば分かること** — 「まず自分で調べて」と突き放す
- **受講者の代わりに開発すること** — 実装は本人がやる
- **ハンズオン応用課題（Part 2）の解法** — 手法を教えない方針の中核（→ 11.6）

この範囲であれば、設計原則の「運営は代わりに作らない」「分からないことは自分で調べる導線を先に渡す」と両立する。**質問できる場が常にあることと、何でも答えることは別**である。チャンネルは代行の窓口ではなく、**詰まりを解く場であり、改善を集める場**。

**改善案の受け取りは第1期で特に効く。** フェーズ1はトライアルの位置づけ（→ 8.1）なので、受講者からの指摘が次版に直結する。チャンネルを一方向の窓口にせず双方向にすることで、**教材改善の経路を最初から用意する**。

### 既存コンテンツの扱い

現在 `contents/` にあるサンプル（4シリーズ・14レッスン）は**基本的にいじらない**。本計画への流用や整理が必要な場合は、実行せず提案のみ行う。

> 参考: 既存サンプルの Python環境構築コースには「Anaconda セットアップ」「uv セットアップ」の両方がある。本計画は **uv に一本化**するため、流用する場合は Anaconda 側を落とす。

## 11. 決定の根拠と却下した案

後から経緯を再現できるよう、主要な分岐と却下理由を残す。

### 11.1 ハンズオンの題材と形式

- **採用**: 共通課題を解く Python スクリプト（組分けスクリプト）。AoC 風に Part 1 / Part 2 へ段階化し、間に3〜4日の自主考察を挟む
- **却下**: 各自が業務課題を持ち込む案 — 環境差とスコープ差で2時間の完走率が読めず、講師のサポート負荷が人数分に膨らむ（前版から継続）
- **却下**: 段階化せず応用込みで一括出題する案 — 「同じメンバーと連続しすぎない」は組合せ最適化（Social Golfer Problem の変種）であり、初心者が2時間で書けるものではない。**Part 1 まででツールとして動く**構成にしないと、完成しなかった人が手ぶらで帰ることになる
- **却下**: Part 3（全期間でペアを均等化）まで用意する案 — 2日しかないので到達しない。用意しても使われない

### 11.2 自分の業務データを使うか

- **採用**: 運営が用意した共通データのみ。受講者自身のデータは使わない
- **却下**: 自分の課のメンバー名・休暇予定を持参させる案

  **理由**: 課題を1日目まで伏せる方針と衝突する。自分のデータを用意させるには CSV の列構成を事前に開示する必要があり、開示すれば課題が部分的に漏れる。加えて、**今回のスクリプトがそのままの形で実務に使えるケースはほぼない**ため、自分のデータにするメリットが労力に見合わない。

  **代償**: 設計原則の「用意されたお題をなぞらせない。実際に使える道具を作らせる」とは緊張が残る。これは**意図的に受け入れたトレードオフ**であり、自分の業務との接続は L18 の「やってみる」（自動化したい作業を書き出す）に残す。

- **却下**: 共通データで解いた後、自分のデータに差し替える案 — 2日間しかないため差し替えの時間が取れない

### 11.3 ハンズオンの出力形式と外部ライブラリ

- **採用**: JSON 出力。外部ライブラリは L26 で **pandas の超基礎**
- **却下**: Excel 出力（`openpyxl`） — 記法に癖があり初心者がつまずく。加えて **CSV → Excel は形式がほとんど変わらず**、変換した実感が薄い
- **却下**: Markdown レポート → `tabulate` で表生成 — tabulate は一般的でなく、覚えても他所で使えない
- **却下**: Markdown レポート → `matplotlib` でグラフ生成 — matplotlib も記法が独特。加えて日本語ラベルのフォント設定でつまずく
- **却下**: Markdown → MkDocs で HTML 化 → リポジトリに配置 — **ビルド成果物である HTML をリポジトリに置くのは不自然**。README.md なら GitHub がそのまま整形表示するので、変換工程を挟む必要がない
- **却下**: **受講者の成果物を** GitHub Pages で公開して URL を共有する案

  **理由**: 公開の自動化には GitHub Actions の説明が必要になり、自己学習に GitHub Actions のレッスンを足すことになる（調整枠20分では足りない）。加えて社内 GitHub Pages はアクセスすると課金が発生するため、受講者それぞれが公開して回る形は避けたい。

  **教材サイト自体の公開先は社内 GitHub Pages で確定している**（8.1）。運営が1つ公開するのと、受講者8人がそれぞれ公開するのとでは、必要な説明量も課金の広がり方も異なる。

### 11.4 ペアの役割

- **採用**: 2人一組。**相互レビューの相手としてのみ**。実装は各自独立。各自が自分のリポジトリを持ち、相方を collaborator に招待する
- **却下**: 交代制ペアプロ（課題ごとに実装者とレビュアーを交代） — **ペアプロをトレーニングに組み込むのはハードルが高い**。進行管理の難度が上がり、片方のペースに引きずられる
- **却下**: 分担制（機能を2分割して並行実装し、後で結合） — 関数のインタフェースがずれたときの結合デバッグに60分は耐えられない。初心者ペアが最も高い確率で時間を溶かす箇所
- **却下**: branch protection（承認1件必須）で承認を強制する案 — 設定の説明に当日の時間を取られる。**レビューを飛ばす動機が受講者側にない**ため、運用ルールとして伝えるだけで足りる
- **却下**: 権限を read に絞るため、リポジトリを org 配下に置く／可視性を internal にする案 — GitHub の granular なロールは Organization 所有リポジトリの機能で、個人リポジトリでは read を選べない。ただし**相互レビューの相手に write が付くことの実害がない**ため、権限を絞るためだけに構成を変える必要はない

### 11.5 発表の形式

- **採用**: 全員が各自2分ずつ発表。定員8人（4組）。**自分のコードを自分で説明できることを要件にする**
- **採用**: **未完成でも発表する。** できたところまでと、詰まった箇所を共有する。設計原則（第11回）の「未完成での参加を許容することを明示する」に沿う。これにより Part 2 が解けなかった場合も2日目が成立し、**「解けた人だけの場」にならない**
- **却下**: 1組だけ代表発表 — 応用課題の手法を教えない方針にしたため**解法が発散する**。全員分に見る価値が出た
- **却下**: 各自3分（計24分） — 8人で24分となり、Part 2 の実装時間を圧迫する。2分に縮めることで実装に25分確保した
- **却下**: 定員10人（5組） — 発表に30分必要になり、2日目の時間割が崩れる。**回数を増やすほうが1回を大きくするより制御しやすい**

**AI 使用可とセットで機能する。** AI に丸投げしても発表で説明を求められるため、理解せずに済ませる導線が塞がる。設計原則の「理解できないものは作るな」を、禁止ではなく**運用ルールとして実装**した形。

### 11.6 応用課題の手法を教えるか

- **採用**: 教えない。各自が数日かけて工夫する。仲間との相談・AI への質問は自由
- **却下**: 想定解法（シャッフル＋リトライ）をレッスンで扱う案 — 全員が同じ解法になり、発表の価値が消える。設計原則の「運営は代わりに作らない」「分からないことは自分で調べる導線を先に渡す」にも反する

この方針の結果、**AI完全マスターシリーズがハンズオンの実質的な前提になった**（3.3 参照）。自主考察期間の主要な調べ手段が AI になるため。

### 11.7 Markdown をどう扱うか

- **採用**: 専用レッスンは作らない。**L14「push と pull」の push 対象を README.md にする**ことで、整形表示される体験だけ通す
- **却下**: Markdown 専用レッスンを新設する案（15分） — 完成物が Python スクリプトになり、README は補足程度になったため、文法を体系的に教える必要がなくなった
- **却下**: はじめにシリーズに置く案 — はじめにシリーズは最初の関門を軽く保つ設計であり、文法レッスンを足すと重くなる

### 11.8 `.gitignore` の置き場所

- **採用**: L08「最初のコミット」に含める（時間は15分据え置き）
- **却下**: 独立レッスンにする案 — 丁寧になるが +10〜15分で調整枠が削られる。`.gitignore` は「何をコミットするか決める」文脈の一部なので、コミットのレッスンから切り離すほうが不自然

**必要になった理由**: ハンズオンの成果物は Python スクリプトであり、**スクリプトが生成する JSON はコミットしない**方針を採ったため。生成物をリポジトリに置かないという原則を、実際に手を動かして守らせる。

### 11.9 ハンズオン2日の間隔

- **採用**: 3〜4日
- **却下**: 1週間 — 思考時間は十分だが、**1日目の内容を忘れ、熱量が下がる**。設計原則の「『作りたい』瞬間を逃さない」に反する
- **却下**: 2週間 — 上記がさらに強く出る。再立ち上げに時間を取られる

### 11.10 環境準備の案内をどこに置くか

- **採用**: **シリーズごとのトピックは、リードタイムがかかってもそのシリーズ内で完結させる**（→ 1.5）。Git申請は L07、社内GitHubアカウント申請は L12、uv は L19。**chocolatey と VSCode だけが横断的なため、はじめにシリーズに置く**
- **却下**: L01 で Git 申請を出させる案（前版の設計）

  **理由1**: L01 の学習目標は「曼陀羅の見方と進め方が分かる」だが、演習が「申請を出す」では**目標を一切検証できていない**。演習は目標の達成を確認するものであるべき。

  **理由2**: **Git が何かを知る前に Git の申請を出させることになり、文脈がない。**

- **却下**: L01 に Git申請のリードタイムを「情報として」載せ、それを踏まえて順番を決めさせる案

  **理由**: **Git の話は Git基礎シリーズでやるべき。** L01 に Git の事情を書き始めると、同じ理由で GitHub アカウント申請も載せることになり、**進め方のレッスンが環境構築の目次になる**。

- **却下**: リードタイムの長い申請をすべて、はじめにシリーズに集める案

  **理由**: 「時間がかかるから先頭に置く」を認めると、はじめにシリーズが全シリーズの環境構築置き場になる。**シリーズの独立性が崩れ、受講者がどのブランチから始めても成立するという曼陀羅の前提も崩れる。**

**口頭とレッスンの役割分担**: リードタイムのある申請は、**キックオフで口頭案内する**。レッスン本文には書かない。口頭は「いつ動くべきか」を伝えるのに向き、レッスンは「どう操作するか」を残すのに向く。前版は両者を L01 に混ぜていた。

**残るリスク**: キックオフの案内を聞き流した受講者は、学習期間の終盤で申請のリードタイムに当たる。自己学習期間は3週間あるため致命的ではないが、期間開始時のリマインド（→ 未決事項2）で保険をかけられる。

### 11.11 VSCode レッスンの置き場所と `format` の拡張

- **採用**: はじめにシリーズを**2コースに分割**。`DX入門コース`《lecture》☆ と `開発環境準備コース`《self-study》
- **採用**: `format` に **`lecture`** を追加。値は `self-study` / `lecture` / `hands-on` の3つ。**☆ は「集合形式かどうか」を表し、`lecture` と `hands-on` の両方に付く**
- **却下**: VSCode レッスンを DX入門コース内に置く案

  **理由**: L01 は F2F 講義、VSCode は自己学習。**「学習形態はコース単位で一貫させる」という既定方針に反する。** VSCode は申請にリードタイムがあるため当日その場では終わらず、集合扱いにはできない。コースに ☆ が付くと VSCode まで集合に見える。

- **却下**: VSCode 設定もキックオフの場で一緒にやる案 — 申請のリードタイム上、当日は完了できない
- **却下**: L01 を曼陀羅の外にある運営イベントとして扱い、`format` を拡張しない案 — 受講者から見て**集合で顔を合わせる回が曼陀羅に現れない**のは不親切。`lecture` を足せば、キックオフとハンズオンが同じ ☆ で表現でき、全体像が1枚で伝わる

**分岐は Git と Python が開発環境準備コースを経由する。** AI だけが DX入門コースから直接分岐する。

- **却下**: 3方向すべてを開発環境準備コースの後ろに置く案

  **理由**: AI は社内AIチャットがブラウザで完結するため、chocolatey も VSCode も必要としない。**要求していないものを前提にすると、承認待ちに進める道が完全になくなる**（→ 3.5）。

- **却下**: 3方向すべてを DX入門コースから出す案

  **理由**: **Python は uv を要求し、uv は chocolatey からしか入らない**（→ 11.19）。環境準備を飛ばすと、Python環境構築コースで供給されていないものを要求することになる。

- **却下**: 開発環境準備コースを分岐から外し、脇に置く案 — 出口の辺がなくなり、**必須にしたいのに任意コースになってしまう**。飛ばして修了できてしまう

  行き止まり自体は任意コースを表現する正当な手段だが（→ `mandala-guide.md`）、環境準備は Git と Python の前提であり必須。任意にしてよいコースではない。

**開発環境準備コースは Git と Python の両方の前提**なので、飛ばして修了することはできない（→ 3.3）。

### 11.12 Git を CLI で教えるか VSCode で教えるか

- **採用**: **CLI を主とし、同じ操作を VSCode でどうやるかをスクリーンショットで併記する**
- **却下**: VSCode を主とし CLI を併記する案 — 実務に近いが、**ボタンの裏で何が起きているかが見えない**。設計原則の「表面的な使い方ではなく原理を教える」に反する
- **却下**: VSCode のみ — L06「Gitの三大エリア」で教えた概念と操作が対応しなくなる。エラー時に検索もしにくい
- **却下**: CLI のみ（前版どおり） — 実務では VSCode から Git を操作することが多く、対応付けを受講者任せにすると学習が実務に繋がらない

**併記の位置づけ**: GUI のボタン位置はツールが変われば無効になるが、Git の概念とコマンドは残る。**原理を CLI で押さえたうえで、実務の入口として VSCode を示す**という順序にする。

### 11.13 Python 環境構築に何を使うか

- **採用**: **uv**
- **却下**: Anaconda — 社内では2026年末まで使用できるが、**主流が uv に移りつつある**。トレーニングで教えたものが期限付きだと、受講者は学び直しになる
- **却下**: 両方を並べて選ばせる案 — 環境構築で分岐すると、以降のレッスンの手順も分岐する。初心者向けトレーニングで環境が2通りあると、詰まったときの切り分けが難しくなる

ライブラリの追加も uv 経由で行うため、L26 の pandas 導入も uv で扱う。

### 11.14 ペアの決め方と配布物

- **採用**: **当日、運営が用意したペア決めスクリプトを実行してデモし、その結果でペアを確定する**
- **採用**: そのスクリプトを受講者に配布する。**ただしシャッフルと分割の部分だけ**に絞る

**採用理由**: 講師が恣意的に決めるより納得感がある。加えて、**今日作るのと同じ種類のツールが、その場の実データ（参加者名簿）で動く**ところを見せられる。設計原則の「実際の操作画面を見せる」を、教材の中ではなく**その場の実務**で成立させている。

11.2 で自分の業務データを使わないと決めた結果、トレーニング中に実データが動く場面がなくなっていた。**このデモがその代償を部分的に埋める。**

- **却下**: フル版（CSV読込・除外・JSON出力を含む）を配る案 — 「シャッフルしてスライスで分ける」は Part 1 の中核であり、フル版だと **Part 1 が調整作業になる**。CSV読込・除外・JSON出力はペア決めに本来不要なので、無理なく排除できる
- **却下**: デモのみで配布しない案 — メタ的な効果は残るが、参考材料としての価値を捨てることになる。Part 1 は「全員が動くツールを完成させる」工程であり、難易度で選別する場ではないので、完走率が上がるほうを取る
- **却下**: 配布を2日目に回す案 — Part 1 の完走率が下がる。Part 1 が終わらないと Part 2 の自主考察が始められない

**Part 2 は漏れない。** 評価関数を書いて条件を満たすまで試すという発想は、一回きりのペア決めには不要だからである。

### 11.15 collaborator 招待をレッスンの課題にするか

- **採用**: **L13 で「やり方の紹介」に留める。「やってみる」にはしない**
- **却下**: L13 の演習として実際に招待させる案

  **理由**: **自己学習では招待する相手がいない。** 自分のリポジトリでは admin なので操作自体は可能だが、練習のために同僚を招くのは不自然で、招かれた側にも作業が発生する。

  実際の操作はハンズオン当日、ペア確定後に行う。Settings → Collaborators から追加するだけなので、当日その場の説明で足りる。

- **却下**: レッスンで一切触れず、当日すべて説明する案 — 当日の冒頭10分に説明が集中する。一度見たことがある状態にしておけば、当日は確認で済む

### 11.16 Python概要コースと環境構築コースの分け方

- **採用**: 概要コースは **L18「Pythonとは何か」の1本**。環境構築コースを **L19「Python環境のセットアップ（uv）」→ L20「はじめてのスクリプトを動かす」の2本**にする
- **却下**: 前版の並び（概要コースに「はじめてのスクリプト」を置き、環境構築をその後にする）

  **理由**: **Python が入っていない状態でスクリプトを実行することになる。** 前版では曖昧なまま通っていたが、**uv に申請が必要と決めたことでこの矛盾が実害を持つ**。承認前に到達した受講者には実行環境がない。

  「Pythonとは何か」は環境がなくても読めるが、「スクリプトを動かす」は環境がないと成立しない。**環境を要するかどうかでコースを分ける**ほうが、コースの意味も明確になる。

レッスン数（9）は変わらない。コース内訳が `概要 2/25分・環境構築 1/15分` から `概要 1/10分・環境構築 2/25分` に移る（uv は chocolatey 済み前提で10分 → 11.19）。

### 11.17 サポート体制の範囲

- **採用**: 専用 Teams チャンネルを用意し、キックオフで案内する。担うのは**資料の補足・進め方の疑問への回答・改善案の受け取り**の3つ
- **採用**: **検索や AI で分かることは「まず自分で調べて」と突き放す。受講者の代わりに開発はしない**

**設けた理由**: 自己学習は一人で進めるため、詰まったまま止まるとフェードアウトする。設計原則の「やる気だけで学び続けられる人はほとんどいない。**意志ではなく環境で続けさせる**」への対応。

**設計原則と矛盾しない。** 「運営は代わりに作らない」「分からないことは自分で調べる導線を先に渡す」は、答える範囲を限ることで保たれる。**質問できる場が常にあることと、何でも答えることは別**である。

- **却下**: 質問の種類を問わず答える案 — 「運営は代わりに作らない」が崩れる。特にハンズオンの応用課題は**手法を教えないことが設計の中核**（→ 11.6）なので、チャンネルで解法を答えると2日目の発表が成立しなくなる
- **却下**: チャンネルを設けない案 — 申請や環境の詰まりは本人には解きようがない。**そこで止まるのは学習ではなく事務**であり、放置するとフェードアウトを招く

**改善案の受け取りを役割に含めたのが本計画の特徴。** 第1期はトライアル（→ 8.1）なので、受講者からの指摘が次版に直結する。**分かれ目は「本人と AI で解けるか」** — 解けるものは委ね、解けないもの（社内の申請、教材の不備）は運営が引き取り、後者は改善のインプットにもなる。

### 11.19 VSCode を部門の正規手順で入れるか

社内には VSCode の導入経路が2つある。

| | 経路 | 部門での位置づけ |
|---|---|---|
| 案A | 社内インストールシステムから直接 | 非正規。ただし**この方法で入れている人は多い** |
| 案B | 社内インストールシステム → chocolatey → **部門向けカスタマイズ版 VSCode** | **部門の正規手順** |

- **採用**: **案B（正規手順）**
- **却下**: 案A（直接インストール）

**理由1: 対象が新入社員・中途採用社員。** これから環境を作る人たちであり、**最初から部門標準を身につけさせるのがトレーニングの役割**。既に案Aで入れている人がいるのは事実だが、それは既存の人が非正規なだけで、新規に非正規を教える理由にはならない。

**理由2: 環境差が減る。** 部門向けカスタマイズ版なら設定や拡張が揃っており、トレーニング中の「私の画面と違う」が減る。

**理由3: 申請が1件に集約されて、実は速い。** 案Aだと VSCode と chocolatey（uv 用）で申請が2件になる。案Bなら chocolatey 1件から VSCode と uv の両方が入る。**手順は長いのに、待ちは短い。**

```
案A                              案B（採用）
  VSCode 申請      1日             chocolatey 申請   1日
  chocolatey 申請  1日 (uv用)           ↓
 （申請2件を管理）                  VSCode  数分
                                    uv      数分
                                   （申請1件）
```

**代償**: chocolatey が Python シリーズの前提にもなるため、**分岐が「AI のみ DX入門から、Git と Python は環境準備から」に変わった**。chocolatey の承認待ち（1日）に進められるのは AI の15分だけになる。前案では145分あった。

この代償を受け入れたのは、**待ちが1日で3週間の期間の初日に収まる**ことと、上記の理由1〜3が上回ると判断したため。

**Git は例外。** chocolatey 経由では入らず、社内インストールシステムからのみ導入できる。そのため Git の申請は別途1日必要（→ 1.5）。

**SourceTree は扱わない。** Git のインストール時に同梱するか選択でき、便利なので同梱は勧める。ただし**使い方はトレーニングの範囲外**とし、選択肢があるとコメントするに留める。Git 操作のメインは VSCode に統一する（→ 11.12）。**教える GUI を2つに増やすと、詰まったときの切り分けが難しくなる。**

### 11.20 GitHub入門コースの分け方とリポジトリ操作の置き場

前版では GitHub入門コースが `L11 GitHubとは・アカウント申請` と `L12 リポジトリを作る / clone` の2本、GitHubリモート連携コースが `L13 push と pull` の1本だった。

- **採用**: 入門コースを **L11「GitHubとは」／L12「アカウント申請とサインイン」の2本に分割**する
- **採用**: **リポジトリ作成と clone をGitHubリモート連携コースへ移す**（入門2本20分／リモート連携2本30分）
- **却下**: 前版の並びを維持する案

**理由1: 受講対象が違うレッスンを1本にまとめない。** 「GitHubとは」は**アカウントを既に持つ人にも必要**だが、申請はアカウントを持たない人だけの作業。1本にまとめると、コース仕様の受講対象を「アカウントを持っていない人」と書いた時点で、アカウント持ちが「GitHubとは」ごと飛ばすことになる。分ければコース単位の飛ばし判定が正しく効く。

**理由2: GitHubリモート連携コースが1本しかなく、コースとして薄かった。** 「リポジトリを作る → clone → push → pull」はすべて**ローカルとリモートをつなぐ**操作で、コース名にも文字通り合う。移動により入門は「準備」、リモート連携は「実操作」に純化される。前提の連鎖も `入門（アカウント取得）→ リモート連携（作る・つなぐ）→ ブランチとPR（回す）` と素直になる。

**理由3: 社内で使う GitHub なので「とは」に補足が要る。** 公開 GitHub との違い、利用上の制約、社内のサポート窓口。これらは申請とは別の話であり、10分を要する。

**代償: 調整枠が 15分 → 5分になる。** +1レッスン・+10分。**これ以上レッスンを追加する余地はほぼ失われた**（→ 7章）。それでも分割を採ったのは、受講対象の切り分けが自己学習の飛ばし判定に直結するため。

**画像素材は増えない。** 前版で L11 に付いていた `【撮】` は、分割後 L12（申請画面）に寄る。L11 は一般の概念を扱う印なしレッスンになり、**`【撮】` の総数は9本のまま、印の精度だけが上がる**（→ 9章）。

**申請レッスンの型も揃う。** L12 に承認後のサインイン・プロフィール設定まで含めることで、L02（chocolatey）・L07（Git）と同じ「申請 → 承認待ち → 承認後の実作業」の形になる。申請だけの単独レッスンにはしない。
