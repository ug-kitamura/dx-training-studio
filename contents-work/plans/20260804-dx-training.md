- 作成日: 2026-08-04
- 対象: DXトレーニング 自己学習コンテンツ ＋ ハンズオントレーニング第1弾
- 決定手段: グリルセッション（本書末尾に決定の根拠と却下案を記載）
- ステータス: 構成確定 / 一部仮置きあり（→「未決事項」参照）

## 1. 前提

### 1.1 目的

システム・ソフトのメンバにツール開発を促し、業務効率を上げる。

### 1.2 受講者像

エンジニアリング部署の新入社員・中途採用社員。

| 項目 | 前提 |
|---|---|
| プログラミング | 多少の知識はある（変数・制御構造の説明は不要） |
| Python | 初心者 |
| Git / GitHub | 初心者 |
| AI | 社内チャットツールや ChatGPT で調べ物をしたことがある程度 |

### 1.3 ゴールの定義

**2時間（1h × 2回）で、必ず動くツールが1つ完成する体験**を全員に届ける。

- ツールのフォーマット（骨組み・処理の流れ）は運営が固定する
- 入力データだけ受講者自身の業務データを使い、自分事として取り組めるようにする

### 1.4 分量方針

| 項目 | 値 |
|---|---|
| 総レッスン数 | 25 |
| 1レッスン | 10〜15分 |
| 自己学習の総量 | 約5時間35分（上限6時間） |
| 自己学習期間 | 3週間 |
| ハンズオン | 1h × 2回（自己学習時間には含めない） |

- 必須／任意の2層分けはしない。25レッスンすべてが必須
- ハンズオンで直接使わない基礎・概念・セットアップも厚くカバーする
- **全レッスンに5分以内の「やってみる」演習を入れる**
- **手順の説明にはスクリーンショットや図を載せる。**文章だけで済ませない。実際の画面を見せることで「こういう画面なんだ、ここをこう操作するんだ」が伝わる
- **小演習には折りたたんだ解答例を1行つける。**完成コード一式を渡すのはハンズオンのみ

解答例は `<details>` で折りたたみ、受講者が自分のタイミングで答え合わせできるようにする。

```markdown
### やってみる
（課題）

<details>
<summary>解答例</summary>

（1行の解答例）

</details>
```

| # | From（コース） | To（コース） | シリーズ間ペア |

### 3.3 規則適合の確認

`lib/course-flow.ts` から読み取った規則に対する自己チェック。

| 規則 | 判定 |
|---|---|
| シリーズ内は `courses[]` 順の直列鎖のみ（シリーズ内分岐は不可） | ✓ 全シリーズが直列 |
| シリーズ間の辺は、同一シリーズペアにつき全体で1本 | ✓ 7本すべて異なるペア |
| 1コースから同一ターゲットシリーズへ出る辺は1本 | ✓ DX入門の3本は宛先シリーズが全て異なる |
| 循環なし | ✓ start → {ai, git, python} → github → build の一方向 |
| 到達不能・行き止まりのコースがない | ✓ Gitシリーズは GitHub 経由で build に接続 |

補足: Gitシリーズは build への直接の辺を持たないが、`Git基本操作 → GitHub入門` を経由するため**全Gitコースが build の前提として必須**になる。

### 3.4 進行ルール

- あるコースに入るには、そこへ合流する**全ての辺の元コースが完了済み**である必要がある
- その範囲内であれば、受講者はどのブランチから進めても構わない（順序は受講者に任せる）
- 全ブランチの完了を求めるが、**ハンズオン参加の強制ゲートにはしない**。未完了でも希望者は参加でき、その時点でできる限りのことをしてもらう

## 4. シリーズ仕様

### ① はじめにシリーズ `start`

| 項目 | 内容 |
|---|---|
| ゴール | 曼陀羅の見方と進め方を理解し、環境申請を先に出せる状態になる |
| 対象 | 受講者全員（最初に必ず通る） |
| レッスン数 / 時間 | 1 / 10分 |
| 前提 | なし |
| 分岐 | AI・Git・Python の3方向へ |

**設計意図**: 社内では Git のインストールに申請が必要で数日かかる。ここで申請だけ先に出させ、**待ち時間に他シリーズを進められる**ようにする。

### ② AIシリーズ `ai`

| 項目 | 内容 |
|---|---|
| ゴール | 社内AIチャットツールの基本操作ができ、詰まったときに聞ける |
| 位置づけ | おまけ。「使えれば良い」程度の温度感 |
| レッスン数 / 時間 | 1 / 15分 |
| 前提 | はじめにシリーズ |
| 今後 | コンテンツを育てていく想定。シリーズを独立させたのはそのため |

### ③ Gitシリーズ `git`

| 項目 | 内容 |
|---|---|
| ゴール | ローカルで変更を記録・確認・取り消しできる |
| レッスン数 / 時間 | 6 / 85分 |
| 前提 | はじめにシリーズ |
| 範囲外 | ブランチ（GitHubシリーズで扱う） |

**設計意図**: ほとんどの操作は結局 GitHub とセットで行うため、Gitシリーズは**ローカル操作の基礎に絞って軽くする**。

### ④ GitHubシリーズ `github`

| 項目 | 内容 |
|---|---|
| ゴール | ブランチを切って PR を出し、レビューを経てマージできる |
| レッスン数 / 時間 | 6 / 85分 |
| 前提 | Git基本操作コース（commit できないと push できないため） |

**設計意図**: 「ブランチを切る → push → PR → マージ」が1コース内で地続きになるよう、ブランチをこのシリーズに置いた。

### ⑤ Pythonシリーズ `python`

| 項目 | 内容 |
|---|---|
| ゴール | ファイルを読んで加工し、結果を出力するスクリプトを書ける |
| レッスン数 / 時間 | 9 / 130分 |
| 前提 | はじめにシリーズ |

**設計意図**: 中級コースの3本（関数分割・ファイル読み書き・外部ライブラリ）は、ハンズオンの完成物から逆算した構成にしている。

### ⑥ ツール開発実践シリーズ `build` ☆

| 項目 | 内容 |
|---|---|
| ゴール | 自分の業務データを入力にした動くツールを1つ完成させる |
| レッスン数 / 時間 | 2 / 10分（事前）＋ 60分×2（当日） |
| 前提 | AI基礎・GitHub ブランチとPR・Python中級 の3本が合流 |

**命名の意図**: 「卒業試験」等ではなく **「ツール開発実践」**。ゴールは「作れた実感」であって評価ではないため、試験という含意を避けた。トレーニングの目的そのものを名前にすることで、曼陀羅を開いた瞬間にゴールが伝わる。

| ID | レッスン | slug | 時間 | 学習目標 | やってみる |
|---|---|---|---|---|---|

## 11. 決定の根拠と却下した案

後から経緯を再現できるよう、主要な分岐と却下理由を残す。

### 11.1 ハンズオンの完成物

- **採用**: フォーマットは運営が固定し、入力データのみ受講者自身のもの
- **却下**: 各自が業務課題を持ち込む案 — 環境差とスコープ差で2時間の完走率が読めず、講師のサポート負荷が人数分に膨らむ

### 11.2 分量の2層化

- **採用**: 25レッスンすべて必須（層分けなし）
- **却下**: 必須20＋任意（reference）の2層構造 — 25レッスンの枠内で基礎は十分カバーできるため、層を分ける複雑さが見合わない

### 11.3 AIシリーズの規模

- **採用**: 1レッスン（社内AIチャットの基本操作のみ）
- **却下**: 3レッスンに拡張する案 — 現時点では「使えれば良い」という位置づけ。今後コンテンツを育てる前提でシリーズは独立させた

### 11.4 ブランチをどのシリーズに置くか

- **採用**: GitHubシリーズ（案B）
- **却下**: Gitシリーズに残し、基本操作コースから GitHub へ分岐する案（案A）

  **理由**: `lib/course-flow.ts` の実装上、**シリーズ間の辺は同一ペアにつき全体で1本**しか張れない。案Aだと `Git基本操作 → GitHub入門` で1本を使い切るため、`Gitブランチ → GitHub PR` の依存が表現できず、**ブランチ未習のまま PR コースに入れてしまう**。さらに Gitブランチコースが行き止まりになり、build への辺を別途足さないと飛ばせてしまう。
  加えて「ブランチを切る → push → PR → マージ」は一連で理解する内容であり、間に別シリーズを挟むと繋がりが切れる。

- **却下**: Gitを全部終えてから GitHub（案C） — 依存は安全だが完全な直列になり、GitHub に触れるのが最も遅くなる

### 11.5 合流先シリーズの名称

- **採用**: 「ツール開発実践シリーズ」
- **却下**: 「卒業試験シリーズ」 — ゴールは「作れた実感」であり、試験＝評価される場という含意は新人・中途にとって心理的ハードルになる
- **却下**: 「卒業制作シリーズ」「総仕上げシリーズ」 — 実務ツールという実用性のニュアンスが弱い

### 11.6 学習形態（独学 / ハンズオン）の保持場所

- **採用**: コース `.meta.json` の `format` フィールド
- **却下**: レッスン frontmatter の `tags` に混ぜる案 — tags は自由語彙のため、内容タグと同列に並んで区別できず、`handson` / `hands-on` / `ハンズオン` の表記ゆれと付け忘れが避けられない
- **却下**: レッスン単位で持つ案 — 学習形態はコース単位で一貫するため、25本すべてに記入するのは付け忘れのリスクだけが増える

### 11.7 演習の入れ方

- **採用**: 全レッスンに5分以内の「やってみる」
- **却下**: コース末に演習レッスンを1本置く案 — 読み物を流し読みして演習で詰まる形になり、どこで分からなくなったか本人にも特定できない
- **却下**: 選択式の確認問題のみ（既存サンプル踏襲） — Python と Git は読んで分かった気になる典型領域で、ハンズオン当日に初めて `git commit` を打つことになる
