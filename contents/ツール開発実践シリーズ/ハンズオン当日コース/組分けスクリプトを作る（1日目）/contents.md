# 組分けスクリプトを作る（1日目）

## 学習目標

ハンズオン1日目へようこそ。集めた武器を実際に振るう日です。この60分が終わったとき、あなたの社内GitHub の main には、**課題を解く動くツールが1つ、レビューを経てマージされています**。作るのはあなた、レビューするのは相方、マージするのもあなたです。

このページは今日の進行表と課題文を兼ねています。手が止まったら、いつでもここに戻ってきてください。

## 今日の時間割

```text
00-10  課題の公開・骨組みの説明
       ペア決めスクリプトのデモ → ペア確定 → スクリプト配布
       collaborator 招待のやり方の説明
10-38  Part 1 実装（各自）
       ※ 実装は別ルート（ブランチ）を切ってから
       ※ この時間内に相方への招待〜承諾まで済ませる（手順は下の「相方を招待する」）
38-50  PR 作成 → 相方がレビュー → 承認 → マージ
50-55  main で動作確認 ―― ここで動くツールが完成
55-60  応用課題（Part 2）の説明
```

## ペアを決める——目の前で動くツール

最初に、運営が**ペア決めスクリプト**を実行します。参加者の名簿を読み、シャッフル（Python の random モジュール）して2人ずつに分ける——それだけの10行ほどの Python スクリプトです。その結果で今日のペアが決まります。

注目してほしいのは、**いま目の前で、実データを処理する小さなツールが動いた**ことです。デモのあとスクリプトは配布されるので、**書き方を参考にしてかまいません**。

_出典: [Python 公式ドキュメント「random --- 疑似乱数を生成する」](https://docs.python.org/ja/3/library/random.html)（2026年8月取得）_

ペアは**相互レビューの相手**です。実装はそれぞれが自分のリポジトリで行い、共同では書きません。

## 課題 Part 1

事前準備で複製したリポジトリに入っていたサンプル CSV——あれが今日の課題データです。**課の10人を、休暇の人を除いて3組に分ける**のが今日の課題です。

始める前に、作業ブランチを切ってください（GitHubブランチ・PRコースのとおり）。スクリプトはリポジトリ直下に1本作り（例: `grouping.py`。名前は自由）、実装中は次のコマンドで何度でも実行して確かめながら進めます。

```bash
uv run python grouping.py
```

| ファイル | 列 | 中身 |
|---|---|---|
| `members.csv` | `name` | 課のメンバー10人の名前 |
| `vacations.csv` | `name,week` | その週に休暇を取る人の行だけが並ぶ（`week` は 1〜4） |

**Part 1 でやること**: `week` が 1 の休暇者を除いたメンバーを3組に分け、結果を JSON ファイルに書き出す。組の人数はできるだけ均等にする（最大の組と最小の組の差が1以内）。

出力のイメージはこうです。

```json
{"week": 1, "groups": [["さとう", "すずき", "いとう"], ["わたなべ", "こばやし", "かとう"], ["よしだ", "なかむら", "ささき"]]}
```

- 考えなくてよいこと: 出力がこの例と一字一句同じである必要はありません。**週・組・名前が読み取れる JSON** なら形は任せます
- 誰がどの組かの「正解」はありません。休暇者が除かれ、3組がほぼ均等なら正解です
- **書き出した JSON はコミットしません。** スクリプトが作る生成物は保管庫に入れない——Git基本操作コースでやったとおり、`.gitignore`（セーブ対象外リスト）に追加してください

## 使う道具はすべて学んだもの

新しい文法は1つも要りません。課題を分解すると、全部どこかのレッスンでやったことです。

| 課題の要素 | どこで学んだか |
|---|---|
| CSV を読む（2ファイル） | Python中級コースのファイル読み書き（csv.DictReader） |
| 休暇の人を除く | Python文法基礎コースの条件分岐とループ（for と if、`in`） |
| 3組に分ける | 配布された**ペア決めスクリプト**の分け方が参考になる |
| JSON で書き出す | Python中級コースのファイル読み書き（json.dump） |
| ブランチ → PR → レビュー → マージ | GitHubブランチ・PRコース |

- pandas を使っても標準の `csv` を使ってもかまいません（pandas を使う場合は `uv add pandas`。プロジェクト化がまだなら先に `uv init` を実行します）
- 関数に切るのは任意です。動けばベタ書きでも完成です
- 詰まったら社内AIチャット（隣の席の相談相手）に聞いてかまいません。エラー文をそのまま貼るのでしたね。**ただし、書いたコードは発表で自分の言葉で説明できること**

## 相方を招待する——実装しながら

レビューし合うには、お互いのリポジトリに入れる必要があります。GitHubリモート連携コースで「見るだけ」だった collaborator 招待を、ここで実際にやります。

> [!IMPORTANT]
> 招待は**双方向**です。あなたも相方も、それぞれ自分のリポジトリに相手を招きます。片方だけだと、どちらかの PR がレビューできません。そして招待は**相手が承諾して初めて有効**になります。往復に時間がかかるので、**実装の手を止めてでも、先に招待を送ってください**。

| 順 | 誰が | やること |
|---|---|---|
| 1 | あなた | 自分のリポジトリの **Settings** → **Collaborators** → **Add people** → 相方の username を入力して追加 |
| 2 | 相方 | 届いた招待（画面の通知またはメールのリンク）を開いて **Accept** |
| 3 | 両者 | 立場を入れ替えて 1〜2 をもう一度（相方のリポジトリに、あなたが招かれる） |

招待が見つからないときは、招待した側が自分のリポジトリの URL を相方に送ってください。相方がそのページを開くと承諾のバナーが出ます。それでも進まなければ、**運営に声をかけてください**——権限や招待まわりの詰まりは、AI より運営を呼ぶほうが早い種類の問題です。

_出典: [GitHub Docs「Inviting collaborators to a personal repository」](https://docs.github.com/en/enterprise-server@latest/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)（2026年8月取得）_

## PR を出して、レビューし合う

実装が済んだら、GitHubブランチ・PRコースの流れをそのまま相方と回します。自分のリポジトリでは作者、相方のリポジトリではレビュアー——**1人で2役**です。

```text
 あなたのリポジトリ                相方のリポジトリ
   別ルート（feature）                別ルート（feature）
       │ PR                              │ PR
       ▼                                 ▼
   相方がレビュー・承認              あなたがレビュー・承認
       │                                 │
       ▼ あなたがマージ                  ▼ 相方がマージ
     main                              main
```

| 順 | やること |
|---|---|
| 1 | ブランチを切って実装し、コミットを積む（これは 10-38 の実装時間の話。ここまでは各自） |
| 2 | push して自分のリポジトリに **PR を作る**（説明には「何を・なぜ」の2行） |
| 3 | 相方の PR を開き、**「なぜこう書いたか」を1つ質問**する（Files changed の行にコメント） |
| 4 | 自分の PR に質問が来たら、自分の言葉で答える |
| 5 | 相手の回答を読んだら **Approve** する |
| 6 | Approve をもらったら、**自分の PR は自分でマージ**する |

- **レビューは自分の実装が終わっていなくてもやってかまいません。** 相方の PR が先に来たら、手を止めてレビューを返すほうが全体が進みます
- 質問は1つでよく、あら探しではありません。形だけ例を挙げると「◯行目で辞書ではなくリストを選んだのはなぜですか？」のような、**書いた本人しか答えられない問い**にします（この例の中身はダミーです）
- 答えられたら承認（Approve）のサインです。これが「自分のコードを自分で説明できる」ことの最初の検証で、2日目の発表のリハーサルにもなります

## main で動かす——完成の瞬間

マージが済んだら、手元を main に戻して取り込み、実行します。

```bash
git switch main
git pull
uv run python grouping.py
```

（スクリプト名は自分が付けたものに読み替えてください。）JSON が書き出されたら——**動くツールが1つ、完成しました**。2時間コースの折り返しにして、このトレーニングの最初のゴールです。

## 応用課題 Part 2——次に会う日まで

最後に、2日目までの応用課題です。

**Part 2 でやること**: 4週分の組分けを一度に生成する（`vacations.csv` の `week` 1〜4 をそれぞれ反映する）。ただし、**前の週と同じペアが同じ組にならない**こと。出力は Part 1 の形を週の配列に広げた JSON（`{"weeks": [...]}`）とする。

間の数日で進めるときも、**作業は別ルート（ブランチ）を切ってから**。2日目の PR はそのブランチから出します。

ここから2日目までの3〜4日、**解法は配られません**。運営に聞いても教えません。それがこの課題の設計です。代わりに、次は全部使ってかまいません。

- 仲間と相談する（ペアの相方でも、それ以外でも）
- 社内AIチャットに聞く（相談の仕方は AI基礎コースのとおり）
- Teams チャンネル **DX Tools Training** で質問する（解法そのものには答えません）

4週分をどう分けるか——そこがあなたの工夫のしどころで、**解き方は1つではありません**。そして、**解けきらなくても2日目は成立します**。できたところまでと、どこに詰まったかを話せば十分です（発表の型は2日目のページにあります）。2日目は、その工夫を2分で発表するところまでがクエストです。
