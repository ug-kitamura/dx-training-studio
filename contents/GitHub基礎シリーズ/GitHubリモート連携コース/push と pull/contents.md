# push と pull

## 学習目標

手元と共有保管庫が線でつながりました。このレッスンでは、その線の上をデータが実際に行き来します。ゴールは、**手元のセーブを共有保管庫へ送れること（push）**、そして**向こうの変更を手元へ取り込めること（pull）**です。

Git基礎シリーズで「名前だけ出てくる」と予告した2つの言葉が、ここで実体になります。難しい話は出てきません。**送る**と**取り込む**、方向が2つあるだけです。

```text
 手元の保管庫  ──── push（送る） ────▶  共有保管庫
              ◀─── pull（取り込む） ───
```

## 送る——push

前のレッスンで clone した `github-practice` フォルダを、VSCode で開いてください。ここにある `README.md` を編集して、共有保管庫へ送ります。

まず編集します。`README.md` を開き、中身を次のように書き換えて保存してください（`Ctrl+S`）。

```markdown
# GitHub の練習

GitHub基礎シリーズの練習用リポジトリです。

## やったこと

- リポジトリを作って clone した
- README を書いた
```

ここから先は、Git基礎シリーズでやったとおりです。**セーブしてから、送ります。**

```bash
git status
git add README.md
git commit -m "READMEを書いた"
```

`git status` では `README.md` が `Changes not staged for commit` の下に出ます。add した後にもう一度打てば `Changes to be committed` へ移ります——Git基礎シリーズで見たとおりの動きです。

ここまでで、手元の保管庫にセーブが1つ増えました。ただし、**この時点では共有保管庫はまだ何も知りません**。ブラウザで社内GitHub のリポジトリを開いても、README は元のままです。

送ります。

```bash
git push
```

数行のメッセージが流れて、最後に `main -> main` のような行が出れば成功です。

ブラウザで社内GitHub のリポジトリのページを開き直してください（すでに開いていれば再読み込み）。**いま書いた README が表示されているはずです。**

> **社内画像**: 社内GitHub のリポジトリトップページで、push した README.md が整形表示された状態。見出し「GitHub の練習」と箇条書きが本文の下に表示されている画角。ユーザー名・組織名・URL のホスト部分はマスクする

セーブ（commit）と送る（push）が**別の操作**であることに注目してください。手元で何回コミットしても、push するまで共有保管庫には届きません。逆に言えば、**まとまってから送ればよい**ということです。

## README は案内板——Markdown を3つだけ

いま書いた README が、画面ではきれいに整形されて表示されました。`#` や `-` の記号が、見出しや箇条書きに変換されています。この書き方を **Markdown** と呼びます。

**README.md は、保管庫の入口に貼る案内板**です。GitHub はリポジトリを開いたとき、README.md を自動で整形して最初に見せます。「これは何のリポジトリか」「どう使うか」を、訪れた人が最初に読む場所です。

このトレーニングで覚える Markdown は**3つだけ**です。

| 書き方 | 表示 |
|---|---|
| `# 見出し` | 大きな見出し（`##` で一段小さく） |
| `- 項目` | 箇条書き |
| ` ```bash ` で囲む | コードブロック（コマンドやコードを枠で囲む） |

これ以上は覚えなくて大丈夫です。表や画像の書き方もありますが、必要になったときに調べれば足ります。

> [!TIP]
> VSCode で `.md` ファイルを開いているとき、`Ctrl+Shift+V` で整形後のプレビューが見られます。push する前に確認できます。

## 取り込む——pull

今度は逆向きです。**共有保管庫の側が変わったとき**、手元へ取り込みます。

実務では「仲間が push した」という状況ですが、いまは一人なので、**ブラウザから直接編集して**その状況を作ります。

1. 社内GitHub のリポジトリで `README.md` をクリックして開く
2. **鉛筆アイコン**（Edit this file）をクリックする
3. 末尾に `- ブラウザから編集した` の1行を足す
4. **「Commit changes」** をクリックして確定する（確認のダイアログが出たら、そのまま確定する）

> **社内画像**: 社内GitHub のブラウザ上で README.md を編集する流れ。①README.md を開いた状態（鉛筆アイコンが見える画角） ②編集画面 ③Commit changes を押すところ。画面が変わるごとに1枚を目安に撮る。ユーザー名・組織名・URL のホスト部分はマスクする

これで、**共有保管庫にだけ**新しいセーブができました。手元の `README.md` を見ても、この行はありません。

取り込みます。VSCode のターミナルで実行してください。

```bash
git pull
```

```text
Updating a1b2c3d..4e5f6a7
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

（表示は要点だけ抜き出しています。実際にはもう少し行が並びます。）

VSCode で `README.md` を開くと、ブラウザで足した行が入っています。

ここで習慣を1つ渡します。**push する前に pull する。**

仲間が先に何かを送っていた場合、いきなり push すると Git に断られます。**共有保管庫のほうが手元より進んでいる状態で上書きすると、仲間のセーブが消えてしまう**——それを防ぐために止めているのです。先に pull して手元を最新にしてから送れば、この面倒は起きません。「**送る前に、取り込む**」——順番だけ覚えてください。

## やってみる

README.md を書いて push し、GitHub 上での表示を確認します。

1. 手元の `README.md` に、**自分の言葉で**1行足す（何の練習リポジトリかなど）
2. `git add` → `git commit -m "..."` → `git push`
3. ブラウザで社内GitHub のリポジトリを開き直し、足した行が表示されていることを確認する

## まとめ

このレッスンで増えた操作は `push` と `pull` の2つ。持ち帰りは3つです。

1. **`git push`** — 手元のセーブを共有保管庫へ送る。**commit しただけでは届かない**
2. **`git pull`** — 共有保管庫の新しいセーブを手元へ取り込む
3. **送る前に、取り込む。** VSCode の「変更の同期」ボタンは、この2つをまとめて実行している

手元と共有保管庫の間で、データが両方向に流れるようになりました。次のコースでは、**本編を壊さずに作業する**方法——ブランチに進みます。

## 確認問題

1. `commit` と `push` は何が違うでしょうか。「手元」と「共有保管庫」という言葉を使って1文で説明してみてください。
2. 「push する前に pull する」のはなぜでしょうか。仲間が同じリポジトリを使っている場面を想像して、自分の言葉で説明してみてください。
