# GitHubとは

## 学習目標

Git基礎シリーズをクリアしたあなたは、自分の作業をいつでもセーブして、安全に元へ戻せるようになりました。ただ、そのセーブデータは**自分の PC の中にしかありません**。「このスクリプト、見てもらえますか」と渡したいとき、PC が壊れたとき——手元の保管庫だけでは困る場面が、実務にはいくつもあります。

このシリーズ（GitHub基礎シリーズ）で学ぶのは、**セーブデータを仲間と共有する場所のつなぎ方**です。手元の保管庫と共有の保管庫をつなぎ（リモート連携コース）、本編から分かれた別ルートで作業して合流させる（ブランチ・PRコース）ところまで進みます。終わる頃には、自分の作業を**壊さず、仲間と安全に合わせる**力が手に入ります。

その最初のレッスンのゴールは、**GitHub が何をする場所かを言えること**、そして**社内で使う GitHub が世の中の GitHub とどう違うか、使うときの約束と困ったときの窓口が分かること**です。コマンドはまだ1つも打ちません。地図を眺める回です。

## GitHub は「共有保管庫」

Git基礎シリーズでは、フォルダの中の `.git` を「セーブデータの保管庫」と呼びました。GitHub は、**この保管庫のコピーをサーバーの上に置く場所**です。ここでは**共有保管庫**と呼びます。

```text
   あなたの PC                          サーバー（GitHub）
 ┌───────────────┐    送る（push）   ┌───────────────┐
 │ 手元の保管庫   │ ───────────────▶ │  共有保管庫    │ ◀── 仲間も見る・取り込む
 │   (.git)      │ ◀─────────────── │               │
 └───────────────┘   取り込む（pull）└───────────────┘
```

矢印の名前（push・pull）は、Git基礎シリーズで「名前だけ出てくる、GitHub基礎シリーズで扱う」と予告したものです。いまはまだ覚えなくてよく、**保管庫が2つあって、行き来できる**という形だけ見てください。

ここで混同しやすい点を先に片づけます。**Git と GitHub は別のものです。**

| | 何か | どこで動くか |
|---|---|---|
| Git | セーブする・戻す**道具**（コマンド） | あなたの PC の中 |
| GitHub | 保管庫のコピーを置く**場所**（Web サービス） | サーバーの上。ブラウザで開く |

Git は GitHub が無くても動きます（Git基礎シリーズがまさにそうでした）。逆に GitHub は Git の保管庫を預かる場所なので、Git 無しでは意味を持ちません。「Git は道具、GitHub は場所」——この1行が持ち帰りの1つ目です。

置き場所であることに加えて、GitHub には**仲間と中身をやりとりする機能**も付いています。これはブランチ・PRコースで実際に使います。

## 社内GitHubと GitHub.com

「GitHub」と聞いて思い浮かべるのは、インターネット上の GitHub.com かもしれません。世界中のオープンソースが置かれている、あの場所です。

私たちが業務で使うのは、それとは**別に建てられた社内版の GitHub**です。このトレーニングでは**社内GitHub**と呼びます。イメージとしては、**同じ造りの保管庫が、社内の敷地の中と外に1つずつある**と思ってください。使うのは敷地の中のほうです。

社内GitHub は **GitHub Enterprise Server** という製品で、会社のサーバーの上で動いています。画面の見た目や操作は GitHub.com とほぼ同じですが、違いが3つあります。

| | GitHub.com | 社内GitHub |
|---|---|---|
| どこにあるか | インターネット上 | 社内のサーバー |
| 誰が見られるか | 世界中（公開リポジトリの場合） | 社内のアカウントを持つ人だけ |
| 向こうのリポジトリが見えるか | — | **GitHub.com の公開リポジトリは、社内GitHub からは見えない**（別の保管庫なので） |

3つ目が、最初につまずきやすい点です。Web の記事で見かける GitHub の話は、たいてい敷地の外のこと。**このシリーズの操作はすべて社内GitHub の上で行います。**

_出典: [GitHub Docs「GitHub Enterprise Server について」](https://docs.github.com/ja/enterprise-server@latest/admin/overview/about-github-enterprise-server)（2026年8月取得）_

社内GitHub の正式な名前と、どこから開くかは次のとおりです。

> **社内**: 社内GitHub の正式名称と開き方を書く。答えるべき問い —
>
> - 正式名称（本文の「社内GitHub」をどう読み替えればよいか）
> - URL、またはポータルでのリンク名
> - 社内ネットワークからだけ開けるのか、VPN が要るのか
>   形式: 箇条書き2〜3点 / 80〜150字

## 申請と費用——使う人・使わない人

社内GitHub を使うには、**アカウントの申請が必要**です。そして、1アカウントにつき**月に 16€ の費用**がかかります。「お金がかかるものを、自分の判断で申請してよいのか」——そう思うのは自然です。

答えは「**この先メインで使うツールなので、申請してください**」です。ツールを作り、仲間に渡し、レビューしてもらう——その置き場が社内GitHub になります。仕事道具の費用として扱われるものなので、迷う必要はありません。

ただし、**社内GitHub は業務で使わないが、DX ツールについて学んでおきたい**という人は、**上司と相談して決めてください**。このシリーズの手順は社内GitHub が無いと進められませんが、Git基礎シリーズの内容は社内GitHub 無しで学べます。申請しないと決めても、トレーニングから外れるわけではありません。

申請の手順は次のレッスンで扱います。窓口は Chocolatey や Git と同じ **IT Service Portal** です。

## 使うときの制約と困ったときの窓口

社内のシステムなので、使い方には約束があります。中身と、詰まったときの聞き先を押さえておきます。

> **社内**: 社内GitHub の利用上の制約と、サポート窓口を書く。答えるべき問い —
>
> - してはいけないこと（公開リポジトリを作ってよいか・外部に公開してはいけないもの・置いてはいけないデータの区分）
> - GitHub.com と違って使えない機能、または追加で使える機能（Copilot 等の付加機能の有無）
> - 詰まったときの問い合わせ先（管理者・チャンネル・チケットの出し方）と、利用ガイドラインの所在（リンク）
>   形式: 制約は表1つ（項目と可否）＋窓口は箇条書き1〜2点＋ガイドラインへのリンク1本 / 150〜300字

操作の分からないことは、これまでどおり Teams チャンネル **DX Tools Training** でも聞けます。上の窓口は「アカウントや権限など、システムそのものの困りごと」、チャンネルは「操作の分からないこと」と使い分けてください。

## やってみる

社内GitHub を実際に開いて、GitHub.com と違う点を1つ挙げてください。

- 前提: まだアカウントが無ければ、**サインイン画面まで**でかまいません。アカウント承認後にもう一度開いて、トップページの違いを見るのもよいです
- 考えなくてよいこと: 中の操作。開いて眺めるだけでよい
- 比べる相手: GitHub.com を開いたことが無ければ、ブラウザで `github.com` のトップページを開いて見比べる

## まとめ

このレッスンはコマンドを1つも打たず、地図を眺めるだけで終わりました。持ち帰るのは3つです。

1. **Git は道具、GitHub は場所。** GitHub は手元の保管庫のコピーを置く**共有保管庫**
2. 使うのは**社内GitHub**（GitHub Enterprise Server）。GitHub.com とは別の保管庫で、向こうのものは見えない
3. 社内GitHub は**申請制・月 16€**。この先メインで使うので申請する。使う予定が無い人は上司と相談して決める

次のレッスンで、実際に申請を出します。承認には日数がかかるので、読み終えたら続けてどうぞ。

## 確認問題

1. 「Git と GitHub は何が違うのか」を、**道具**と**場所**という言葉を使って、自分の言葉で1〜2文で説明してみてください。
2. Web の記事で見た GitHub.com 上のリポジトリを、社内GitHub で探しても見つかりません。なぜでしょうか。「保管庫」という言葉を使って説明してみてください。
