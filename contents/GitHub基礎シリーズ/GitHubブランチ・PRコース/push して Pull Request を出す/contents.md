# push して Pull Request を出す

## 学習目標

前のレッスンで作った別ルートは、まだ手元にしかありません。このレッスンのゴールは、**別ルートを共有保管庫へ送り、本編への合流を申し込む**ことです。この申し込みを **Pull Request**（略して **PR**）と呼びます。

一人で練習しますが、ここで作る PR は**ハンズオンで相方に見てもらうときの形そのもの**です。当日いきなりやるより、いま1本通しておくほうが確実に楽になります。

## ブランチを push する

`github-practice` フォルダを開き、**`add-greeting` ブランチにいる**ことを確認してください（VSCode の左下、または `git status` の1行目）。

前のレッスンの「やってみる」で、README に1行足してコミットしてあるはずです。まだなら、`README.md` の末尾に `- 別ルートで書いた行` を足して保存してから、次を打ってください。

```bash
git add README.md
git commit -m "別ルートで1行足した"
```

さて、送ります。ここで `git push` を打つと、**エラーが返ってきます**。

```text
fatal: The current branch add-greeting has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin add-greeting
```

（表示は要点だけ抜き出しています。実際にはこの下に、設定を変えれば省ける旨の案内が数行続きます。）

**これは失敗ではなく、案内です。** 共有保管庫にはまだ `add-greeting` というルートが無いので、「向こうにも作ってよいか、この命令で教えてくれ」と言っています。実際、**必要なコマンドがそのまま書いてあります**。

エラーが出たら、まずこうやって**メッセージを読む**——これは Git 全般に効く習慣です。読んでも分からなければ、そのままコピーして AI に貼ってください（AI基礎シリーズでやったとおりです）。

案内どおりに打ちます。短い書き方もあります。

```bash
git push -u origin add-greeting
```

`-u` は `--set-upstream` の短い形で、**「このルートは向こうのこのルートとつながっている」と覚えさせる**指定です。一度打てば、次からは `git push` だけで通ります。**新しいブランチの初回だけ** `-u` が要る、と覚えてください。

> [!NOTE]
> `origin` は「共有保管庫」を指す呼び名です。clone したときに自動で付けられました。自分で決める場面はしばらく来ないので、**そういう名前だと流してかまいません**。

## Pull Request を作る

push が終わったら、ブラウザで社内GitHub のリポジトリを開いてください。

ページの上のほうに、**「Compare & pull request」** という黄色っぽいバナーが出ています。いま送ったばかりのブランチを社内GitHub が検知して、「合流させますか」と聞いてくれている状態です。

1. **「Compare & pull request」** をクリックする
2. PR の作成画面が開く。上部に `main ← add-greeting` のような表示があり、**どのルートをどこへ合流させるか**が示されている
3. **タイトル**を書く（既定でコミットメッセージが入っている。分かりにくければ直す）
4. **説明欄**に何をしたかを書く（次の節で詳しく）
5. **「Create pull request」** をクリックする

> **社内画像**: 社内GitHub で PR を作るまでの流れ。①push 直後のリポジトリトップに出る「Compare & pull request」バナー ②PR 作成フォーム（タイトル・説明欄・Create pull request ボタンが見える画角） ③作成後の PR ページ。画面が変わるごとに1枚を目安に撮る。ユーザー名・組織名・URL のホスト部分・アバター画像はマスクする

バナーが出ていない場合は、リポジトリの **「Pull requests」** タブ →**「New pull request」** から、合流元のブランチを選んでも同じことができます。

> [!TIP]
> **Pull Request という名前は、いったん流してください。** 「向こうのルートを引き取ってほしい」という依頼から来た名前ですが、覚えても操作の役には立ちません。**「合流の申し込み」**とだけ思っておけば十分です。

_出典: [GitHub Docs「pull request について」](https://docs.github.com/ja/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests)（2026年8月取得）_

## PR 画面の見方

作成すると PR のページが開きます。タブがいくつか並びますが、**覚えるのは次の3つ**です（環境によっては Checks などが一緒に並びますが、いまは無視してかまいません）。

| タブ | 何が見えるか | いま見るべきか |
|---|---|---|
| **Conversation** | 説明文とコメントのやりとり | 相手とやりとりするとき |
| **Commits** | この PR に含まれるコミットの一覧 | ほとんど見ない |
| **Files changed** | **変更された行の差分**（`+` と `-`） | **ここを見る** |

**Files changed を開いてください。** 緑の `+` で、あなたが足した行が表示されています。Git基礎シリーズで `git diff` を読んだときと同じ、あの `+` と `-` です。今度はブラウザ上で、色付きで見えているだけです。

**PR の本体はこの画面**です。レビューする人も、ここを見て「合流させてよいか」を判断します。次のレッスンでは、この画面の行にコメントを付けます。

なお、PR を作っただけでは **`main` はまだ何も変わっていません**。申し込みが出ただけで、合流は次のレッスンです。

## 説明に何を書くか

説明欄は空でも PR は作れます。ただ、**読む人がいる前提では、「何を」と「なぜ」を1行ずつ書くだけで十分に役立ちます**。

```markdown
## 何をしたか
README に練習用の1行を追加した。

## なぜ
GitHub基礎シリーズの練習のため。
```

見出しの `##` は無くてもかまいません。要るのは**「何を」と「なぜ」の2つ**だけです。「何を」は Files changed を見れば分かるので短くてよく、**書く価値があるのは「なぜ」のほう**——差分を見ても分からないのはそこだからです。

ハンズオンでは、相方があなたの PR を読んでレビューします。そのとき、この2行があるかないかで相手の手間がまるで変わります。

## やってみる

自分のリポジトリで PR を1本作ります。

1. `add-greeting` ブランチにいることを確認する
2. `git push -u origin add-greeting` で共有保管庫へ送る
3. ブラウザで「Compare & pull request」から PR を作る（説明に「何を」「なぜ」を1行ずつ）
4. **Files changed** タブを開き、自分が足した行が緑の `+` で表示されていることを確認する

- 前提: `add-greeting` ブランチにコミットが1つ以上あること
- 考えなくてよいこと: Reviewers・Assignees・Labels の設定。すべて空のままでよい（レビューは次のレッスンで扱う）

## まとめ

このレッスンで増えた操作は、`push -u` と PR の作成です。持ち帰りは3つです。

1. **新しいブランチの初回 push だけ `-u` が要る。** エラーメッセージに正解のコマンドが書いてある
2. **PR は「合流の申し込み」。** push した後のバナーから作れる
3. **見るべきは Files changed タブ。** レビューする人もここを見る

申し込みは出ました。次のレッスンでは、それを**確認して、合流させます**。ぶつかったときの直し方も、そこで扱います。

## 確認問題

1. PR を作った時点では、まだ本編（`main`）に変更は入っていません。では PR は何をした状態なのでしょうか。「申し込み」という言葉を使って1文で説明してみてください。
2. `git push` でエラーが出たとき、あなたは最初に何をしますか。このレッスンで実際にやったことを踏まえて答えてみてください。
