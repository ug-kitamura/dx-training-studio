# レビューとマージ・コンフリクト解消

## 学習目標

申し込み（PR）は出ました。あとは、**中身を確認して、合流させる**だけです。このレッスンのゴールは3つ——**PR の行にコメントを付けられること**、**マージして本編に合流させられること**、そして**衝突（コンフリクト）が起きたときに直せること**です。

ここはハンズオンの当日手順そのものです。当日は、あなたの PR を相方が見て、相方の PR をあなたが見ます。**その練習を、いま一人で通します。**

## レビューする——行にコメントを付ける

ブラウザで、前のレッスンで作った PR を開いてください。**Files changed** タブに移ります。

行の左端にマウスを乗せると、**青い「＋」ボタン**が出ます。これがコメントの入口です。

1. コメントを付けたい行の左端の **「＋」** をクリックする
2. 入力欄が開くので、コメントを書く（例: `この行の書き方をそろえたい`）
3. **「Add single comment」** をクリックする

これで、**その行に紐づいたコメント**が付きます。ファイル名や行番号を言葉で説明する必要がないのが、この仕組みの利点です。

コメントをまとめて出すときは、右上の **「Review changes」** から3つのうち1つを選びます。

| 選択肢 | 意味 | いつ使うか |
|---|---|---|
| **Comment** | 感想・質問を伝える。可否は判断しない | 聞きたいことがあるとき |
| **Approve** | 「合流させてよい」と承認する | 中身を見て問題ないとき |
| **Request changes** | 直してほしい点がある | 修正が必要なとき |

> [!IMPORTANT]
> **自分の PR に Approve は付けられません。** GitHub の仕様で、自分自身の申し込みを自分で承認することはできないためです。いま一人で練習しているので、選べるのは **Comment** だけです。**Approve を使うのはハンズオンで相方の PR を見るとき**——そのときは、この同じ画面で Approve を選びます。

> **社内画像**: 社内GitHub の PR で、レビューからマージまでの一連の操作の短い画面録画（10秒以内が目安）。①Files changed で行の「＋」からコメントを付ける ②Review changes を開いて Approve を選び送信する ③Conversation タブに戻って Merge pull request → Confirm merge を押す、までを続けて撮る。**Approve は自分の PR には出せないため、撮影は2つのアカウント（レビュアー役と作成者役）が必要**。ユーザー名・組織名・URL のホスト部分・アバター画像はマスクする

## マージする

確認が済んだら、合流させます。PR の **Conversation** タブに戻ってください。

1. **「Merge pull request」** をクリックする
2. 確認のボタン **「Confirm merge」** をクリックする
3. 画面が紫色の「Merged」表示に変わる
4. **「Delete branch」** ボタンが出るので、押してブランチを片づける

手順4は必須ではありませんが、**押しておくのが普通**です。合流が済んだ別ルートは役目を終えているので、残すと一覧が散らかります。消しても、合流した中身は本編に入っているので失われません。

さて、本編（`main`）は共有保管庫の側で更新されました。**手元はまだ古いまま**です。取り込みます。

```bash
git switch main
git pull
```

`README.md` を開くと、別ルートで書いた行が本編に入っています。1周まわって戻ってきました。

```text
  main（本編）  ──●───●───────────●──▶  ← いまここを pull した
                      \          /
  add-greeting        ●───●─────┘
                              （合流済み。ブランチは削除してよい）
```

**マージした後は手元で `git pull`。** これも習慣にしてください。忘れると、次のブランチを古い本編から切ってしまいます。

## 衝突したらどうなるか

ここからが、このシリーズで唯一「怖い」と言われる話です。先に結論を言います。**コンフリクトが起きてもデータは壊れません。** Git が勝手に決められないので、人に「どちらを採るか」を聞いてきているだけです。

起きるのは、**同じファイルの同じあたりを、2つのルートで別々に書き換えたとき**です。離れた行なら、Git が自動で両方を取り込みます。違うファイルなら、なおさら何も起きません。

> [!NOTE]
> 厳密には、すぐ隣の行を触った場合やファイルごと消した場合にもぶつかることがあります。ただ、**最初は「同じあたりを二人が触ったとき」と覚えておけば十分**です。

衝突すると、ファイルの中がこうなります。

```text
<<<<<<< HEAD
- 別ルートで書き換えた
=======
- 本編で書き換えた
>>>>>>> 4e5f6a7
```

読み方は3行だけ覚えれば足ります。

| 記号 | 意味 |
|---|---|
| `<<<<<<< HEAD` から `=======` まで | **いま自分がいるルート**の中身 |
| `=======` から `>>>>>>>` まで | **これから取り込もうとしている側**の中身 |

`>>>>>>>` の右に出るのは、取り込む側の目印（ブランチ名かコミットの ID）です。**どちらが上に来るかは、どのルートで作業しているかで変わります。** 上下の位置ではなく、`HEAD` が付いているほうが自分の側、と覚えてください。

やることは、**どちらを残すか（あるいは両方をどう混ぜるか）を決めて、記号の行を消す**ことです。`<<<<<<<` `=======` `>>>>>>>` の3行は目印なので、**最後には1つも残っていない**のが正しい状態です。

VSCode なら、この作業がボタンでできます。衝突したファイルを開くと、記号の上に選択肢が出ます。

| ボタン | 何が残るか |
|---|---|
| **Accept Current Change** | `HEAD` 側（いま自分がいるルート）だけ |
| **Accept Incoming Change** | 取り込もうとしている側だけ |
| **Accept Both Changes** | 両方（順に並ぶ） |

押すと記号ごと消えて、選んだ中身だけが残ります。

_出典: [VS Code Docs「Resolve merge conflicts」](https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts)（2026年8月取得）_

直した後は、いつもどおりです。

```bash
git add README.md
git commit -m "コンフリクトを解消した"
git push
```

これで PR の画面から衝突の表示が消え、マージできるようになります。

> **1回の説明で腑に落ちなくて当然です。** 実際にぶつかったときに、この節へ戻ってきてください。画面をそのまま AI に貼って「これは何ですか」と聞くのも有効です——エラー文と同じ扱いでかまいません。

## やってみる

自分の PR にコメントしてマージします。

1. PR の **Files changed** で、自分が足した行に **「＋」** からコメントを1つ付ける
2. **Conversation** タブに戻り、**「Merge pull request」→「Confirm merge」**
3. **「Delete branch」** でブランチを片づける
4. 手元で `git switch main` → `git pull` して、本編に反映されたことを確認する

- 前提: 前のレッスンで作った PR が Open のまま残っていること
- 考えなくてよいこと: コメントの内容（`練習用のコメントです` でよい）。Approve は自分の PR には出せないので試さなくてよい

手順4の後、`main` の `README.md` に別ルートで書いた行が入っていれば成功。

## まとめ

このレッスンの持ち帰りは3つ。

1. **レビューは行にコメントを付ける。** まとめて出すときは Review changes（Comment / Approve / Request changes）
2. **マージしたら、手元で `git pull`。** 本編を最新にしてから次のブランチを切る
3. **コンフリクトは壊れていない。** 同じあたりを2つのルートで変えたときに起きる。記号を消して、どちらを残すか人が決める

リポジトリを作り、clone し、push して、ブランチを切り、PR を出し、コメントして、マージする。**GitHub の一周を、あなたはもう自分の手で回しました。** 一人で回したこの輪は、そのまま二人で回せます——相手が増えるだけで、操作は1つも増えません。

ハンズオンでは、ペアの相方をリポジトリに招き、お互いの PR を見てコメントし、承認してマージします。**唯一まだ試していない Approve のボタン**も、そのとき初めて押すことになります。今日1本 PR を出しておいたおかげで、当日は手順ではなく中身に集中できるはずです。

## 確認問題

1. コンフリクトが起きるのは、どんなときでしょうか。「同じ」という言葉を2回使って1文で説明してみてください。（`<<<<<<< HEAD` が付くのはどちら側かも、あわせて答えてみてください）
2. マージした後に手元で `git pull` をするのはなぜでしょうか。「共有保管庫」と「手元」という言葉を使って説明してみてください。
