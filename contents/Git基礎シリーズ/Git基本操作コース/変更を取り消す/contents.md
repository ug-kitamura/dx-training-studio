# 変更を取り消す

## 学習目標

いよいよ、このシリーズ最後のレッスンです。シリーズ最初のレッスンで「バージョン管理があると安心して変えられる」と学びました。このレッスンでは、その安心を**自分の手で確かめます**。ゴールは、**コミット前の変更を安全に戻せる**ようになること。7つの操作の最後の1つ、`restore` の出番です。

わざとファイルを壊して、元に戻します。「壊すのが怖い」と感じるかもしれませんが、その怖さを消すのがこのレッスンの目的です。

## 「戻したい」には種類がある

ひとくちに「戻したい」と言っても、場面は2つあります。

<!--
「戻したい」の2場面を左右比較のカード2枚で。左のカード「編集をなかったことにしたい」：ファイルをぐちゃぐちゃに編集してしまった状態から、直前のセーブの状態に戻る矢印、コマンドラベル git restore。右のカード「セーブに含める選択から外したい」：ステージに載ったファイルが作業ツリーに降りるだけの矢印、編集内容はそのまま、コマンドラベル git restore --staged
-->
![git restoreの2つの使い分けを左右比較](images/git-restore-two-cases.png)

| 場面                           | 何をするか                             | コマンド               |
| ------------------------------ | -------------------------------------- | ---------------------- |
| **編集をなかったことにしたい** | 直前のセーブからロードしてやり直す     | `git restore`          |
| **add を取り消したい**         | セーブの選択から外す（編集内容は残る） | `git restore --staged` |

どちらも `restore` でできます。この2つだけ押さえれば十分です。

なお、**コミット済みの内容を取り消す**（セーブ自体をやり直す）方法もありますが、このシリーズでは扱いません。必要になったら、状況を社内AIチャットに貼って聞いてください——「git コミットを取り消したい」と聞けば道具の名前を教えてくれます。

## 直前のセーブからロードする

ファイルの編集を全部なかったことにして、直前のセーブの状態に戻すには:

```bash
git restore memo.txt
```

これでファイルの中身が、最後にコミットしたときの状態に巻き戻ります。ゲームで言えば、**プレイをやめて直前のセーブからロードし直す**操作です。（厳密には、add 済みの変更が残っている場合は「add した時点」に戻りますが、最初の理解は「直前のセーブに戻る」で十分です）

_出典: [git-restore 公式ドキュメント](https://git-scm.com/docs/git-restore)（2026年8月取得）_

> [!CAUTION]
> **restore で消した編集は、元に戻せません。** 7つの操作の中で唯一、結果を取り消せないコマンドです。実行する前に `git status` で「何が消えるのか」を確認する癖をつけてください。

セーブしていないプレイがロードで消えるのと同じです。裏返せば、**こまめにコミットしてあるほど、restore は安全な道具になる**ということです。確認の癖さえついていれば、怖い操作ではありません。

ちなみに、取り消しの方法を検索すると `git checkout` や `git reset` を使う古い記事がよく出てきます。`restore` は取り消し専用に後から作られた新しいコマンドで、**いまはこれだけ覚えれば十分**です。古い記事のコマンドを無理に読み解く必要はありません。

## セーブの選択から外す

もう1つの場面。`git add` した後で「これは今回のセーブに含めるつもりじゃなかった」と気づいたときは:

```bash
git restore --staged memo.txt
```

これは**ステージから降ろすだけ**です。ファイルの編集内容には一切触れません——三大エリアの地図で言えば、変更がステージから作業ツリーに戻るだけ。消えるものは何もないので、こちらは安心して打てるコマンドです。

「選ぶ段（ステージ）がある」ことは Git概念コースで学び、前のレッスンで add として使い、いままた「選び直す」形で登場しました。3回目のいま、だいぶ手に馴染んできたはずです。

## VSCode ではこう見える

ソース管理ビューの変更ファイルの横にある**「変更を破棄」（くるっと戻る矢印のアイコン）**が `git restore` に対応します。押す前に確認ダイアログが出るのはコマンドと違う点で、VSCode なりの安全装置です。add の取り消し（`--staged` 相当）は、ステージ済みファイルの横の「−」ボタンです。

## やってみる

わざと壊して、restore で戻します。

1. 練習リポジトリの `memo.txt` を開き、**中身を全部消して**保存する（思い切って！）
2. `git status` で `memo.txt` が変更ありになっていることを確認する
3. `git restore memo.txt` を打つ
4. VSCode で `memo.txt` を見て、中身が元に戻っていることを確認する

- 前提: これまでの練習リポジトリ（`memo.txt` がコミット済み）
- 考えなくてよいこと: 壊し方。全部消す以外に、適当な文字を書き散らしてもよい

## まとめ

戻し方は2種類、これで7つの操作がそろいました。

1. `git restore ファイル名` — 編集をなかったことにして、直前のセーブからロード（**消した編集は戻らない**、唯一の注意コマンド）
2. `git restore --staged ファイル名` — セーブの選択から外すだけ。編集は無傷

`init`・`status`・`add`・`commit`・`log`・`diff`・`restore`——シリーズ最初のレッスンで約束した7つを、すべて自分の手で打ちました。お疲れさまでした。**Git基礎シリーズは、これでクリアです。**「自分の作業をいつでもセーブして、安全に元へ戻せる」——最初のレッスンで予告した武器は、もうあなたの手の中にあります。

曼陀羅では、次のクエストとして **GitHub基礎シリーズ**が解放されました。リポジトリをチームで共有し、ブランチを使って協力する方法は、そちらで扱います。

## 確認問題

1. `git restore` で戻せるのは「どこまで」の変更でしょうか。「セーブ」という言葉を使って1文で説明してみてください。
2. `git restore` と `git restore --staged` の違いを、「消えるもの」に注目してそれぞれ1文で言い換えてみてください。
