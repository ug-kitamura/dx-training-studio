# Gitの三大エリア

## 学習目標

概念コースも、この回で仕上げです。前のレッスンで、バージョン管理があると「いつでも戻れる・記録が残る・安心して変えられる」と学びました。このレッスンでは、Git がそれを実現している**3つの場所（三大エリア）**を地図として手に入れます。

コマンドはまだ打ちません。先に地図を持っておくと、次のコースで実際に操作したとき「いま自分がどこにいて、何をしたのか」が分かるようになります。逆にここを飛ばすと、コマンドは打てるのに何が起きたか分からない、という状態になります。急がば回れの回です。

## Git が保存しているのは「セーブデータ」

まず、Git が何を記録しているのかを1つだけ押さえます。Git がセーブのたびに残すのは、**その瞬間のフォルダ全体の状態**です。「前回からの変更点のメモ」ではなく、フォルダまるごとのセーブデータが毎回残る、とイメージしてください。だからどの時点にもロードし直せるわけです。（「毎回まるごとで容量は大丈夫？」と思った人へ——Git は内部で賢く節約しているので大丈夫です。その仕組みは知らなくてかまいません）

_出典: [Pro Git 日本語版「使い始める - Gitの基本」](https://git-scm.com/book/ja/v2/%E4%BD%BF%E3%81%84%E5%A7%8B%E3%82%81%E3%82%8B-Git%E3%81%AE%E5%9F%BA%E6%9C%AC)（2026年8月取得）_

この「1回分のセーブデータ」を、Git では**コミット**と呼びます。このシリーズで何十回も出てくる、いちばん大事な言葉です。**コミット＝セーブする（セーブデータを1つ作る）**、この対応だけ覚えてください。

## ３つの場所を地図にする

では、ファイルを編集してからセーブ（コミット）されるまで、変更はどこを通るのか。Git には3つの場所があります。

<!--
Git の三大エリアを左から右への3ステップフロー図で。左「作業ツリー：いま編集しているフォルダの中身」→中央「ステージ：セーブに含める変更を選んで置く場所」→右「リポジトリ：セーブデータ（コミット）がたまる保管庫」。左から中央への矢印に「git add」、中央から右への矢印に「git commit」のラベル。カードを3枚横に並べたシンプルな構成
-->
![作業ツリー・ステージ・リポジトリの3ステップ図](images/git-three-areas-flow.png)

| エリア         | どういう場所か                                                                   | 次へ移す操作            |
| -------------- | -------------------------------------------------------------------------------- | ----------------------- |
| **作業ツリー** | いま自分が編集しているフォルダの中身そのもの（ゲームで言えば**プレイ中の状態**） | `git add` で載せる      |
| **ステージ**   | セーブに含める変更を**選んで置いておく**場所                                     | `git commit` で記録する |
| **リポジトリ** | セーブデータ（コミット）が**たまっていく保管庫**                                 | —                       |

2点だけ補足します。作業ツリーは Ctrl+S で保存しても、**まだ Git には記録されていません**。リポジトリの実体はフォルダ内の `.git` という隠しフォルダで、中を触ることはありません。

図の細部より、**左から右へ「編集 → 選ぶ → セーブ」の一方通行**という流れだけ見てください。前のレッスンの「ファイルは1つのまま、裏に記録が積み重なる」の答えがこれです——積み重なる先がリポジトリです。

この3つの名前は、このシリーズの土台なので覚えてください。なお、調べものをすると、ステージのことを「ステージングエリア」や「インデックス」、作業ツリーのことを「ワーキングツリー」や「作業ディレクトリ」と呼ぶ記事もありますが、それぞれ同じものです。呼び名の違いは覚えなくてかまいません。

## なぜセーブの前に「選ぶ」段があるのか

ここで、こう思いませんでしたか。「ただセーブしたいだけなのに、なぜいちいち選ぶ段を挟むのか。二度手間では？」——もっともな疑問です。実際、**ゲームのセーブには『選ぶ』に当たる段はありません**。ここがたとえの効かない、Git 独自の部分です。初めて Git を学ぶ人が最初につまずくのも、だいたいここです。

選ぶ段がある理由は、**1回のセーブを意味のあるまとまりにするため**です。たとえば、誤字の修正と、新しい機能の追加を同時に作業していたとします。全部まとめて1つのセーブにしてしまうと、後から記録を見ても「何のセーブか」が言えません。ステージがあると、「今回は誤字修正だけをセーブに含める」という選び方ができます。

とはいえ、この便利さは実際に使い込むまで実感できなくて普通です。いまは「**セーブの前に、含める変更を選ぶ段が1つある**」——これだけ持ち帰れば十分です。Git基本操作コースで手を動かすとき、この段は `git add` という1コマンドで通過できます。

## 画面ではどう見えるのか

この地図は、頭の中だけのものではありません。Git基本操作コースで使う `git status` というコマンドは、**作業ツリーとステージにいま何があるか**をこういう形で答えてくれます（実際の画面にはもう少し行がありますが、ここでは要点だけ抜き出しています）。

```text
Changes to be committed:        ← ステージに載っている変更
        modified:   report.md

Changes not staged for commit:  ← 作業ツリーだけにある変更
        modified:   memo.md
```

では3つ目のリポジトリはどこに出るのか——**出ません**。すでにセーブ済みで変化していないファイルは、`git status` には表示されないのです。「表示されない＝リポジトリのセーブと同じ状態」という読み方を、Git基本操作コースで実際に確かめます。

`Changes to be committed` は「セーブに含めることが決まった変更」、`Changes not staged for commit` は「まだ選ばれていない変更」という意味です。「`git status` の表示は三大エリアの地図に対応している」——それが分かっていれば、実際に打つときに迷いません。

## やってみる

下の図の (A)〜(C) に、エリア名（作業ツリー／ステージ／リポジトリ）を当てはめてください。

```text
   ┌───────────────┐  git add   ┌───────────────┐  git commit  ┌───────────────┐
   │      (A)      │ ─────────→ │      (B)      │ ───────────→ │      (C)      │
   │ ファイルを     │            │ セーブに含める │              │ セーブデータが │
   │ 編集する場所   │            │ 変更を選ぶ場所 │              │ たまる保管庫   │
   └───────────────┘            └───────────────┘              └───────────────┘
```

- 前提: この図は上の本文の図と同じ流れ
- 考えなくてよいこと: コマンドの綴りや打ち方（Git基本操作コースで扱います）

<details>
<summary>解答例</summary>

(A) 作業ツリー、(B) ステージ、(C) リポジトリ。

</details>

## まとめ

持ち帰るのは**3つの場所と1つの流れ**です。

1. **作業ツリー** — 編集する場所（プレイ中の状態）
2. **ステージ** — セーブに含める変更を選ぶ場所（ゲームにはない Git 独自の段）
3. **リポジトリ** — セーブデータ（コミット）がたまる保管庫
4. 流れは常に **編集 → add で選ぶ → commit でセーブ**

次のコースでは Git をインストールし、その次のコースでこの地図の上をコマンドで歩きます。地図は手に入りました——概念コース、クリアです。

## 確認問題

1. ファイルを編集して Ctrl+S で保存した直後、その変更は三大エリアのどこにありますか。また、まだどこには無いでしょうか。
2. 「セーブの前に選ぶ段がある」ことの利点を、自分の言葉で1文にしてみてください。
