| git 操作 | ユーザーが別ツールで主導（スキル・agent 側は関知しない） |

### 2. スペック記録機構は作らない【Q4】（A4）

| 担い手 | 内容 |
|--------|------|
| `references/`（design-principles.md / lesson-template.md） | 明文化できる**規則**（命名・対象者前提・表・リンク形式 等） |

### 3. 実行単位はコース既定【Q5】（A5）

| 単位 | 扱い |
|------|------|
| コース | **既定**（1 コース≈15 分。承認ゲート・レビュー採否に人が付き合える上限） |
| レッスン | 可（追加・書き直し用） |
| シリーズ | 可だが**時間警告付き** |
| 複数シリーズ一括 | やらない |

付帯: コース単位化で用語・たとえの一貫性が run をまたぐため、**同シリーズの過去 run の設計メモから用語表・たとえ体系を引き継ぐ手順**をスキルに追加する。

### 4. 命名規則は dx-training-plan 側に置く【Q6】（A1）

| 規則 | 強度 |
|------|------|
| 名前にキャッチーさを加える | 方針 |
| シリーズ名は「〜シリーズ」で終える | 必須 |
| コース名は「〜コース」で終える | 必須 |
| レッスン名に「〜レッスン」は付けない | 必須 |
| 題材名（Git 等）をシリーズ名に含める | 必須 |
| 題材名をコース名に含める | 推奨 |
| レッスン名は自由 | 現状どおり |

- 名前の出典は計画書第 5・6 章なので、規則は**構成を決める plan スキル**が持つ。create は従来どおり計画書に従うだけ（変更なし）
- **既存計画書は「名前だけ」の限定更新**を次回実行前に行う（ハンドオフで対象外の「計画書の再修正」＝構成の作り直しとは別と整理）
- 既存 Git シリーズのリネームは原稿更新パスで対応

### 5. author と status【Q7】（A2・A3）

| 項目 | 決定内容 |
|------|----------|
| `author` | run の最初（フェーズ1・計画書選択時）に **1 回だけ**ユーザーに確認し、全レッスンに適用 |
| `status` | テンプレート規則を「草稿は `open`」→「**執筆時点から `in_progress`**」に変更（完成時切替の中間状態管理はしない） |

スキーマ変更は不要（`lib/schema.ts` に両フィールド既存）。lesson-template.md の「値の選び方」の書き換えだけ。

### 6. 注釈＝GitHub アラートと整理【Q8】（B4 = C6）

- B4「注釈を積極的に使ってよい」は C6 の GitHub アラート（`[!NOTE]` 青 / `[!TIP]` 緑 / `[!IMPORTANT]` 紫 / `[!WARNING]` 黄 / `[!CAUTION]` 赤）と同一の要望に統合
- 脚注（`[^1]`）ではない（必要になれば remark-gfm が既に対応済み）

### 7. Studio プレビュー改修は 5 件を 1 change に束ねる【Q9】（C1・C2・C4・C6・C7）

| # | 内容 | 実現手段の目安 |
|---|------|----------------|
| C1 | `<details>` / `<summary>` 対応 | rehype-raw 追加 |
| C2 | `**…（…）**を` が太字にならない CJK バグ | remark-cjk-friendly 系プラグイン（要実地検証） |
| C4 | アスキーアートの横幅ズレ | コードブロックに CJK 等幅フォント指定 |
| C6 | GitHub アラート 5 種の色付き表示 | rehype-github-alerts 等 |
| C7 | git コマンド・diff の色分け（削除=赤 / 追加=緑） | rehype-highlight の言語登録＋ CSS（`.hljs-addition` 等） |

- 全件が同じプレビューパイプライン（プラグイン構成＋ CSS）に集中するため 1 change（例: `enhance-lesson-preview-markdown`）で最先行
- スキル側の記法推奨ルール（アラート・diff フェンス）は**この change のマージ後**に追記（「プレビューで見えない記法を推奨する」矛盾期間を作らない）

### 8. AI 画像は事前判定なし・AI 先行＋注意書き常付与【Q10】（C5）

| 項目 | 決定内容 |
|------|----------|
| 実画面系スロット（VSCode・GitHub 等） | 常に **AI（Tailwind mock）先行**。事前の難易度判定はしない |
| 注意書き | スキルが書くプロンプトコメントに定型 1 行を常に含める（例: 「実際の画面との一致が重要な図。生成品質が悪ければスクリーンショットで代用すること」） |
| Studio 側の変更 | **不要**（lesson-template.md への規則追記のみ） |

根拠: 生成はペイン4 で人が回す操作なので品質判定は生成直後に人ができ、事前判定の価値が小さい。

### 9. 社内コンテキストは 3 段フォールバックで参照【Q11・Q12】（D1）

**方針転換**: 家/会社の分業を開発前提にしない。ゆくゆくは社内だけで完結し、多くの人にスタジオとして使ってもらう。各スキルは Claude Code / Cursor でも単体で動くことを維持する。

| 段 | 参照先 | 補足 |
|----|--------|------|
| 1 | **社内コンテキスト DB** | ペイン4: 既存の `search-company-context` ツール / Claude Code: `local-db/context-items.json` 直読み |
| 2 | DB にアクセスできない場合、**ユーザーに提出を依頼** | Cursor / Claude Code 単体実行など |
| 3 | 提出できない場合、**穴**として設計 | 家での実行は従来どおりここへ自然降格 |

- 解決タイミングは**設計メモ段階で一括**: 社内データが要る箇所を全列挙 → DB 検索 → 不足分をまとめてユーザーに問合せ → 残りを穴として設計。承認ゲート前に完了させ、執筆中の都度質問はしない
- 穴埋めスキル（社内側の埋め作業フロー）は引き続き別系統

### 10. 確認問題に答えは付けない【Q13】（D2）

- 「**確認問題は本文を読み返せば答えが確認できる形に限る**」を lesson-template.md に明文化（担保ルール）
- 本文に戻って確かめる行為自体に学習効果がある。書かれていないルールは崩れうる（今回のレッスン番号参照の実例と同じ構図）ため規則化する
