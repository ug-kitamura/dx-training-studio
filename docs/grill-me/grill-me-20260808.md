### 4. 公開サイトのフレームワーク選定 ★最も議論した点

**結論: 第一候補 Nextra 4 / 第二候補 Astro + Starlight**

#### 4-1. 前提の整理（議論の途中で判明し、判断を単純にしたこと）

- **GitHub Pages は静的ホスティング。どのフレームワークを選んでも Pages 側ではサーバーランタイムを持てない。** 「Next.js ベースであること」の価値は Vercel 側でしか効かない
- **ゲーミフィケーション（ログイン・トロフィー・ランキング）は、静的サイトでも作れる。** Supabase 等の BaaS をブラウザから直叩きすればよい。サーバーが本当に要るのは「APIキーを隠す」「サーバー側で集計・不正防止」だけ
- **必達ラインまでの工数の大半はフレームワーク非依存。** `contents/` の走査・slug 決め・ファイル変換が主工数で、ここはどれを選んでも同じ（→ 7章）
- **Vue Flow は React では動かない。** Studio は React なので React Flow（`@xyflow/react`）に置き換える。xyflow という同じチームの同じライブラリの React 版

|---|---|---|---|---|---|---|---|---|---|
| **Nextra 4** | ○ | ◎ | ◎ 完全共有 | ◎ | ○ export要 | ◎ | ◎ 最も素直 | ○ | ◎ Tailwind v4 |
| **Astro + Starlight** | ○ | ◎ | ◎ | ◎ Pagefind | ◎ | ◎ | ◎ アダプタでAPI可 | ◎ | ◎ 端正 |
| Fumadocs | ○ | ◎ | ◎ 完全共有 | ◎ | ○ export要 | ◎ | ◎ | ○ | ◎ shadcn そのもの |
| Docusaurus | ○ | ◎ | ◎ | ◎／○ | ◎ | ◎ | ○ 静的専用 | ◎◎ 最強 | △ 素だと古い |
| VitePress | ○ | ○ Vue Flow | **△ コード2本** | ◎ | ◎ | ◎ | ○ Vueで書く | ◎ | ○ 既視感 |

**「1. Studio から変換」は全選択肢で可能なので差にならない。** Studio は既に `child_process` で git を叩いている（`lib/lesson-git-diff.ts:3`）ため、同じ仕組みで各フレームワークの CLI を呼べる。

**差がつくのは 2・3・7・8・9 と、後述のドキュメント機能。** とくに **3（Studio と曼陀羅のコードを共有できるか）が選択肢をきれいに割る**。React 系は共有でき、Vue（VitePress）と Python（MkDocs）は共有できない。

| Mermaid | ◎ | ○ | ◎ 内蔵 | ○ | △ プラグイン |
| バージョニング | **◎◎ 唯一の標準機能** | △ 非公式 | ✗ | ✗ | ✗ |

**教材で効く機能／効かない機能**

- **効く**: Tabs（Git インストール手順の Windows / Mac 分岐で確実に要る）、コードブロックの質（Git・Python は端末出力が大量）、Steps、FileTree、検索・サイドバー・前後ナビ
- **効かない**: **バージョニング**（Docusaurus 唯一の独占機能だが、教材には不要。ソフトウェアの API ドキュメント向け）、ブログ

→ **Docusaurus は「機能が一番多い」が、多い分がまるごと用途の外側。ここで落選。**

**唯一の実質的な差は Expressive Code（Starlight のコードブロック品質）。** ただしこれには `rehype-expressive-code` という remark/rehype 統合があり、**Nextra にも後から差し込める。**

> **構造上の重要点**: remark / rehype 系（Nextra・Fumadocs・Docusaurus・Starlight）は、足りない機能を既存プラグインで足せる。VitePress は markdown-it で生態系が別なので、この資産を一切流用できない。**天井の高さが違う。**

#### 4-4. Nextra 4 を第一候補にした理由

| 決め手 | 内容 |
|---|---|
| Next.js 16 対応 | **確認済み**。唯一の懸念が解消した |
| 新しく覚えるもの | **ほぼゼロ**。Studio と同じ Next.js 16 + React 19 + Tailwind |
| 曼陀羅 | Studio の React Flow コンポーネントを**文字通り同じコードで**共有できる |
| 言語切り替え | 2言語＋トグルなら `output: 'export'` の制約に当たらない（→ 6章） |
| デザイン | Tailwind v4 ベースで素の状態から洗練されている |
| ゲーミフィケーション | Vercel 側は通常ビルドなので Route Handlers がそのまま使える。最も素直 |
| 機能の天井 | remark/rehype なので、足りない機能はプラグインで足せる |

#### 4-5. Starlight を第二候補に残す理由

- **静的サイトがデフォルトなので、Pages と Vercel で機能差が生まれない。** Next.js 系は「Vercel では全部動くが Pages では削れる」という二層構造を頭に置き続けることになる
- 全文検索が Pagefind で内蔵。サイドバーが `autogenerate` でディレクトリ構造から自動生成できる
- Expressive Code が標準。コードブロックの初期完成度が最も高い
- Vercel アダプタを足せばサーバー API も持てる（`prerender = false` を付けたファイルだけサーバー実行）
- 代償は **Astro という新しいフレームワークの学習コスト**。残り1ヶ月ではここが効いて第二候補にした

**Nextra で詰まったら Starlight に切り替える。** どちらも remark/rehype 系・React 使用可なので、変換スクリプト（7章）はほぼそのまま流用できる。

#### 4-6. デプロイ構成（変わらず）

```
公開用ベース（Nextra 4 + React Flow）
├─ output:'export' + basePath  → GitHub Pages（サブパス配信）
└─ 通常ビルド                   → Vercel（ルート配信・サーバーランタイムを残す）
```

- Vercel 側は静的 export にしない。ゲーミフィケーション追加が構成変更なしで済む
- `basePath` は環境変数で切り替える
- React Flow は `"use client"` か `dynamic(..., { ssr: false })` で読み込む
- **GitHub Pages の落とし穴**: Jekyll が `_` 始まりのディレクトリを無視するため、`out/.nojekyll` を置かないと `_next/` の JS・CSS が全部 404 になる
- `images: { unoptimized: true }` も必要（画像最適化はサーバーが要るため）

### 5. markdown → HTML の変換（タイミングと技術）

**Studio は markdown を HTML に変換しない。** Studio がやるのは `.md` を書くところまで。

```
[ローカル]                    [GitHub]                   [公開]
Studio (Next.js)              リポジトリ
 └ CodeMirror で編集     →    contents/**/*.md    →   Actions が起動
 └ react-markdown で             (markdown のまま)       └ 公開サイトを build
   プレビュー                                              └ ここで md → HTML
   ※画面上だけ。                                        out/**/*.html
     HTMLファイルは出ない                                      ↓
                                                        Pages / Vercel
```

| タイミング | 変換される？ |
|---|---|
| Studio で保存した瞬間 | されない。`contents.md` が書かれるだけ |
| Studio のプレビュー表示 | 画面上だけ React 要素として描画。ファイルは残らない |
| **`git push` → Actions のビルド中** | **ここで HTML になる** |
| 閲覧者がページを開いた瞬間 | されない。もう HTML になっている |

**変換パイプライン（remark / rehype）**

```
contents.md
  ↓ fs.readFile          ファイルを読む
  ↓ gray-matter          フロントマターと本文を分離
  ↓ remark-parse         markdown → mdast
  ↓ remark-gfm           表・打ち消し線・チェックボックス
  ↓ remark-rehype        mdast → hast
  ↓ rehype-highlight     コードブロックの色付け
  ↓ rehype-stringify/JSX HTML 文字列 or React 要素
  ↓ next build           各レッスンを静的 HTML にプリレンダ
out/git/branch/index.html
```

**Studio と同系統であることの効き目**: Studio のプレビューが使う `react-markdown` は中身が remark/rehype（`package.json:48-50` に `react-markdown` `remark-gfm` `rehype-highlight`）。**同じプラグイン設定を共有できるので、プレビューと本番の見た目が一致する。** VitePress（markdown-it）だとここが別実装になり「プレビューでは崩れないのに公開すると崩れる」が起きる。

**注意**: Mermaid と React Flow の曼陀羅はビルド時に HTML にならない。どちらもブラウザ上で描画するため、`"use client"` でハイドレーション後に描かれる。静的 HTML に焼き込みたい場合は、ビルド時に Mermaid CLI で SVG 化する工程を足す必要がある。**最初は client-side 描画で問題ない。**

### 6. 多言語対応（日本語・英語）

| 項目 | 決定内容 |
|---|---|
| **対象言語** | **日本語と英語の2つだけ** |
| **切り替え方法** | 画面のトグルボタン。ブラウザ言語による自動振り分けはしない |
| **URL 構造** | 日本語をルート、英語をサブツリー |

```
/git/branch          ← 日本語（既定・ルート）
/en/git/branch       ← 英語
```

**この構造にする理由**: Next.js の i18n は本来ロケール判定とリダイレクトに middleware を使うが、**`output: 'export'`（Pages 向けビルド）では middleware が動かない。** しかし日本語をルートに置けばリダイレクトが1回も発生せず、トグルボタンは現在のパスに `/en` を足す・外すだけになる。**export でも完全に動く。**

middleware が要るのは「多言語をブラウザ設定から推測したい」ケースであり、2言語＋明示トグルという要件はそこに当たらない。**これにより Nextra の export 制約は言語切り替えに影響しない。**

**未翻訳レッスンの扱い（推奨案・未確定）**

| 案 | 挙動 |
|---|---|
| **A（推奨）** | 英語モードでも英語版が無ければ日本語本文を表示し、「未翻訳」バッジを出す |
| B | 英語サイドバーから未翻訳レッスンを隠す |
| C | 全部翻訳するまで英語版を公開しない |

A を推す理由: B は英語モードで学習の流れが途切れ、C は「英語版がいつまでも出ない」になりがち。A なら1本翻訳するたびに価値が積み上がる。

### 7. `contents/` の構造上の課題 ★必達ラインの主工数

repo を確認した結果、**フレームワーク選定より先に解くべき問題**が見つかった。

```
contents/Git完全マスターシリーズ/Gitブランチ操作コース/ブランチとは何か/contents.md
```

- **全レッスンのファイル名が `contents.md` で同一**
- **ディレクトリ名が日本語**
- **フロントマターに `slug` がない**（`series` / `course` / `lesson` / `status` / `description` / `tags` / `estimated_minutes` / `author`）

どの静的サイトフレームワークもファイル配置から URL を決めるため、**このままではどれも成立しない。** つまりどれを選んでも「`contents/` を走査して公開サイトが期待する形に並べ替える変換スクリプト」が1本必要になる。

| 作業 | フレームワークで差が出るか |
|---|---|
| `contents/` を走査してツリーを組む | **出ない** |
| 日本語ディレクトリ → URL 用 slug を決める | **出ない** |
| `contents.md` を期待される配置に変換・出力 | **出ない** |
| サイドバー構成（Nextra なら `_meta`）を作る | 少し出る |
| ビルド → Actions → Pages デプロイ | ほぼ出ない |

**工数の大半がフレームワーク非依存。** 「セットアップが軽いフレームワーク＝必達ラインへの最短距離」という当初の見立ては誤りだった（VitePress を「最短距離」と評価していたが、これは取り下げ）。

**英語版ファイルの置き場所（推奨案・未確定）**

```
contents/Git完全マスターシリーズ/Gitブランチ操作コース/ブランチとは何か/
    contents.md       ← 日本語
    contents.en.md    ← 英語（無くてよい）
    session.json
```

理由:
1. Studio の Pane2 でレッスンを選んだとき日英が同じ場所にあり、**翻訳漏れが一目で分かる**。将来「英語版を生成する」スキルを作るときも対象が自明
2. `lib/contents-loader.ts` の変更が小さい。別ツリー（`contents/en/...`）にするとローダーとスキーマが二重化する

**slug の決め方（推奨案・未確定）**

フロントマターに `slug: branch-basics` のようなフィールドを足すのが安全。理由は Studio 側で編集でき、URL が人の判断で決まるため。変換スクリプト側でローマ字変換テーブルを持つ案もあるが、URL が機械任せになる。**ただし `lib/schema.ts` の Zod スキーマ変更と、既存レッスン全件への追記が必要。**

### 9. 発表（グループセッション・4分）

**時間が6分から4分に短縮された。** 使用する技術とリンクは口頭からごっそり削る。

| パート | 時間 | 扱い |
|---|---:|---|

| **解決したい課題** | **60秒** | 削らない。主語はトレーナー側の消耗 |
| 企画の概要 | 25秒 | さらっと |
| **モック紹介** | **60秒** | 新規追加 |
| 進捗 | 15秒 | さらっと |

## 却下した案

| 案 | 却下理由 |
|---|---|
| 公開先を GitHub Pages 1本に絞る | 社内で実用レベルまで作り込む動機を優先。2系統を維持する |
| 完成の定義を「Git の1コースを企画から公開まで通すこと」にする | ゴールはツール側。コンテンツは制作例で十分 |
| **VitePress** | Vue 製。曼陀羅が Vue Flow になり **Studio の React Flow とコードが2本**になる。markdown-it なので remark/rehype のプラグイン資産も流用できない |
| **Vue Flow** | Vue 専用。React では動かない → React Flow（`@xyflow/react`）へ |
| **MkDocs Material** | ドキュメント機能は最強クラスだが、Python 製で **React コンポーネントを埋められない**。曼陀羅のモダン化とゲーミフィケーションで詰む |
| **Docusaurus** | React で i18n は最強だが、**独占機能のバージョニングとブログが用途の外側**。デザインが Infima で素だと古く、静的専用でゲーミフィケーションが袋小路 |
| **Next.js App Router + MDX 自作** | サイドバー・目次・検索・前後ナビを全部自作することになり、必達ラインへの距離が最も遠い |
| **Fumadocs** | shadcn デザインで魅力的だが、Nextra と同じ Next.js 系で優位は見た目のみ。**公開サイトと Studio はユーザーが違う**ので見た目を揃える実利が薄い |
| MDX 方式（本文に JSX を書けるようにする） | `contents/` の `.md` が純粋な markdown でなくなり、Studio の CodeMirror 編集と噛み合わない |
| 発表を6要素の機能紹介型にする | 聞き手が他部署。機能名を並べても繋がらない |
| モック紹介をライブで動かす | AI 生成の待ち時間と画面共有の事故で4分が崩壊する（→ ライブだが動かさない、に着地） |
| 今後の計画を必達／次／余裕ありの3段＋日付にする | グループセッションは細かいマイルストーンを伝える場ではない。熱量重視 |
| 検証で受講者に実際に独習してもらう | 公開が必達ライン上にあり、検証期間が最後の数日に押し込まれる |

## 途中で取り下げた自分の主張（記録）

- **「VitePress は React 資産を流用できないから不採用」** — 事実だが決定打ではない。公開サイトは読み物の画面で、Studio の shadcn 部品を流用したい場面はほぼない。**本当の理由は曼陀羅の二重実装。**
- **「VitePress が必達ラインへの最短距離」** — 取り下げ。必達ラインの工数の大半は `contents/` の変換スクリプト（7章）でフレームワーク非依存。セットアップの軽さは全体工数にほぼ効かない
- **「ゲーミフィケーションには認証とDBが要るから重い」** — 静的サイトでも BaaS 直叩きで実装できる。サーバーが要るのは集計・不正防止・キー隠しだけ
