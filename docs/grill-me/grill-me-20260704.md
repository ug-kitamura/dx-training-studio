# DX Training Studio — グリルセッション記録（コンテンツ公開・基盤）

**実施日**: 2026-07-04  
**目的**: トレーニングコンテンツの公開方針と、その先のゲーミフィケーション／Azure 基盤の方向性を固める  
**前提**: 作成はローカルの dx-training-studio、組織 API キーは配布しない  
**ステータス**: 主要決定済み ✅ / 未決事項あり（後述）

---

## 背景

- ⚙メニューで保存した AI / Pixabay API キーはブラウザの `localStorage`（`dx-training-studio-settings`）に平文保存される。サーバーには永続化しない。
- 組織キーを使い、かつキーを配布したくない場合、ローカル完結だけではグループ制御は効かない。**キーは社内ゲートウェイのみが持ち、ローカル studio はトークンだけ送る**形が本命。
- 御社は Azure と Entra ID SSO が使える前提。ただし **最初のゴールは受講者向け静的コンテンツの公開**であり、ゲーミフィケーションや AI ゲートウェイは後続。

---

## 決まったこと

### 1. フェーズ分け

| フェーズ | 内容 | App Service |
|----------|------|-------------|
| **トライアル** | 社内 GitHub Pages に静的サイトを載せて検証 | 不要 |
| **本公開** | Azure Static Web Apps（Pages と**同じ静的成果物**） | 不要 |
| **後続** | ゲーミフィケーション、作成者向け AI ゲートウェイ | **必要**（後付け可） |

ゲーミフィケーション（進捗・スコア・トロフィー）は静的公開のあとから足せる。最初の静的デプロイをやり直す必要はない。

### 2. トライアル: GitHub Pages

| 項目 | 決定内容 |
|------|----------|
| **公開先** | 社内向け GitHub の GitHub Pages |
| **アクセス** | 社員のみ（社外公開の心配なし） |
| **Pages を本運用にしない理由** | 普段 GitHub を使わない社員が Pages にアクセスした瞬間に課金対象になるデメリットがある |
| **位置づけ** | うまくいったら Azure SWA へ。**やり方は大きく変えない**（同じ静的成果物を載せるだけ） |

### 3. 本公開: Azure Static Web Apps

| 項目 | 決定内容 |
|------|----------|
| **デプロイ先** | Azure Static Web Apps |
| **受講者のグループ制限** | **設けない**（社内なら広く見せる） |
| **Entra ID SSO** | SWA なら最初から使える想定。**簡単であれば入れてもよい**（「社員アカウントなら誰でも」の入口であり、特定グループのみではない） |

### 4. 公開対象・リリース運用

| 項目 | 決定内容 |
|------|----------|
| **status フィルタ** | **しない**。`open` / `in_progress` も公開してよい |
| **ステータス表示** | 受講ページ上にステータスを明記する |
| **公開の起点** | **release タグ**（main への日常 push では公開しない） |
| **タグ運用** | 公開してよいタイミングで、作成者（またはリード）が**手動**でタグを打つ → GitHub Actions がデプロイ |

### 5. 受講サイト第1弾の範囲

| 含める | 含めない（トライアル） |
|--------|------------------------|
| シリーズ → コース → レッスンの**一覧表**（対象者・レッスンメタ等） | 認証の本格運用（Pages） |
| 一覧から各シリーズ／コース／レッスンのトップへの**リンク** | 進捗・スコア・トロフィー |
| **グローバル曼陀羅**（各コースのトップへリンク） | Azure Blob / App Service |
| **レッスン本文**ページ | |

- **mkdocs は候補の一つ**に過ぎない。曼陀羅・メタ付き一覧はカスタム UI の比重が大きい。
- おすすめ方向: `contents/` を入力にする**小さな静的サイト**（Astro や Next の静的エクスポート等）で一覧・曼陀羅・本文を一体生成する。Pages と SWA で成果物を共有しやすい。

### 6. 画像

| 段階 | 決定内容 |
|------|----------|
| **トライアル** | 公開に必要な画像は **GitHub リポジトリに含める** |
| **Azure 許可後** | **Azure Blob Storage** へ移行する想定 |

### 7. 多言語（日本語 / 英語）

| 項目 | 決定内容 |
|------|----------|
| **既定言語** | 日本語 |
| **切替** | 言語切替ボタンで英語版を表示 |
| **英語原稿** | AI スキル等で各レッスンの英語版を作成する予定（**未実装**） |
| **レッスン ID** | 日英で**同一**の安定 ID を使う方向（進捗は言語非依存）。詳細は未決 |
| **配信** | 静的のまま実現可能（多言語のために App Service は不要） |

ファイル配置・URL 設計・英語未用意時のトグル挙動などは未決。検討用の一例:

```
.../レッスン名/
  contents.md        # 日本語
  contents.en.md     # 英語（未作成可）
  .meta.json         # 共有メタを置く案（§8）
```

### 8. レッスンメタと安定 ID（検討中）

- 進捗・トロフィーを足すなら、表示名やフォルダ名だけに依存しない **安定 lesson id** があった方がよい、という方向性のみ合意。
- **現状**レッスン ID は `contents.md` フロントマターでは定義していない。メタはフロントマターのまま。
- 日英で本文ファイルを分ける場合、フロントマターを両方に書くと共有メタの二重定義になりやすい、という懸念あり。
- **有力な案**（未決定）: シリーズ／コースと同様、レッスン毎の `.meta.json` に共有メタ（`id`, `status` 等）を切り出し、md は本文中心にする。
- **今のフロントマター維持**でも、日本語のみのトライアルには大きな支障はない。切り出しは英語や ID を本格化する前後で改めて決める。
- Pages トライアルのブロッカーにはしない。
### 9. API キー（作成者向け・公開とは別件）

| 項目 | 決定内容 |
|------|----------|
| **現状** | localStorage または `.env.local`（`AI_API_KEY` / `PIXABAY_API_KEY`） |
| **本命** | 組織キーは **Azure Key Vault** に保管。**App Service 上の AI ゲートウェイ**が Entra グループを確認してから外部 AI を呼ぶ。キーは利用者に配布しない |
| **ローカル studio** | ゲートウェイへトークン付きでリクエストするクライアントのまま（studio 全体を App Service に載せる必要はない） |
| **受講者静的公開だけなら** | ゲートウェイは不要。作成者 AI は当面ローカルキー運用でよい |

### 10. 将来の Azure サービス使い分け（全体像）

| 関心事 | サービス | 最初から必要か |
|--------|----------|----------------|
| 受講者向け静的サイト | **Azure Static Web Apps** | 本公開時 |
| 画像・公開ファイル | **Azure Blob Storage** | Azure 許可後（トライアルはリポ内） |
| 社内コンテキスト DB | **Azure Database for PostgreSQL** | 共有 DB 移行時（現状 Neon / ローカル可） |
| API キー保管 | **Azure Key Vault** | AI ゲートウェイ導入時 |
| AI ゲートウェイ・進捗 API | **Azure App Service** | 後続 |
| 認証・グループ | **Microsoft Entra ID** | SWA SSO / ゲートウェイ時 |

**Supabase のような BaaS は必須ではない。** Azure 上で同等の部品を組み合わせる。

### 11. 将来リポジトリ構成（案）

リポジトリ名 `dx-training-studio` にまとめる場合のざっくり構成:

```
dx-training-studio/                 # リポジトリルート
├── .github/workflows/
│   ├── publish-content.yml         # 静的サイト → Pages / SWA
│   ├── deploy-ai-gateway.yml       # 後続
│   └── deploy-learner-api.yml      # 後続
├── studio/                         # 作成ツール（現行本体）
│   └── contents/                   # 原稿の正本（中に置くのは自然）
├── apps/
│   ├── ai-gateway/                 # App Service（後続）
│   └── learner-api/                # App Service（後続）
├── learner-site/                   # 受講者向け静的サイト生成
└── packages/shared/                # 任意
```

- `contents` を studio 内に置くのは自然。
- `apps` を studio **内**に置くのは不自然 → **リポジトリ直下で studio と兄弟**がよい。

## 次のステップの候補

1. **公開プランを短く固定する** — フェーズ0（Pages トライアル）/ フェーズ1（SWA）のチェックリスト化
2. **受講サイトの試作** — 一覧・曼陀羅・レッスン本文を `contents/` から静的生成（スタックは試作しながら決めてよい）
3. **release タグ用 GitHub Actions** — タグ push で Pages へデプロイ（後でデプロイ先を SWA に差し替え）
4. **レッスンメタ / ID** — 必要になったタイミングで、フロントマター維持か `.meta.json` かを改めて決める
5. **英語版** — スキルとファイル契約はメタ方針が固まってからでもよい
6. **（後続）AI ゲートウェイ** — Entra + Key Vault + App Service
7. **（後続）ゲーミフィケーション** — learner-api + PostgreSQL 等
