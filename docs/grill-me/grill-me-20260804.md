## 決まったこと

### 1. トレーニングの前提

| 項目 | 決定内容 |
|------|----------|
| **目的** | システム・ソフトのメンバにツール開発を促し、業務効率を上げる |
| **受講者** | エンジニアリング部署の新入社員・中途採用社員 |
| **前提スキル** | プログラミングの素養は多少あり。Git / GitHub / Python は初心者。AI はチャットで調べ物をした程度 |
| **ゴール** | 2時間（1h × 2回）で必ず動くツールが1つ完成する体験 |
| **完成物の方針** | フォーマット（骨組み・処理の流れ）は運営が固定し、**入力データだけ受講者自身の業務データ**を使う |
| **基礎の扱い** | ハンズオンで直接使わない基礎・概念・セットアップも**厚くカバーする** |

### 2. 分量

| 項目 | 決定内容 |
|------|----------|
| **総レッスン数** | 25 |
| **1レッスン** | 10〜15分 |
| **自己学習の総量** | 5時間35分（目標5h・上限6h） |
| **自己学習期間** | 3週間 |
| **必須 / 任意の層分け** | **しない**。25レッスンすべて必須 |
| **演習** | **全レッスンに5分以内の「やってみる」を入れる**。読み物と選択式問題だけにしない |

### 3. シリーズ構成（6シリーズ・25レッスン）

| シリーズ | slug | レッスン | 時間 | コース構成 |
|---|---|---:|---:|---|
| ① はじめに | `start` | 1 | 10分 | DX入門 |
| ② AI | `ai` | 1 | 15分 | AI基礎 |
| ③ Git | `git` | 6 | 85分 | 概念2 / 環境構築1 / 基本操作3 |
| ④ GitHub | `github` | 6 | 85分 | 入門2 / リモート連携1 / ブランチとPR3 |
| ⑤ Python | `python` | 9 | 130分 | 概要2 / 環境構築1 / 基礎3 / 中級3 |
| ⑥ ツール開発実践 ☆ | `build` | 2 | 10分＋120分 | 事前準備 / 当日 |

- **AI は独立シリーズにする**。今は1レッスン（社内 Gemini ベースのチャットツールの基本操作）だが、今後コンテンツを育てる前提
- **AI はおまけの位置づけ**。「使えれば良い」程度の温度感で、必要に応じて聞きながら Python を書いたり Git を調べたりする想定
- **ブランチは Git ではなく GitHub シリーズに置く**（理由は「却下した案」4を参照）
- 合流先シリーズ名は **「ツール開発実践シリーズ」**

### 4. 曼陀羅の規則（`lib/course-flow.ts` から読み取り）

コードを読んで確認した規則。**設計の自由度を決める最重要の制約**。

| 規則 | 実装箇所 |
|------|----------|
| シリーズ内は `courses[]` の配列順で自動的に直列の鎖。**シリーズ内では分岐できない** | `buildCourseFlowAdjacency` |
| 別シリーズへの辺のみ `cross_series_prev` / `cross_series_next` で張れる（同シリーズ ID は自動除去） | `filterCrossSeriesIds` |
| 1コースから同一ターゲットシリーズへ出せる辺は1本まで | `removeOtherNextInTargetSeries` |
| 1シリーズから特定コースへ入る辺も1本まで | `establishOutgoingLink` |
| 循環は禁止（保存時にドライラン判定） | `hasCourseFlowCycle` / `wouldCourseMetaEditCreateCycle` |

上2つの排他を掛け合わせると、**シリーズ A → シリーズ B の辺は全体で1本だけ**になる。

### 5. 曼陀羅の構成と進行ルール

**辺（7本、すべて異なるシリーズペア）**

| # | From | To |
|---|---|---|
| 1 | はじめに / DX入門 | AI / AI基礎 |
| 2 | はじめに / DX入門 | Git / 概念 |
| 3 | はじめに / DX入門 | Python / 概要 |
| 4 | Git / 基本操作 | GitHub / 入門 |
| 5 | AI / AI基礎 | ツール開発実践 / 事前準備 |
| 6 | GitHub / ブランチとPR | ツール開発実践 / 事前準備 |
| 7 | Python / 中級 | ツール開発実践 / 事前準備 |

**進行ルール**

- あるコースに入るには、そこへ合流する**全ての辺の元コースが完了済み**である必要がある
- その範囲内であれば、受講者はどのブランチから進めても構わない（順序は受講者に任せる）
- 全ブランチの完了を求めるが、**ハンズオン参加の強制ゲートにはしない**。未完了でも希望者は参加でき、その時点でできる限りのことをしてもらう
- Git シリーズは build への直接の辺を持たないが、`Git基本操作 → GitHub入門` を経由するため全 Git コースが必須になる

### 6. 学習形態の保持場所

| 項目 | 決定内容 |
|------|----------|
| **保持場所** | コース `.meta.json` の `format` フィールド |
| **値** | `self-study` / `hands-on` |
| **粒度** | **コース単位**（レッスン単位では持たない） |
| **表示** | 曼陀羅上で `hands-on` のコースに **☆** を付ける |

理由: 学習形態はコース単位で一貫し（事前準備コース=独学、当日コース=ハンズオン）、レッスン単位にすると25本への記入で付け忘れが出る。曼陀羅がコースノードのグラフなので、コースに属性がある方が色分け表示できる。

### 7. 公開と識別子

**公開（2段階）** — 詳細な基盤方針は [grill-me-20260704.md](grill-me-20260704.md) を参照

| フェーズ | 形態 | 内容 |
|---|---|---|
| 1 | 静的サイト → 社内 GitHub Pages | Markdown を HTML 変換。曼陀羅を目次として掲載。画像も同梱 |
| 2 | Azure Static Web Apps | アカウント紐付けで進捗・トロフィー等のゲーミフィケーション。画像は Azure Blob |

生成スタックは **VitePress を第一候補、うまくいかない場合は MkDocs** の二段構え（未決）。

**識別子**

| 種別 | 用途 | 採番 |
|---|---|---|
| `id`（`srs-` / `crs-` / `lsn-`） | 不変キー。フェーズ2の進捗・トロフィーのキー | **Studio がプログラムで採番**（計画では扱わない） |
| `slug` | 公開URL `/{series}/{course}/{lesson}/` | **計画段階で決める** |

両方持つ理由: slug を後から推敲しても id が不変なので進捗データが壊れない。逆に id を URL にすると `/crs-git-4fh0j2/` となり可読性と検索性を失う。

### 8. 制作体制

1. 本計画に沿って **Studio の AI エージェントで全レッスンの草稿を生成**
2. Studio 上で人が磨く（技術検証・社内事情の追記・画像の差し込み）
3. 静的サイトへ変換して公開

25レッスンを手書きすると1本2時間として50時間かかり、同じ8月にツール開発・画像用意も並行するため、草稿生成を前提にしないと締切に届かない。

**既存 `contents/` は基本的にいじらない。** 変更が必要な場合は実行せず提案のみ。

### 9. スキルの分担

| スキル | 責任範囲 | 状態 |
|---|---|---|
| **計画スキル** | 企画の深掘り、構成と仕様の決定、計画書の出力 | 🚧 作成中（`create-plan`） |
| **草稿作成スキル** | レッスン本文・演習・画像の作り込み | 次のステップ |
| Studio 本体 | id 採番、曼陀羅の厳密な検証、シリーズ・コースの実体作成 | 既存 |

**計画スキルの対象外**: id 採番 / 厳密な曼陀羅検証 / 画像・演習の作り込み / 既存コンテンツの改変（提案のみ）

**計画スキルの成果物**: 全体構造 / 曼陀羅構成 / 各シリーズ仕様 / 各コース仕様 / 各レッスン仕様（大まかな構成まで）/ 時間予算 / 未決事項 / 決定の根拠と却下案

**対話の設計**:

- **上流は1問ずつ対話、下流は案を出してレビュー**。上流の答えが下流を機械的に決めるため
- **共通方針のみ既定値**（曼陀羅の規則・1レッスン10〜15分・全レッスンに演習・`format` をコースに持つ・id/slug 両建て）、**今回固有は毎回問う**（受講者層・ゴール・分量・シリーズ構成）
- `grill-me` は呼び出さず、作法（1問ずつ・必ず推奨案つき・通し番号）だけ踏襲する。grill-me は汎用で、トレーニング設計特有の決定順序を知らないため

### 10. Studio スキルの実行契約（`lib/agent/skill-loader.ts` から読み取り）

`dx-training-studio/.claude/skills/` は **Studio 内蔵エージェント用**のスキル置き場であり、Claude Code のスキルとは別のランタイム。

| 項目 | 内容 |
|---|---|
| 読み込み対象 | `<id>/SKILL.md` のみ。**`references/` は読まれない**（3段階ローディングは使えない） |
| frontmatter | `name` / `description` / `hidden` / `variables` / `tools` |
| 変数注入 | 本文の `{{var}}` を `injectSkillVariables` が置換 |
| 変数の配線 | `AgentChatPane.tsx` の `buildVariables` が skillId ごとにハードコード。**未配線の変数を宣言すると invoke が 400 エラー** |
| 利用可能ツール | Studio が実装したもののみ（`search_company_context` / `select_company_context`）。ファイル操作ツールはない |

### 11. 既存スキルの扱い

`create-draft` / `create-structure` は**お試しで作ったもの**。参考にしてよいが引っ張られる必要はない。
この機会にちゃんとした名前のスキルにし、**完成後に古いスキルは削除する**。

## 却下した案

### 1. ハンズオンの完成物

- **採用**: フォーマットは運営が固定し、入力データのみ受講者自身のもの
- **却下**: 各自が業務課題を持ち込む案 — 環境差とスコープ差で2時間の完走率が読めず、講師のサポート負荷が人数分に膨らむ

### 2. 分量の2層化

- **採用**: 25レッスンすべて必須（層分けなし）
- **却下**: 必須20＋任意（reference）の2層構造 — 25レッスンの枠内で基礎は十分カバーできるため、層を分ける複雑さが見合わない

### 3. AI シリーズの規模

- **採用**: 1レッスン（社内 AI チャットの基本操作のみ）
- **却下**: 3レッスンに拡張する案 — 現時点では「使えれば良い」という位置づけ。今後育てる前提でシリーズだけ独立させた

### 4. ブランチをどのシリーズに置くか ★

- **採用**: GitHub シリーズ
- **却下**: Git シリーズに残し、基本操作コースから GitHub へ分岐する案

  **理由**: 「決まったこと」4の通り、**シリーズ間の辺は同一ペアにつき全体で1本**しか張れない。この案だと `Git基本操作 → GitHub入門` で1本を使い切るため、`Gitブランチ → GitHub PR` の依存が表現できず、**ブランチ未習のまま PR コースに入れてしまう**。さらに Git ブランチコースが行き止まりになり、build への辺を別途足さないと飛ばせてしまう。
  加えて「ブランチを切る → push → PR → マージ」は一連で理解する内容であり、間に別シリーズを挟むと繋がりが切れる。

- **却下**: Git を全部終えてから GitHub — 依存は安全だが完全な直列になり、GitHub に触れるのが最も遅くなる

### 5. 合流先シリーズの名称

- **採用**: 「ツール開発実践シリーズ」
- **却下**: 「卒業試験シリーズ」 — ゴールは「作れた実感」であり、試験＝評価される場という含意は新人・中途にとって心理的ハードルになる
- **却下**: 「卒業制作シリーズ」「総仕上げシリーズ」 — 実務ツールという実用性のニュアンスが弱い

### 6. 学習形態の保持場所

- **採用**: コース `.meta.json` の `format`
- **却下**: レッスン frontmatter の `tags` に混ぜる — tags は自由語彙のため内容タグと同列に並んで区別できず、`handson` / `hands-on` / `ハンズオン` の表記ゆれと付け忘れが避けられない
- **却下**: レッスン単位で持つ — 学習形態はコース単位で一貫するため、25本すべてに記入するのは付け忘れのリスクだけが増える

### 7. 演習の入れ方

- **採用**: 全レッスンに5分以内の「やってみる」
- **却下**: コース末に演習レッスンを1本置く — 読み物を流し読みして演習で詰まる形になり、どこで分からなくなったか本人にも特定できない
- **却下**: 選択式の確認問題のみ（既存サンプル踏襲） — Python と Git は読んで分かった気になる典型領域で、ハンズオン当日に初めて `git commit` を打つことになる

### 8. 公開 URL の方式

- **採用**: id（不変キー）＋ slug（URL）の両建て
- **却下**: URL も id にする — `/crs-git-4fh0j2/` では共有時に内容が分からず検索性も落ちる
- **却下**: slug だけ使う — タイトル推敲で slug を変えるとフェーズ2の進捗レコードとトロフィーが壊れる

### 9. 計画スキルの成果物

- **採用**: 計画書（markdown）まで。実体化は人が Studio で行う
- **却下**: 承認後に `contents/` の骨格（ディレクトリ・`.meta.json`）まで生成する案 — id 採番と曼陀羅の検証は Studio 側の責任であり、スキルが二重に持つべきではない
