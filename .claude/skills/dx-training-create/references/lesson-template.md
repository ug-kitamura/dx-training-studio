# レッスンの型

レッスン1本の**形式**を決める。本文は `contents.md`、メタはレッスンフォルダの `.meta.json`。何を書けば良い草稿になるかという**質**の判断材料は [design-principles.md](design-principles.md) にある。両方を使う。

## レッスン `.meta.json`

メタはレッスンフォルダ直下の `.meta.json` に書く。**`contents.md` には frontmatter を書かない**——本文（`# <レッスン名>` から）だけで始める。キーの集合の正本は `lib/schema.ts` の `lessonMetaFileSchema`。ここで決めるのは**値の選び方**だけ。

| キー                | 値の決め方                                                                                                                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `slug`              | 計画書のレッスン slug（`git/concepts/what-is-version-control` の末尾）をそのまま転記する。公開サイトの URL になる。自分で考えない。計画書に無ければフェーズ1の確認ゲートで確定させた値を使う |
| `status`            | `in_progress`。本文を書いた時点で未着手ではない。完成後に `done` へ上げるのは人がやる                                                                                                        |
| `description`       | 1行で書く                                                                                                                                                                                     |
| `tags`              | 小文字英数とハイフンのみ。正本は `lib/lesson-tags.ts` の `TAG_PATTERN`。弾かれた値は黙って捨てられる                                                                                         |
| `estimated_minutes` | 計画書の時間をそのまま入れる                                                                                                                                                                 |
| `author`            | この run の執筆者名（聞く手順は `SKILL.md`）。**空にしない**                                                                                                                                 |

**書かないキー**: `series` / `course` / `lesson`（名前の正本はフォルダ名）、`id`（loader が自動採番して書き戻す。シリーズ・コースと同じ）、`author_en`（表記を書き分けたい人が書く値。スキルは触らない）。

## 受講者の前提

読者は**社内の業務環境で学ぶ社員**。この前提から外れる書き方をしない。

| やらない                                                        | なぜ                                                                         |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 私物 PC・社外の共有フォルダ・個人所有の資料を代替手段として出す | 業務環境以外は使わない。演習の代替案も業務環境の中で完結させる               |
| 「英語の文言を読める必要はまだありません」のような断り          | 基礎的な英語は読める。短い画面表示やメッセージは、断りを置かず意味を説明する |

## 章立て

見出しは `##`。冒頭に `# <レッスン名>` を1本置く。章の並びと「やってみる」を全レッスンに置くことは計画書の既定方針で、**章を足したり順を変えたりしない**。

**例外は集合回の当日資料**——コースの `style` が `lecture` / `hands-on` のレッスンは、その時間の全体が演習・発表にあたるため、「やってみる」の独立章と確認問題を置かなくてよい。代わりに時間割・課題文・進行の型を本文の節にする。

| 章         | 役割                                                                                                                                                                                     | 目安            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| 学習目標   | なぜこれを学ぶかを、読者が経験している場面で受け取らせる                                                                                                                                 | 3〜5行          |
| 本文       | `##` で節に割る（学習目標・まとめと同じレベル。記述例・既存レッスンと同じ）。1節につき読者の問いを1つ解く                                                                                | 全体の6〜7割    |
| やってみる | 5分以内で手が動く課題を1つ。やること・前提・考えなくてよいことを書く                                                                                                                     | 課題1つ＋解答例 |
| まとめ     | 持ち帰る骨を数で名指しする（「この3つだけ」）                                                                                                                                            | 3〜4行          |
| 確認問題   | 自分の言葉で言い換えさせる・学んだ概念で分類させる。**本文を読み返せば自分で確かめられる問いに限る**（解答は付けない）。計算や複数選択のように解答が無いと正誤の分からない問いは出さない | 1〜2問          |

分量は `estimated_minutes` から逆算する。読了は400字≒1分（換算の正本は `lib/lesson-meta.ts` の `estimateDraftMinutes`）。手を動かす時間がその外側に乗るので、本文を時間いっぱいまで書かない。

解答例は `<details>` に畳んで**1行**に収める。完成コード一式を置いてよいのはハンズオンのレッスンだけ。

**演習は、本文を通した後の状態から始める。** 本文で作らせたブランチ・ファイル・リポジトリを、演習でもう一度作らせるとエラーで止まる（「すでに存在します」）。本文と同じ操作を演習で繰り返すなら、**既にある場合の分岐を演習側にも書く**。

**後続レッスンが要求する前提は、本文ではなく演習の終状態で保証する。** 演習を飛ばす読者はいないが、本文の途中の手順は読み流される。設計メモの「後続へ供給するもの」に挙げたものが本文の中ほどで作られているなら、演習の最後に置き直す。

## 声かけ

レッスンの**位置**によって、情緒を出す量を変える。中身は計画書と曼陀羅から取り、創作しない。

| レベル | 対象                                                                            | 置くもの                                                                           |
| ------ | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Lv0    | すべてのレッスン                                                                | 冒頭（`学習目標` の入り）と結び（`まとめ` の締め）に一言ずつ。本文の節には足さない |
| Lv1    | シリーズの**最初 / 最後**のレッスン                                             | 声かけを下の定型構造で書く                                                         |
| Lv2    | 計画書が**集合（F2F）**と定めたコースのレッスン（コースの `style` が `lecture` / `hands-on` かで判定する） | 声かけに留めず、本文の骨格に組み込む                                               |

章は増やさない。Lv0・Lv1 は既存の `学習目標` と `まとめ` の中に収める。

**Lv1 の定型構造**:

| 位置               | 含めるもの                                    | 材料                           |
| ------------------ | --------------------------------------------- | ------------------------------ |
| シリーズ最初の冒頭 | ①このシリーズで学ぶこと ②終了時に手にするもの | 計画書のコース仕様（学習目標） |
| シリーズ最後の結び | ①ねぎらい ②手にした武器 ③解放される次         | 計画書＋曼陀羅の辺             |

- **文言は決めない。構造だけ守る。** 定型文を使い回すと、読者は2シリーズ目から読み飛ばす
- **「解放される次」は解放の言い方で書く**（「□□が解放されました」）。曼陀羅は進む順が自由なので、「次は□□へ」と書くと、辺が複数あるときに一本道の指示になる
- **Lv2 のキックオフは、トレーニングの目的・ゴール・修了時に得られるものを冒頭で明示する。** 動機づけの禁じ手は [design-principles.md](design-principles.md) の「書いてはいけないもの」
- 計画書が**全体を貫く比喩**（世界観）を指定している場合、その語彙は説明なしで通じるものだけを使い、声かけと情緒の箇所にだけ出す。本文の説明には持ち込まない
- 既存レッスンにあとから声かけを足す必要はない
- **「解放される次」は曼陀羅の進行ルールで判定する。** あるコースを終えて「解放されました」と書けるのは、出口の辺の相手コースが**作成済み**で、かつその相手へ**合流する辺がこの1本だけ**のとき。相手が複数シリーズからの合流点（例: ハンズオン事前準備コースは AI・GitHub・Python の3本が揃って初めて入れる）なら、このコースを終えても解放されない——「□□への道が1本つながりました（残りは △△ と ××）」のように、**揃っていない辺があることが読める言い方**にする。相手が未作成なら、解放の言い方を使わず、手にした武器の用途の案内に留める。判定材料は計画書の「シリーズ間の辺」の表と `dx-training-plan/references/mandala-guide.md` の進行ルール

## 本文の書き方

### 前後のレッスンへの参照

**記述的に書く。**「前のレッスンで」「三大エリアのレッスンで」。`L06` のようなレッスン番号を読者向け本文に書かない——読者に番号は見えておらず、順序が変われば嘘になる。

### 専門用語の初出

受講対象（コースの `target`）が知らない前提の語は、**そのレッスンでの初出で短く説明する。** 説明のないまま使うと、読者はそこで降りる。

**受講順で前のコースに説明があれば、繰り返さず参照の一言で足りる**（「はじめにシリーズで見た曼陀羅」）。同じコース内の前のレッスンで説明済みのものは、上の「前後のレッスンへの参照」に従う。

### 表

項目と属性が対応づく情報は**表で示す**。コマンドと役割の一覧、複数手段の比較、利点と欠点。箇条書きに畳むと対応関係が読み取れなくなる。

### アラート

補足・注意は GitHub アラートで示してよい。多用しない——本文の流れで書けるものは本文で書き、**読み飛ばされると困る一点**にだけ使う。

| 記法             | 使いどころ                         |
| ---------------- | ---------------------------------- |
| `> [!NOTE]`      | 知っておいてほしい補足             |
| `> [!TIP]`       | よりうまくやるコツ                 |
| `> [!IMPORTANT]` | 成功に必要な重要事項               |
| `> [!WARNING]`   | すぐ対応が要る、危険を伴いうる内容 |
| `> [!CAUTION]`   | 実行すると悪影響・リスクがある内容 |

### コードブロック

フェンスには**必ず言語を指定する**（` `bash `/` `python ` 等）。変更前後を見せる場面は ` `diff ``` を使い、`+`と`-` で示す。

**本文のコードには実行の足場を敷く。** 本文にコードブロックを載せるレッスンは、最初のコードの前に「どのファイルに書き、どう実行するか」を1度明示する。コードが連続するときは、**前のコードの続きに足すのか、新しいファイルなのか**をブロックごとに区別できるように書く。足場が無いと、読者は写経できずに読み流すか、別のファイルで動かして未定義のエラーで止まる。

### コマンドの出力

**コマンドを実行できる環境なら、実際に実行して出力を確認してから書く。** 実行できない環境では、推測した出力を断定形で書かない。

出力を短くして載せるときは「要点だけを抜き出しています」と**その場で断る**。追記式のコードで前の節の出力も一緒に出るときは、「ここでは増えた行だけ載せている」と断る。省略を黙ってやると、読者は自分の画面との差分を自分のミスだと思う。

エラー出力を載せるときは、**掲載するスニペットと行番号が一致する状態で採取する**——採取用ファイルに、掲載しない行を入れない。行番号は読者が最初に照合する場所なので、ズレると同じ誤解が起きる。追記式のレッスンでは「行番号は自分のファイルでの位置になります」と添える。

## 空欄の記法

設計メモの3段梯子（DB 検索 → 一括問合せ → 空欄。手順は `SKILL.md`）で解決できなかったものは、blockquote で空欄として残す。**プレビューに残るので埋め忘れが見える。**

| 記法              | 何の空欄か                                                | 埋める場所               |
| ----------------- | --------------------------------------------------------- | ------------------------ |
| `> **社内**:`     | 社内固有のテキスト（手順・呼称・ルール・窓口）            | 後工程の空欄を埋める作業 |
| `> **社内画像**:` | 社内画面の撮影・録画（計画書の `【撮】` `【録】` に対応） | 後工程の空欄を埋める作業 |
| `> **素材**:`     | 社内ではないが人手が要る画像                              | どこでも                 |

- **`社内` の空欄は中身を書かず、答えるべき問いを箇条書きにする。** 期待する形式と分量も指定する（「番号付き手順3〜5ステップ / 200〜300字」のように）。空欄になるのは DB に無く、ユーザーもその場で出せなかった情報である。後工程の作業者がこの実行の文脈なしで埋められるよう、**空欄は誰にも聞かずに自己完結している必要がある**
- **`社内画像` の空欄は撮影指示を具体的に書く。** 何の画面を、どの状態で撮り、どこをマスクするか。中身を知らなくてもここは具体化できる——テキストと画像で「具体的」の意味が違う
- **空欄の周囲に一般論を書かない。** 導入文と次への接続文だけを書く。一般論は埋め忘れたときそのまま公開され、文章として自然に読めるためレビューでも空欄と認識されない
- 空欄は後工程で、AI の支援を受けて埋められる。**AI への指示として読める粒度**で書く

## 画像

AI 生成で埋まる図は HTML コメントで枠を置く。書式は `contracts/image-slot-contract.md` に従い、**印や接頭辞を足さない**。コメント本文はそのまま画像生成のプロンプトになるため、印を付けるとプロンプトに混入する。

**図を置くと決めた節には、必ずコメントを残す。** 画面を見せる前提の本文だけ書いてコメントを省くと、作者はプロンプトをゼロから組むことになり、そこで画像が諦められる。逆に図が要らないと判断した節では、図がある前提の書き方（「下の画面のとおり」など）もしない。

素材を待たずに済む図は**アスキーアート**で書く。空欄を1つ減らせる。

図を置いたら、どこを見てほしいかを本文で指定する。

### 手順型レッスンの密度

手順を書くときは、**画面が変わる操作ステップごとに枠を置く**。ステップの粒度は題材で決めてよいが、画面が変わっているのに枠の無いステップを続けない——読者は自分の画面と本文を照合できなくなり、そこで手が止まる。同じ画面の中で入力が続くだけのステップに1枚ずつ置く必要はない。

**社内システムの手順では、枚数を決めない。** どんな画面かを知らないまま枚数を決めると実物と合わない。`> **社内画像**:` の空欄に、差し込みの方針（「画面が変わるごとに1枚を目安に」）と対象の手順範囲を書き、差し込みは人に渡す。

**ブラウザ上の手順も、コマンドと同じ密度で扱う。** コマンドには出力例を置くのに、Web 画面の手順だけ枠を省く落とし穴がある——書き手は画面を思い浮かべられるので、文章だけで足りると錯覚する。あわせて、**見たことのない画面のボタン位置を断定しない**（「右上の」「下の」）。位置は製品のバージョンで変わり、外した瞬間に読者は自分の画面と照合できなくなる。ボタンの**名前**で指し、位置は撮影した画像に語らせる。

### 実在アプリの画面を求めるとき

VSCode や GitHub のような**実在するアプリの画面**を頼むスロットには、代替手段の断りをプロンプトの末尾に1行足す。

```
実際の画面との一致が重要な図。生成品質が悪い場合はスクリーンショットで代用すること。
```

生成の難しさを事前に見積もって書き分けない——生成は人がその場で回すので、出来を見てから判断できる。**概念図やイメージには足さない**（代替手段が要らない）。

あわせて、**画面だけが欲しいのか、注釈も要るのかを書き分ける。** 書き分けないと、生成側は画面の中に説明ラベルや見出しを補って埋めてくる——実物に無い文字が入った画面は、読者が自分の画面と照合できなくなる。

| 求めるもの     | プロンプトに書くこと                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| 画面の再現だけ | 画面の再現のみである旨と、実際の画面に表示されない説明ラベル・ヒント・タイトルを加えない旨 |
| 画面＋注釈     | 欲しい注釈を**列挙する**。列挙したもの以外を加えない旨を添える                             |

画面の再現だけを求める例:

```
VSCode のソース管理ビューの UI mock。左端のアクティビティバーに枝分かれ形のソース管理アイコン、パネルに「変更」の見出しとファイル名 memo.txt。画面の再現のみ。実際の画面に表示されない説明ラベル・ヒント・タイトルを加えない。
実際の画面との一致が重要な図。生成品質が悪い場合はスクリーンショットで代用すること。
```

注釈も求める例:

```
VSCode のソース管理ビューの UI mock。パネルの「変更」の下にファイル名 memo.txt、その右に「＋」ボタン。上部にコミットメッセージの入力欄と「コミット」ボタン。添える注釈は「＋ ＝ git add」「コミット ボタン ＝ git commit」の2つだけで、ほかの説明ラベル・ヒント・タイトルは加えない。
実際の画面との一致が重要な図。生成品質が悪い場合はスクリーンショットで代用すること。
```

## 出典

Web で調べた事実には出典を添える。**斜体1行**を、本文の該当箇所の直後に置く。脚注や巻末の参考文献リストは作らない。

**URL を裸で書かない。タイトル文字列にリンクを埋め込む。** 長い URL（日本語をパーセントエンコードしたものは特に）が本文に露出すると読む線が切れる。

```markdown
_出典: [Pro Git 日本語版「使い始める - Gitの基本」](https://git-scm.com/book/ja/v2/...)（2026年8月取得）_
```

社内コンテキスト DB のアイテムを本文素材に使った箇所にも、同じ形式で出典を添える。リンク先はアイテムの `source_url`。日付は取得日ではなく**ソース最終更新日**を「YYYY年M月D日更新」で書く。最終更新日が無いアイテムは括弧ごと省略する。

```markdown
_出典: [NMS Git ブランチ運用ルール](https://intra.example.com/git-rules)（2026年8月1日更新）_
```

段2（ユーザーの聞き取り）で得た社内の事実も本文の素材にしてよい。`source_url` が無ければ出典行は付けない。ただし、**断定で書く前に次を確かめる**——①社内コンテキスト DB に同じ主題のアイテムがあれば内容を突き合わせ、食い違いは設計メモの解決表に記録して承認ゲートに乗せる。②ルール・契約・費用のように**読者の行動を縛る事実**（「学習に使われない」「無料」「入力禁止の区分」）は、聞き取りだけで断定せず、ユーザーに根拠資料（ガイドライン・契約ページ等）の提出を求め、出せなければ `> **社内**:` の問いに「根拠の所在」を含めて空欄側へ寄せる。③レビュー役には設計メモの解決表を渡し、段2由来の事実を「未確認」と誤判しないようにする。

## 書き終えたら

本文を通しで1度読み、次の2点を見る。

- **誤字と表記ゆれ** — 同じものを2つの呼び方で書いていないか（`最終版_2` と `最終版2`、`.meta.json` の `description` と本文の食い違い）、半角スペースが紛れていないか
- **単純化した箇所に断りがあるか** — 判断と落とし方は [design-principles.md](design-principles.md) の「単純化していることを明示する」

設計メモとの突き合わせは執筆フェーズの手順にある（`SKILL.md`）。

## 記述例

**形式だけを示す例で、中身は質の見本ではない**（質は [design-principles.md](design-principles.md)）。

`.meta.json`:

```json
{
  "slug": "what-is-version-control",
  "status": "in_progress",
  "description": "「最終版2」問題を入口に、バージョン管理が要る理由を3つ挙げられるようにする",
  "tags": ["git", "basics"],
  "estimated_minutes": 15,
  "author": "DX トレーニング運営"
}
```

`contents.md`（本文のみ・frontmatter なし）:
