# レッスン草稿作成スキル

計画書が決めた構成に、**本文・演習・図・空欄**を入れて `contents.md` を作る。

## 責任範囲

| やる                                                                         | やらない                                                          |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 本文・演習・確認問題の執筆                                                   | シリーズ・コース・レッスンの構成決め（`dx-training-plan` の担当） |
| **内容の深掘り**（計画書には学習目標と演習の骨しかない）                     | 計画書の修正・レッスンの追加削除                                  |
| **必要な画像の判断**と、AI 生成／人手撮影の切り分け                          | 画像そのものの生成                                                |
| **必要な社内データの判断**と、3段梯子での解決（DB 検索 → 一括問合せ → 空欄） | 社内情報の創作・正本の社内コンテキスト DB への登録                |
| **情報収集**（定義・最新動向・具体例の裏取り）                               | 技術的な動作検証（人が行う）                                      |
| `.meta.json` の `order` と `target` の書き出し                               | `id` の採番、曼陀羅のシリーズまたぎの辺の書き込み                 |

## 依存

- `contents-work/plans/` — 入力。**どれを使うかはユーザーに選ばせる**（→ 入力の把握）
- `references/design-principles.md` — **質**の判断材料と、書いてはいけないもの
- `references/lesson-template.md` — **形式**（レッスン `.meta.json`・章立て・空欄の記法・出典）
- `references/model-answer/` — 模範解答。**無くてよい**（後述）
- `contracts/image-slot-contract.md` — 画像コメントの書式。**変更しない**
- `local-db/context-items.json` / `.env.local` の `DATABASE_URL` — 社内コンテキストの検索元（→ フェーズ3の梯子）。**どちらも無くてよい**（段2へ降格する）
- `lib/schema.ts` / `lib/contents-loader.ts` / `lib/lesson-meta.ts` — 出力先のデータ構造

## 進め方

**フェーズを飛ばさない。** 各フェーズの完了条件は口頭の宣言ではなく**ファイルの存在**で判定する。このチェックリストを写して進捗を管理する。

- [ ] フェーズ1: 生成範囲を決め、最小限だけ聞く
- [ ] フェーズ2: 情報収集
- [ ] フェーズ3: 設計メモを**ファイルに書く**
- [ ] フェーズ4: 詰めの対話 → **承認ゲート**
- [ ] フェーズ5: 執筆（1レッスンずつ、都度ファイルへ）
- [ ] フェーズ6: 自己レビュー
- [ ] フェーズ7: 曼陀羅
- [ ] フェーズ8: ふりかえり
- [ ] 模範解答への昇格を問う

### 入力の把握

1. **計画書を選び、読む。** `contents-work/plans/` の候補を一覧で提示し、どれを使うかユーザーに選ばせる。**最新の1本を勝手に選ばない**——古い版を土台に作り直すことがある。候補が無ければその旨を報告し、`dx-training-plan` の実行を促して止まる。制約は表の行と**その表の直後の注記**に分かれている。両方読まないと条件を取りこぼす（「pandas は超基礎のみ」のような限定は注記側にある）
2. **既存の `contents/` を読む。** 出力先に同名のディレクトリが既にあるかを調べる
3. **名前が衝突したら、衝突する対象を一覧で提示し、確認を得るまで書き込まない**

## フェーズ1: 生成範囲を決め、最小限だけ聞く

範囲を**シリーズ / コース / レッスン**から選ばせる。**既定はコース単位**で、迷ったらこれを勧める。**複数シリーズをまとめて作る範囲は提示しない。**

シリーズを選ばれたら、**そのシリーズのレッスン数 × 10分**を見積もりとして添えて警告する。1レッスンで承認ゲート・執筆・レビュー採否まで含めて10分前後かかり、シリーズ単位では人が付き合う時間が長くなる。**警告は伝えるだけで、選択は妨げない。**

範囲は**設計メモの単位**であって執筆の単位ではない。どれを選んでも執筆は1レッスンずつになる。

### 名前を確認してから先へ進む

範囲が決まったら、**これから作る名前を一覧で見せて確認を取る。** 計画書から範囲内のシリーズ・コース・レッスン名を読み取り、計画書が定めた slug を添えて出す。

```
この範囲で、次の名前のディレクトリを作ります。

  シリーズ: Git基礎シリーズ           [git]
  コース:   Git概念コース             [git/concepts]  《self-study》
  レッスン: バージョン管理ってなに？   [git/concepts/what-is-vcs]

計画書のこの名前で進めてよいですか？
```

- **範囲内だけを出す。** 計画書の全体構造を貼らない
- **一括で1回。** シリーズ・コース・レッスンに取り掛かるたびに聞き直さない——ディレクトリを1つも作っていないいまが、止まっても何も捨てずに済む唯一の場所
- slug は公開サイトの URL になる。名前と同じく**ディレクトリを切る前に確定させる器**なので、同じ問いに乗せる
- **計画書に slug が無い階層は、この場で案を出して確定させる。** 小文字英数とハイフンのみ（正本は `lib/schema.ts` の `SLUG_PATTERN`）、兄弟間で重複しないこと。「slug が無いので名前だけ出す」で済ませない——slug は各階層（シリーズ・コース・レッスン）の `.meta.json` に書く値であり、後から足すと URL が変わる
- **コース行には計画書の受講形態（`style`）を `《self-study》` の形で添える。** ここでは**見せるだけで聞かない**——計画書に書いてあることは聞かない。読み取れないコースは `《未設定》` と出す
- **ファイル名に使えない文字が名前に含まれていたら、この一覧で指摘して修正案を添える**（`リポジトリを作る / clone` → `リポジトリを作る／clone`）。置換されると受講者に見える名前が変わるため、ディレクトリを切る前に直す。規則は計画書の命名規則が正本
- **否認されたら実行を止め、計画書の修正案を提案する。** 名前を自分で直さない（→ 制約）

名前の確認が済んだら、**この run の執筆者（レッスン `.meta.json` の `author`）を1回だけ聞く。** 聞いた値はこの run の全レッスンに使う。レッスンごとに聞き直さない。

### 受講形態が計画書に無いときだけ、もう1問

上の一覧で `《未設定》` になったコースがあるときに限り、**執筆者の問いとは別に、1回だけ**受講形態を確定させる。全コースに計画書の記載があるなら**この問いは出さない**。

```
次のコースは計画書に受講形態（style）がありません。

  GitHub入門コース          → self-study
  GitHubリモート連携コース  → self-study

このままでよければ「はい」。違うものがあれば「入門は lecture」のように教えてください。
```

- **`author` と1問にまとめない。** `author` は run に1つで答えが1語、`style` はコースごとに変わりうる。まとめると2つの粒度を1つの返信に畳ませることになる
- **既定は `self-study`** を添えて出す。白紙で聞くより速く、コース単位で上書きもできる
- **対象コースが複数でも問いは1回。** コースごとに聞き直さない
- 確定した値は `.meta.json` の `style` に書く。**計画書は書き換えない**（→ 制約）。代わりに**ふりかえりで計画書への反映を提案する**（→ フェーズ8）

ここでの対話は最小限にする。**必ず1問ずつ**聞き、まとめて質問しない。聞くのは、計画書から読み取れないもの——たとえ話に使える現場の場面、受講者がつまずいた実例、扱ってよい社内固有の範囲。計画書に書いてあることは聞かない。

**社内情報の中身はここでは聞かない。** フェーズ3の3段梯子（DB 検索 → 一括問合せ → 空欄）でまとめて解決する。

## フェーズ2: 情報収集

`creating-visual-explainers` の「ウェブで情報収集」ステップ（Step 3）に準拠する。検索は**2〜3回**に絞り、正確な定義・最新動向・具体例の観点で組み立てる。採用した情報の出典 URL を控え、本文に添える（書き方は `references/lesson-template.md`）。

## フェーズ3: 設計メモをファイルに書く

この実行の **run ディレクトリ**（`contents-work/runs/<yyyymmdd>-<slug>/`）を作り、その中に `design-note.md` として出力する。slug は計画書が定めたものを使う。**範囲をどれに決めてもファイル名は変わらない。**

run ディレクトリの作法は [`contracts/agent-write-contract.md`](../../../contracts/agent-write-contract.md) に従う。

### 先に、同じシリーズの過去 run を引き継ぐ

`contents-work/runs/` の設計メモを開き、**今回と同じシリーズを対象にしたものがあるか探す。** run ディレクトリ名からは対象が分からないので、中を読んで判断する。

見つかったら、そこで固定した**用語の呼び名とたとえの体系をそのまま引き継ぎ、今回の設計メモにも書く。** 同じ概念に新しいたとえを作らない——コース単位で回す以上、シリーズの一貫性は run をまたいで守るしかない。

**そのシリーズの初回なら、引き継ぐものは無い。** これは正常で、何も無いまま進める。

### 社内データを3段梯子で解決する

本文に社内データが要る箇所を全列挙し、**承認ゲートの前に**3段で解決を済ませる。執筆中にユーザーへ都度質問しない。

1. **段1: DB 検索。** 実行環境から届く社内コンテキストのバックエンドを検索する——`local-db/context-items.json` があれば読んで走査し、`.env.local` に `DATABASE_URL` があれば使い捨てスクリプトで Neon を検索する（`@neondatabase/serverless` は依存に既存）。両方届けば結果をマージする。**どちらが運用中の正本かは判定しない**——読み取りのマージは無害で、判定材料（保存先設定）はスキルから見えない
2. **段2: 一括問合せ。** 段1で解決しない箇所をまとめて1回ユーザーに聞く。聞くのは**本文・ソースURL・ソース最終更新日（任意）**の3点だけ。title・tags・本文の整形は自動で行う
3. **段3: 空欄。** それでも残った箇所を空欄として設計する（記法は `references/lesson-template.md`）

**社内コンテキストの店には書き込まない。** 段2で聞き取った内容は run ディレクトリの `context-outbox.json` に退避する——登録 API（`POST /api/context/items`）の入力スキーマに一致する配列（`title` / `body` / `tags` / `source_url` / `source_last_updated_at`〔null 可〕）で、**`id` は書かない**（バックエンドごとに独立採番のため、登録は必ず新規作成を通す）。書き出したら、dx-training-studio で正規の保存先へ登録するようメッセージで促す。

段1で使ったアイテムは本文転記時に出典を添える（書き方は `references/lesson-template.md` の「出典」）。

### 設計メモに書くもの

- レッスンごとの**要求と供給** — そのレッスンが前提とする知識と、それがどのレッスンで供給されるか。供給元のない要求はここで見つける
- **公開サイト向けメタの案** — この run で作るシリーズ・コースの `slug` / `description` / `catch`（書き方は「出力規約」）。公開サイトのトップページに出る文面なので、ディレクトリを作る前に承認ゲートで人の目を通す。`catch` は用語のたとえと同じ語彙で揃える
- **用語ごとに固定するたとえ**（コース内の全レッスンで守る）
- 各レッスンの**声かけレベル**（判定材料は計画書の構成と `style`。基準は `references/lesson-template.md`）
- **社内データの解決表** — 社内データが要る箇所ごとに、どの段で解決したか。段1は使用アイテム（id・title・source_url）と使い先、段2は聞き取り内容（outbox 行き）、段3は空欄の3種の別。**空欄と outbox がそのまま後工程への作業リストになる**
- 各レッスンの節構成と、その節で解く読者の問い

**チャットに流して済ませない。** 社内素材の作業リストは別の環境へ持っていくものなので、ファイルとして残らないと届かない。受け渡しの手段は問わない。

## フェーズ4: 詰めの対話と承認ゲート

設計メモを提示し、1問ずつ詰める。空欄の数もここで見えるので、多すぎるなら範囲や扱いを見直す。

**ユーザーの承認を得るまで執筆に進まない。** 上流が濁っていれば下流でどれだけ磨いても濁ったまま残る。

## フェーズ5: 執筆

**1レッスンずつ順次書き、1本書き終えるたびにファイルへ保存する。** 複数レッスンをまとめて生成しない——量を増やすとアテンションが分散し、後半の選択肢が雑になり解説が薄くなる。

副次的に、途中で止まっても再開でき、次のレッスンが前のレッスンを読めるので二重説明を実際に避けられる。**書く前に、同じコースの既に書いたレッスンを読む。**

型は `references/lesson-template.md`、質は `references/design-principles.md` に従う。

### 1本書き終えたら、設計メモと突き合わせる

自己レビューに回す**前**に、書いたレッスンと設計メモの該当箇所を並べて確認する。

- **用語の呼び名** — 設計メモの用語表と本文が一致しているか
- **空欄の一覧（解決表の段3）** — 空欄にする計画だった箇所が、本文で空欄を介さない断定文になっていないか。段1で解決した箇所には出典が添えられているか
- **画像計画** — 置く予定だった図が本文にあるか。図を置く節に**コメントが実在するか**（本文だけ書いてコメントを落としていないか）
- **声かけ** — 設計メモで決めたレベルどおりに、冒頭と結びが書けているか

ずれを見つけたらここで直す。**レビューに回してから気づくのでは遅い**——執筆者が自分で気づける種類のずれで、レビューの指摘枠を使う価値がない。

### 執筆中に新しい社内データが必要になったら

設計メモに無い社内データが必要だと分かったら、**まず段1（DB 検索）で解決を試みる**。段2（ユーザーへの問合せ）は執筆中にはやらない——執筆フローを細切れにしない。見つかれば本文素材として、見つからなければ空欄として、**本文に書く前に提示して承認を得る**。承認後、**設計メモ（解決表）と本文を同時に更新する**。

黙って本文に足すと設計メモとずれ、後工程の作業リストが不完全になる。承認なしに設計メモだけを更新することもしない。

## フェーズ6: 自己レビュー

1レッスン書き終えるごとに、**フレッシュな文脈**でレビューする。**指摘は run ディレクトリの `reviews/<レッスン名>.md` として残す**——チャットに流すと、何を採用し何を却下したかが後から追えない。

- **レビュー役に本文を修正させない。** 指摘だけを受け取り、反映するかは執筆側が判断する
- 全体評価で終わらせず、**初学者が頭から読んだときの反応を本文の順に**出す。俯瞰でまとめると冒頭の分かりにくさが消える
- レビューは根本的なやり直しを提案しない。「問題なし」は完璧を意味しない

## フェーズ7: 曼陀羅

**範囲に関わらず最後に必ず通る。** レッスン1本だけを作った場合も、それがコース内のどの位置に入るかを確認する。**案は run ディレクトリに `mandala.md` として残す。**

- 同一シリーズ内の順序は `.meta.json` の `order` で表す
- **シリーズをまたぐ接続は提案に留める。** `cross_series_prev` / `cross_series_next` を書き込まない

### 図を描く

`mandala.md` には**アスキーアートの図を必ず入れる。** 表だけでは、何が確定していて何が提案のままかを読み比べないと分からない。

- **シリーズ内のコースの並びと、シリーズをまたぐ辺を1枚に収める**
- **書き込み済みの辺と、提案に留まる辺を描き分ける**（実線と破線など）。凡例を図に添える。`.meta.json` に反映した順序は確定、相手のコースが未作成で張れない辺は提案
- **今回の run で作った範囲が図のどこかを示す**
- 図法は計画書第3章と [`dx-training-plan/references/mandala-guide.md`](../dx-training-plan/references/mandala-guide.md) に従う。独自の描き方を作らない

CJK 幅で枠が多少ずれても構わない。**接続の向きと、確定・提案の別が読めることを優先する。**

## フェーズ8: ふりかえり

この run で気づいた**スキル自体の改善候補**を挙げ、`references/` に反映するかをユーザーに問う。

- 拾うのは「次回も同じことが起きる」もの——守りにくかったルール、書かれていなくて迷った作法、レビューで繰り返し出た指摘
- 今回限りの事情（この題材固有の判断、この計画書の癖）は挙げない
- **承認されたものだけを `references/` に反映する。** 却下された候補はどこにも残さない

### 候補は名前だけで問わない

1つずつ、次の3点を添えてから可否を問う。

| 添えるもの | 中身 |
| ---------- | ------------------------------------------------------------------------ |
| 根拠       | フェーズ6のレビューのどの指摘・どの場面で起きたか。ファイル名で指せば足りる |
| 反映先     | `references/` のどのファイルのどの節に入るか                              |
| 反映文案   | 承認されたらそのまま貼る文面                                              |

**文案を見せずに問わない。** 見出しだけを示されても、ユーザーは何を承認したのか分からないまま答えることになる。判断材料になるのは候補の名前ではなく、**その文が `references/` に載った後で次の run がどう変わるか**である。

**ふりかえりの記録ファイルを作らない。** 学びの受け皿は `references/` と模範解答の2つだけで、run ごとに書き溜めると同じことが何箇所にも散り、やがて食い違う。

**`context-outbox.json` が空でなければ、dx-training-studio で正規の保存先へ登録するよう改めて促す。** 空欄の一覧と同じ、run ディレクトリに残る持ち帰り物として扱う。

**フェーズ1で受講形態を確定させたコースがあれば、計画書への反映を提案する。** この run では `.meta.json` にだけ書いており、計画書は `style` が空のまま。放っておくと次の run でまた同じことを聞くことになる。書き換えるのは人（または `dx-training-plan`）。

## 最後に: 模範解答への昇格

`references/model-answer/` は**存在しなくても空でもエラーにしない。** 無ければテンプレートと執筆原則だけで書く。

実行の最後に、生成した草稿のうち出来の良い1本を模範解答に昇格させるかをユーザーに問う。

## 出力規約

出力先は `contents/<シリーズ名>/<コース名>/<レッスン名>/contents.md`。ディレクトリごと作る。

**ディレクトリ名は計画書の「コース仕様」表のシリーズ名・コース名と、「レッスン仕様」表のレッスン名をそのまま使う。** slug は使わない——名前の正本はディレクトリ名。

- 計画書の全体構造ツリーにある「〜シリーズ」「〜コース」という表記は**使わない**。コース仕様表の短い名前が正
- `L01` のような ID、`【撮】` `【録】` の印、`☆` は名前に含めない
- **名前は計画書の命名規則に従う**（ファイル名に使えない文字を含まない）。含んでいたらフェーズ1の名前確認ゲートで指摘し、自分で書き換えない

コースの `.meta.json` には **`order` `target` `slug` `description` `catch` `style` を書く**。新しいシリーズを作る run では、シリーズの `.meta.json` にも `slug` `description` `catch` を書く（`style` はコース単位の属性なのでシリーズには書かない）。レッスンのメタ（`slug` `status` `description` `tags` `estimated_minutes` `author`）は**レッスンフォルダの `.meta.json`** に書く——`contents.md` は本文のみで、frontmatter を書かない（形式は `references/lesson-template.md`）。

- `target` は計画書のコース仕様表の受講対象
- **`slug` は計画書の slug（`git/concepts` のような表記の該当階層）をそのまま転記する。** 自分で考えない。計画書に無ければフェーズ1の名前確認ゲートで確定させた値を使う
- **`description` はそのコース（シリーズ）で何ができるようになるかを 1〜2 文で書く。** 計画書の学習目標・ゴールから起こす。公開サイトのトップページに出る紹介文になる
- **`catch` は受講者の心を動かす短い一言**（15字前後）。設計メモで固定したたとえの語彙を使うと、シリーズ全体で言葉が揃う。`description` の要約にしない——説明は `description` の仕事
- **`style`（受講形態）は計画書のコース仕様表（第5章）・全体構造ツリー（第3章の `《self-study》` 等）から転記する。** 値は `self-study` / `lecture` / `hands-on`（正本は `lib/schema.ts` の `COURSE_STYLES`）。**書かずにコースを作らない**——受講形態は曼陀羅のノードに出る受講者向けの情報で、抜けても原稿を読む限り気づけず、曼陀羅を開いて初めてわかる。計画書から読み取れないときはフェーズ1で確定させる（→ フェーズ1）
- `slug` `description` `catch` は**設計メモに書いて承認ゲートに乗せる**。ディレクトリを作る前に人の目を通す
- `id` は書かない——loader が無ければ採番し、既存キーを保ったまま書き戻す
- `cross_series_prev` / `cross_series_next` は書かない
- `cover`（シリーズのヒーロー画像）は書かない——画像は人が用意して指定する
- `name_en` / `description_en` / `catch_en` は書かない——翻訳は別工程
- `order` には**実在するディレクトリだけ**を計画書の順で並べる。まだ作っていないものを先回りして書かない——loader が実体に合わせて整理するため消える
- **後からコースやレッスンを足したら、親の `order` を計画書の順に直す。** 直さないと末尾に追加されて並びが崩れる。直してよいのは**このスキルが作ったディレクトリの `.meta.json`** だけ
- シリーズの並びを持つ `contents/.meta.json` は既存コンテンツと共有なので**触らない**。新しいシリーズは loader が末尾に追加する。並び替えが要るなら提案に留める

## 制約

- **既存の `contents/` を変更・削除しない。** 名前が衝突したら一覧を提示し、確認を得るまで書き込まない
- **`contents-work/plans/` の計画書と `dx-training-plan/` を変更しない。** 計画側の修正が要ると判断したら、実行せず提案する
- **`contracts/` を変更しない**
- **`references/design-principles.md` を変更しない**
- 出力は日本語
- **書込の境界とホストごとの制約は [`contracts/agent-write-contract.md`](../../../contracts/agent-write-contract.md) に従う**——書ける階層・保護されるフィールド・使えない機能の代替はすべて契約が正本。ここに再掲しない
