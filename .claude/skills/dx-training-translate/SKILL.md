# 教材英訳スキル

日本語が正本、英語は派生——翻訳は常に**日本語 → 英語の一方通行**。鮮度は**処理対象を決めるゲートではなく参考情報**。未翻訳と古いものは常に処理し、翻訳済みのものを含めるかは1回だけ確認して人が決める。

## 責任範囲

| やる | やらない |
|---|---|
| `contents.en.md` の生成・更新（原文ハッシュ行つき） | **日本語正本の変更**（`contents.md`・日本語メタ） |
| `.meta.json` の `_en` フィールドと `en_source_hash` の記入 | `author` / `author_en` の記入——人名のローマ字表記は本人の流儀 |
| `changelog.en.md` の作成・不足エントリの追訳 | 構造キー（`id` / `order` / `slug` / `cross_series_*` / `is_start` / `is_goal`）の変更 |
| 進捗レポート（全体の残量・範囲の内訳・欠落フィールド）の提示 | 画像の生成・差し替え |
| 訳注コメントでの判断保留 | **コミット**——差分レビューと採否は人 |
| 訳した本文1本ごとの受講者読み（読みづらさの指摘） | **公開前レビュー**——用語のゆれ・リリース可否は `dx-training-review` の担当 |
| 規約の改善候補を**報告に載せる**こと | **契約・自身の `SKILL.md`・他スキルの文書の変更**——勝手に書き換わる規約は実行結果をぶれさせる |

## 依存

- `contracts/translation-contract.md` — **翻訳規則と用語集の正本。実行前に必ず全文を読む。**規則はここに一切複製しない
- `references/scan-freshness.mts` — 鮮度と欠落の走査（読み取り専用・**常に全体**）。判定・ハッシュ・階層ごとの `_en` キー対応は Studio の正本 lib（`studio/lib/translation/freshness.ts`）を import して計算する——**自前でハッシュを計算したり、キー一覧を書き写したりしないこと**
- `contents/` — 対象。レッスン本文・各階層 `.meta.json`・`changelog.md`

## 進め方

このチェックリストを写して進捗を管理する。

- [ ] フェーズ1: 範囲を確認する
- [ ] フェーズ2: 契約を読む
- [ ] フェーズ3: 鮮度を走査しレポートを提示して対象を決める
- [ ] フェーズ4: 対象を差分翻訳して書き込む
- [ ] フェーズ5: 自己点検（機械照合＋受講者読み）と完了報告

### フェーズ1: 範囲を確認する

範囲は4種: **全体／シリーズ指定／コース指定／レッスン指定**（いずれも配下のメタ含む）。依頼文から明確なら聞き直さず、曖昧なときだけ1回で確認する。**changelog はどの範囲でも鮮度チェックに含める**（コース単位の運用で英語版 changelog が置き去りになるのを防ぐ）。

### フェーズ2: 契約を読む

`contracts/translation-contract.md` を**全文**読む。英訳するもの・変えないもの・迷ったときの訳注（`<!-- 訳注: … -->`）・トーン・用語集のすべてがここにある。

### フェーズ3: 鮮度を走査しレポートを提示して対象を決める

```bash
node --experimental-strip-types .claude/skills/dx-training-translate/references/scan-freshness.mts [シリーズ名] [コース名] [レッスン名]
```

（引数省略＝範囲も全体。cwd はどこでもよい——スクリプトが自分の位置から解決する）

⚠ **走査は引数によらず常に `contents/` 全体**。引数は処理対象の印付け（各ユニットの `inScope`）であって走査の絞り込みではない——絞ると「あと何件残っているか」の分母が範囲ごとに変わり、進捗が読めなくなる。

出力から次の表を組んでユーザーへ提示してから翻訳に入る。**この整形はスキルの仕事**（スクリプトは JSON を出すだけ）。

```
英訳の進捗（全体）
              完了   未翻訳   古い    計
  本文          1       8       0      9      ← total.body
  メタ          2      15       0     17      ← total.meta
  変更履歴      —       —      最新    1      ← total.changelog

今回の範囲: Git基礎シリーズ
  本文          0       6       0      6      ← inScope.body
  メタ          0      10       0     10      ← inScope.meta

⚠ 「完了」でも欠けているフィールド                ← missingEnFields
  （無ければこの節ごと出さない）

※ 未完成レッスン（作成中 4 本）も分母に含む      ← lessonStatusCounts
```

- **`missingEnFields` は「翻訳済みに見えるのに欠けている」ものだけ**が載る（未翻訳ユニットは除外済み）。鮮度が `fresh` でも出る——鮮度は原文への追随、欠落は記入の完全性で**別の軸**
- **`inScope` かつ `untranslated` / `stale` のユニットは常に処理対象**。範囲外は報告に含めるだけで**翻訳しない**
- 未完成（open / in_progress）のレッスンも対象に含める——status で絞らない（status は日英共有なので、未完成の英語版は公開サイトで自動的に「作成中」表示になる）
- **この走査出力はフェーズ5 まで保持する**（前後比較に使う）

**範囲内に `fresh`（翻訳済み）のユニットがあるときだけ**、レポートの末尾で1回確認してから翻訳に入る。無ければ聞かずに進む。依頼文で扱いが明示されているとき（「全部訳して」「未翻訳だけ」等）も聞かない。

```
今回の範囲に「最新」が n 本 / m 件あります。どう扱いますか
  (a) 未翻訳＋古いものだけ                      ← 既定
  (b) 最新も含めて、現行の契約で再点検・更新
  (c) ユニットを選ぶ
```

⚠ **鮮度は「あと何が残っているか」を示す参考情報であって、処理対象を決めるゲートではない。** 契約（用語集・名前の規則・トーン）は運用で育つので、最新のユニットにも直すべき箇所が生まれる。それを人が判断できるようにするのがこの確認。

### フェーズ4: 対象を差分翻訳して書き込む

**1ユニットずつ**処理する。走査出力の `metaHashToWrite` / `bodyHashToWrite` をそのまま使う（原文が変わっていなければ既存のハッシュと同じ値になる）。

⚠ **既訳があるユニットは訳し直さない。** 直すのは (1) 原文の変更に対応する箇所 (2) **現行の契約に違反している箇所**（用語集・名前の規則・トーン・「英訳するもの／変えないもの」）の2つだけ。他の段落は一語も変えない——最新のユニットを (b)/(c) で処理するときも同じ規則。

**本文（`contents.en.md`）**:

1. `contents.md` 全文と、既訳があれば `contents.en.md`（1行目のハッシュ行は訳文ではない）を読む
2. 契約に従って翻訳する（既訳があるときは上の2点だけを直す）
3. 次の形で全文を書く（1行目が走査出力の `bodyHashToWrite`）:

   ```
   <!-- source: sha256:… -->

   （訳文）
   ```

**メタ（`.meta.json`）**:

1. 既存の `.meta.json` を読む
2. 対象キー**だけ**を差し替えたオブジェクトを 2 スペースインデントで書き戻す（他のキーは順序ごと保全）
   - 全体: `name_en` / `description_en`、シリーズ: `name_en` / `catch_en` / `description_en`、コース: `name_en` / `catch_en` / `description_en` / `target_en`、レッスン: `name_en` / `description_en`
   - 名前（`name_en`）の原文は**フォルダ名**
   - `en_source_hash` に走査出力の `metaHashToWrite` を書く

**changelog（`changelog.en.md`）**:

- 状態が `untranslated` → 全文（ヘッダー含む）を翻訳して新規作成
- 状態が `stale` → 英語側の先頭エントリより新しい日本語エントリ**だけ**を訳し、ヘッダー直後（既存エントリ群の前）に挿入。**既存の英訳エントリには触れない**
- 見出しの日付（`## YYYY-MM-DD`）は変えない。ハッシュ行は書かない
- シリーズ・コース・レッスンの名前は契約の「既存の英語表記に合わせる」に従う（自分で訳さない）

### フェーズ5: 自己点検と完了報告

**まず機械で照合する**（対訳の忠実さ。原文を見てよい）。

- 各本文について、原文と訳文の**見出し数**を突き合わせる（大きく減っていたら訳し漏れを疑って直す）
- 画像パス・URL・コードブロックが原文と一致していることを1本ずつ確認する
- 走査スクリプトをもう一度実行し、処理したユニットが `fresh` になったことを確かめる

**次に受講者として読ませる**（英文の読みやすさ。原文を見てはいけない）。

処理した本文1本ごとに、サブエージェントへ **`contents.en.md` だけ**を渡して本文の順に心の声を出させる。

- ⚠ **原文・`translation-contract.md`・用語集を渡さない。** 原文を知った読者は「原文がこうだからこの英語で正しい」と読めてしまい、不自然さに気づけない。**渡さないことがこの検査の設計そのもの**。心の声の出させ方は `dx-training-review` の `references/quality-checks.md`（U）と `references/integrity-checks.md`（心の声ウォークスルー）が正本——**ここに写さない**
- **指摘だけを受け取る。** サブエージェントに訳文を修正させない。採否は訳者が決める
- ⚠ **今回処理しなかったユニットへの指摘は訳文に反映しない。** 触っていないファイルまで直すと、人が読む git 差分が今回の変更を超えて膨らみ、「今回何が変わったのか」が読めなくなる。それらの指摘は**完了報告に参考として載せる**だけにして、判断を人へ渡す（処理対象に含めたユニットは、その本文全体が採否の対象）

⚠ ここで見るのは**1本の中の読みづらさ**まで。用語のゆれ・メタと本文の食い違い・リリース可否は**複数本を並べないと見えない**ので `dx-training-review` の担当（公開前レビュー）。二重に抱え込まない。

- 報告する: 書き込んだファイルの一覧（新規翻訳／更新の別）・訳注を残した箇所・受講者読みの指摘（採用分と参考分を分けて）・気づいたこと。**コミットはしない**——採否は人が git 差分で行う
- **既訳（`fresh`）を処理した場合は、ユニットごとの変更行数**（`git diff --numstat` の値）**も並べる。** 人が「今回の意図を超えて差分が膨らんでいないか」を見るための数字で、閾値による判定はしない（0 行＝直すべき違反が無かった、も正常）

**進捗の前後比較も報告する。** フェーズ3 で保持した走査出力と、上の再走査の出力を同じ形式で並べ、今回進んだ量と残量を示す（⚠ 走査を追加で実行しない——再走査の結果を使い回す）。

```
              実行前        実行後        残り
  本文        1 / 9        4 / 9        5 本
  メタ        2 / 17       6 / 17       11 件
  変更履歴    最新         最新         —
```

**最後に規約の改善候補を出す。** 受講者読みで**採用した**指摘のうち、他のレッスンや将来の翻訳にも効くものを、個別具体の修正ではなく**抽象度の高い規則案**にまとめて載せる。

絞り込みは3つ: (1) そのレッスン固有でないこと (2) 既存の契約・用語集で既に言えていないこと (3) 読者の反応であって規範の誤りではないもの（用語集どおりの語への「唐突」等）を除くこと。**最大3件**。無ければ「規約候補: なし」の一行で終える——0 件が正常。

```
候補 1 ／ 訳す規則 ／ 宛先: contracts/translation-contract.md
  規則案: 原文で同じ語が一般動作と用語の両方に使われるとき、英語では訳し分ける
  根拠:   履歴と差分を読む — 「保存」が Ctrl+S と commit の両方を指し、同一手順と誤読された
```

種別は**訳す規則／用語／書く規則／検査する規則**。宛先は種別で決まり、書く規則は `dx-training-create`、検査する規則は `dx-training-review` になる。

⚠ **候補はどこへも書かない。報告に載せるだけ。** 承認を取って書き込むこともしない——実行のたびに規約が動くと、同じ入力でも結果が変わる。更新は人が `creating-skills` や `openspec-explore` で横断的に見直すときに行う。
