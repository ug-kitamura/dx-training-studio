# 曼陀羅ガイド

曼陀羅は、コースをノードとする有向グラフのロードマップ。受講者はこの地図を見て、自分のペースで進む順路を選ぶ。

**このガイドを読むタイミング**: トレーニング構成（シリーズ → コース → レッスン）が固まった後。構成を設計している間は読まない。

## SSoT について

規則の正本は `dx-training-studio/lib/course-flow.ts` の実装。このガイドはその要旨を転記したもので、**意図的な SSoT 逸脱**である。

理由は、スキルが実行環境を問わず単体で動くことを優先したため。ファイル読取ができない環境でも構成案を出せる必要がある。

そのため、このガイドは**規則の細部まで写していない**。関数名やコードレベルの挙動には踏み込まず、設計判断に必要な粒度に留めてある。厳密な検証は dx-training-studio 本体が行うので、企画段階では以下の内容で足りる。判断に迷う構成に出会ったら、正本を確認するようユーザーに促すこと。

## 何が表現できるか

```
シリーズ                          シリーズ
┌──────────────┐                ┌──────────────┐
│ コースA      │                │ コースX      │
│    ↓         │  ← 直列のみ    │    ↓         │
│ コースB      │                │ コースY      │
│    ↓         │                └──────────────┘
│ コースC      │ ─── 別シリーズへの辺 ───▶
└──────────────┘
```

| 単位 | 表現できること |
|---|---|
| シリーズ内 | コースの並び順そのものが依存関係になる。**直列の鎖のみ** |
| シリーズ間 | 明示的に辺を張る。分岐・合流はここでしか表現できない |

**シリーズ内では分岐も合流もできない。** 並び順を決めれば、その順に一本道でつながる。

この性質から、**分岐させたい単位でシリーズを切る**という設計指針が出る。「同じ技術領域だが、ここから2方向に分かれてほしい」という構成は、シリーズを分けないと表現できない。

## 辺の張り方の制約

### シリーズAからシリーズBへの辺は、全体で1本だけ

```
   Gitシリーズ                GitHubシリーズ
   ┌─────────┐                ┌─────────┐
   │ コース1 │                │ コースX │
   │ コース2 │ ──── ✓ ──────▶ │ コースY │
   │ コース3 │ ──── ✗ ──────▶ │ コースZ │  ← 2本目は張れない
   └─────────┘                └─────────┘
```

同じシリーズの組み合わせに複数の辺は張れない。1本張ると、同じ組み合わせの他の辺は自動的に外される。

**設計上の意味**: 「AシリーズのX章とY章の両方が、BシリーズのZ章の前提だ」という依存は表現できない。表現したい場合は、シリーズの切り方そのものを見直すか、曼陀羅では諦めてレッスン本文の注意書きで補う。

### 循環は禁止

保存時に検出され、循環を作る編集は拒否される。

### 別シリーズ宛なら複数本出せる

1つのコースから、**異なるシリーズ**へ向けてなら複数の辺を出せる。

```
              ┌──▶ AIシリーズ
   入門コース ├──▶ Gitシリーズ        ← 3本とも宛先シリーズが異なるので OK
              └──▶ Pythonシリーズ
```

合流も同じで、**異なるシリーズから**なら1つのコースへ複数本入れられる。

## 進行ルール

- あるコースに入るには、そこへ合流する**全ての辺の元コースが完了済み**である必要がある
- その範囲内なら、受講者はどのブランチから進めてもよい
- 完了を求めるかどうか、どこまで厳密に運用するかは計画側で決める（強制ゲートにしない運用もありうる）
- **任意コース（行き止まり）を置くなら、完了記録に必須／任意の区別が要る。**「全コース完了」を求める運用とは衝突するため、どちらを採るかは計画側で決める

---

## 順路は内容から決める

**どのコースをどの順で進めるかは、曼陀羅の制約ではなく内容の依存から決まる。** あるコースが別のコースで供給される環境やスキルを要求しているなら、要求を満たすコースを前に置く。

その判断には `verification.md` の**要求と供給の突き合わせ**を使う。フェーズ2で作った表をそのまま辺の起点判断に再利用できる。

このガイドが扱うのは**表現できるかどうか**であって、**何を先に学ぶべきか**ではない。後者は内容の問題であり、先に決まっているべきもの。

## 分岐・合流の型

### 起点から扇状に分岐する

```
   ┌────────────┐
   │ 入門       │
   └─┬───┬───┬──┘
     ▼   ▼   ▼
    A   B   C      並行して進められる
```

導入を1つ通した後、独立に学べる領域へ散らす。最も素直な形。

### 途中から派生する

```
   A1 → A2 → A3
         └──────▶ B1 → B2
```

Aシリーズの途中を前提に、Bシリーズが始まる。Aの残りとBは並行して進められる。

**注意**: A→B の辺は1本しか張れないので、Bの後半がAの後半にも依存する場合、その依存は表現できない。

### 終端で合流する

```
   A3 ─┐
   B2 ─┼──▶ 最終コース
   C1 ─┘
```

複数の領域を修めてから最後の関門に入る。合流元が異なるシリーズであれば何本でも入れられる。

### 任意コースにする

```
   初級 → 中級 → 上級      ← 出口の辺なし
           │
           └──────▶ 別シリーズ
```

上級コースは**誰の前提でもない**ので、やらなくても他に影響しない。進みたい人は進み、そうでない人は別シリーズへ抜ける。**上級者向けや補足の内容を任意トレーニングとして置ける。**

**任意にしたいコースはシリーズの末尾に置く。** シリーズ内は直列鎖しか張れないため、中間に置くと後続コースまで道連れで任意になる。

分岐元（上の図では中級）が、**シリーズ内の後続とシリーズ間の辺を同時に持つ**のがこの型の要点。

### 経由による暗黙の必須化

```
   Gitシリーズ ──▶ GitHubシリーズ ──▶ ゴール
```

Git はゴールへの直接の辺を持たないが、GitHub の前提になっているため、結果的に Git 全コースが必須になる。**辺を増やさずに必須化できる**ので、辺1本制約の下では有効な手。

## チェック項目

構成を曼陀羅に写したら、以下を確認して結果を計画書に書く。厳密な検証は不要で、目視で追える範囲でよい。

- [ ] **循環がないか** — たどって元のコースに戻ってこないか
- [ ] **ゴールに到達できるか** — すべてのシリーズが、辺をたどってゴールに至るか
- [ ] **行き止まりが意図的か** — 出口の辺を持たないコースは、任意コースとして設計したものか
- [ ] **到達不能なコースがないか** — 入口の辺を持たず、かつ起点でもないコースがないか
- [ ] **辺の重複がないか** — 同じシリーズの組み合わせに2本以上の辺を張っていないか

### 行き止まりは欠陥ではない

**行き止まりの存在自体は問題ない。** 任意コースを表現する手段になる（→「任意コースにする」）。問うべきは有無ではなく**意図**。

```
グラフから分かること      出口の辺がない
グラフから分からないこと   それが任意なのか、辺の張り忘れなのか
                          ↓
                    計画書に書くしかない
```

**意図的な行き止まりと事故の行き止まりは、グラフとしてまったく同じ形をしている。** 区別できるのは計画書の記述だけなので、任意コースにしたときは**その旨と理由を必ず書く**。理由が書けないなら、それは必須か不要かのどちらかである。

**必須にしたいコースを行き止まりにしてはならない。** 受講者が飛ばしても修了できてしまう。必須にするなら、別シリーズ宛の辺を足すか、経由による暗黙の必須化が効く位置に置き直す。

## 構成と衝突したとき

**トレーニング構成が曼陀羅構成に優先する。**

```
構成が曼陀羅で表現できない
        │
        ▼
  ① まず曼陀羅側を妥協する
     ・依存の一部を辺で表現するのを諦め、レッスン本文の注意書きで補う
     ・計画書の未決事項として残す
        │
        ▼（それでも解決しないとき）
  ② 構成の変更を検討する
     ・教育上の理由を示す
     ・ユーザーの承認を得る
```

**制約は問いを立てる材料にしてよいが、答えの根拠にしてはならない。**

たとえば「辺が1本しか張れない」という制約から「この内容をどちらのシリーズに置くか」という問いが立つのは健全。しかし、その答えを「辺が1本だから」で決めてはいけない。答えは常に学習設計上の理由で選ぶ。
