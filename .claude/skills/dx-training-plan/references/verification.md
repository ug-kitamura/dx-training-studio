# 検証手順

計画の抜け漏れを検出するための手順。フェーズ2で表を作り、フェーズ3で再利用し、フェーズ5で通しの確認に使う。

## 目次

- 要求と供給の突き合わせ
- 変更波及マップ
- レビュー観点

---

## 要求と供給の突き合わせ

各レッスン・コースが**供給するもの**（習得済みになるスキル、使えるようになるツールや状態）と、**要求するもの**（実行に必要な前提）を並べて突き合わせる。

### 表の作り方

**受講者像を0行目に置く。** 受講者が最初から持っているものは、トレーニングが供給しなくてよい。ここを起点にしないと「既に知っていることを教えている」冗長が見えない。

```
        供給するもの              要求するもの              判定
──────────────────────────────────────────────────────────────
受講者像 プログラミングの基礎      —                       ← 0行目（初期供給）
        Python は未経験
L02     chocolatey               —
L03     VSCode                   chocolatey ✓L02          OK
L07     commit できる             Git ✓ / エディタ ✓L03     OK
L13     push できる               README を書ける ✗         供給元なし
L19     スクリプトを実行できる      uv ✓L18                  OK
L20     Python の変数と型          —                        受講者像と重複か？
```

供給は「レッスンを終えた受講者が何をできるようになるか」、要求は「そのレッスンの手順や演習を実行するのに何が要るか」。**完成物から逆算して要求を洗う**と漏れにくい。

### 検出する3種

| 種別 | 条件 | 対処 |
|---|---|---|
| **供給元なし** | 要求されているが、他のどのレッスンでも供給されず、受講者像にも含まれない | 供給するレッスンを足すか、受講者像を見直すかをユーザーに問う |
| **順序の逆転** | 供給するレッスンが、要求するレッスンより後ろにある | 入れ替えを提案する |
| **受講者像との冗長** | 受講者像が習得済みとしている内容を、レッスンが改めて教えている | 受講者像とレッスンのどちらを直すかをユーザーに問う |

いずれも**検出して提示するまでが役割**で、どちらを直すかは人が決める。

### いつ作り、いつ使うか

```
フェーズ2  表を作る
           └→ レッスン順・コース順を決める

フェーズ3  同じ表を再利用
           └→ どのコースからどのシリーズへ辺を張るかを決める
```

作り直す必要はない。粒度が違うだけで、同じ突き合わせを2階層で使う。

### 曼陀羅の制約とは別物

**学習上の依存と、曼陀羅の表現上の制約を混同しない。**

| | 例 | 参照してよいフェーズ |
|---|---|---|
| 学習上の依存 | uv を入れないと python コマンドは試せない | フェーズ2から |
| 曼陀羅の表現上の制約 | 辺は同一シリーズペアにつき1本 | フェーズ3のみ |

「フェーズ2で曼陀羅を見ない」という規定は後者を禁じているのであって、**依存を考えることを妨げない**。順序は内容から決まるものであり、曼陀羅の都合で決めるものではない。

## 変更波及マップ

対話の途中で決定が変わったら、下表に従って再チェックする。**構成が変わったのに時間予算や曼陀羅を据え置かない。**

| 変わったもの | 再チェックするもの |
|---|---|
| ハンズオンの題材・完成物 | 要求と供給の突き合わせ（必要スキルが変わる）／逆算で組んだレッスンの中身 |
| レッスンの増減 | 時間予算の集計／調整枠の残り |
| **コースの追加・分割・統合** | **曼陀羅の辺**／`style` の記入と一貫性／時間予算／コース仕様の表 |
| 学習形態の変更（独学 ↔ 集合） | `style`／曼陀羅の ☆／時間予算の集合・自己学習の振り分け |
| 技術スタックの変更 | 要求と供給の突き合わせ／レッスンの順序 |
| 環境制約の判明（申請・リードタイム等） | レッスンの内容と順序／分岐の起点／未決事項 |

一箇所の変更が複数段に波及することがある。コースを1つ足すと、辺・形態・時間・番号付けまで動く。

## レビュー観点

フェーズ5で計画書に当てる。**指摘は報告するに留め、計画書を書き換えない。** 直すかどうかはユーザーが判断する。

### 確認する項目

- **要求と供給の未解決分** — 検出したのに解消も明記もされていない箇所が残っていないか
- **時間予算** — レッスンの増減が集計に反映されているか。目標・上限に対する判定と調整枠の残りが書かれているか
- **`style` の記入漏れ** — 全コースに受講形態（`style`）が書かれているか。抜けているコースは名前を挙げて指摘する。値は `self-study` / `lecture` / `hands-on`（正本は `studio/lib/schema.ts` の `COURSE_STYLES`）。ここで埋めておかないと、`dx-training-create` が実行時にユーザーへ問い返すことになる
- **`style` の一貫性** — 同一シリーズ内で受講形態が揃っているか。揃っていない場合、理由が書かれているか
- **却下理由の記録漏れ** — 対話で複数案から選んだ判断が、採用案・却下案・却下理由とともに残っているか
- **画像素材の積算** — 人手が要るレッスンの本数が制作体制に反映されているか
- **未決事項** — 「未定」だけで終わらず、決まらないと何が確定しないかが書かれているか

### 設計原則の扱い

**「原則に従っているか」ではなく「原則から逸脱している箇所に理由が書かれているか」を見る。**

意図的な逸脱は正しい判断でありうる。理由を明記したうえで原則を外れているなら、**それを指摘してはならない**。指摘対象は無自覚な逸脱だけ。

| 状態 | 判定 |
|---|---|
| 原則どおり | 指摘しない |
| 原則から外れ、決定の根拠の章に理由がある | **指摘しない** |
| 原則から外れ、理由がどこにもない | 逸脱箇所と対応する原則を示して報告する |

### 報告の形

指摘と、確認できた項目の両方を出す。指摘ゼロでも「何を見たか」が分かる形にする。

```
## レビュー結果

⚠ 指摘 2件
  1. 6章 L13「push と pull」が README を要求するが、Markdown の供給元がない
  2. 1.2 受講者像「変数・制御構造の説明は不要」と L20〜L22 が矛盾

✓ 時間予算（自己学習345分・上限内、調整枠15分）
✓ style の記入（全12コース）と一貫性
✓ 却下理由の記録（19項目）
```
