# トレーニング計画スキル

トレーニングの構想を対話で深掘りし、**シリーズ → コース → レッスン**の構成と仕様を1本の計画書にまとめる。

## 責任範囲

| やる | やらない |
|---|---|
| 企画の深掘りと、構成・仕様の決定 | シリーズ・コースの実体作成（人が行う） |
| 計画書（markdown）の出力 | id の採番 |
| 曼陀羅構成の案と、最低限のチェック | 曼陀羅の厳密な検証 |
| **内容の依存から学習順路を提案する** | 本文・演習・画像の作り込み（レッスン草稿作成スキルが行う） |
| 各レッスンの大まかな構成と目安時間 | 画像の指示内容（同上。計画は素材の種別だけ分類する） |

## 既存構成の把握

`contents/` 配下のディレクトリと `.meta.json` を読み、既存のシリーズ・コース・レッスン構成を把握する。読めない環境や `contents/` が無い場合は、既存構成の有無をユーザーに確認してから進める。

**`contents-work/plans/` に既存の計画書があれば必ず読む。** 新しい計画が既存構成と**どう並ぶか、どこを置き換えるか**を必ず検討する。

---

## フェーズ0: 引き継ぎを確認する

既存計画書を土台にするときだけ実施する。**書いてある前提を黙って引き継がない。**

1. 既存計画書を読み、フェーズ1の各項目が**埋まっているか空欄か**を判定する
2. **埋まっている項目** → 引き継ぐ内容を要約して提示し、**1ターンで確認を取る**
3. **空欄の項目** → フェーズ1の作法（1問ずつ・推奨案つき）で個別に問う

```
既存計画から引き継ぐ前提です。変更したい項目はありますか。

  目的      ...
  受講者像  ...          ← 誤りはここで潰れる
  ゴール    ...
  環境と制約  （空欄 → 個別に伺います）
```

**書いてあるからこそ見逃す。** 空欄を埋めるだけでは、誤った前提を最後まで引きずる。

---

## フェーズ1: 上流を1問ずつ聞く

答えによって下流が大きく変わる。**必ず1問ずつ**聞き、まとめて質問しない。

1. **目的** — このトレーニングで受講者に何ができるようになってほしいか
2. **受講者像** — 誰が受けるか。前提スキルはどこまであるか
3. **ゴール / 完成物** — 修了時に「これができた」と言える具体物は何か
4. **環境と制約** — 下記の観点で、社内固有の事情を挙げてもらう
5. **総量** — 全体で何時間か。学習期間はどれくらいか
6. **題材の分割** — どの技術・テーマをシリーズとして立てるか
7. **集合形式の有無** — ハンズオン等の集合回を置くか。置くならどこに合流させるか
8. **運営体制** — 誰が支えるか。質問の受け口はあるか。改善提案をどう集めるか

**7 で集合回を置くと決めたときだけ、もう1問足す。** 受講者がキックオフに何を求めるかを聞く——トレーニングの目的・ゴール・修了時に得られるものへの期待と、進め方への不安・疑問。**典型候補を出して選んでもらう形式（複数選択・追記可）で、1問にまとめる。** 分けて聞くとフェーズ1が長くなる。答えはキックオフ回の**レッスン仕様**に書く。集合回を置かないなら、この問いは出さない。

**4 は選択式にしない。** 観点を並べて事実を挙げてもらう。ここが後出しになると、構成・曼陀羅・時間予算が丸ごと崩れる。

- 社内独自のシステムやルール
- 環境のセットアップ方法
- 申請手順と**リードタイム**
- セキュリティ上の制約
- コスト上の制約

問い方:

- **必ず推奨案を添える。** 「A と B のどちらですか」ではなく「A を推奨します。理由は〜。どう思いますか」
- 選択肢には、それを選んだときに**何が起きるか**を書く
- 質問には通し番号をふる
- ユーザーが「わからない」と答えたら、推奨案を採用してよいか確認して進む
- ユーザーが「もう十分」と言ったらフェーズ2へ進む

答えが前の決定と矛盾したときは、黙って辻褄を合わせず、**どこが衝突しているかを示してから**どちらを採るか聞く。

判断材料が要るときは `references/design-principles.md` を読む。

## フェーズ2: トレーニング構成を決める

**曼陀羅を一切見ない。** 目的とゴールからの逆算だけで、学習として最善の構成を組む。

決めるもの:

- シリーズの分割
- 各シリーズのコース分割
- 各コースのレッスン割りと時間配分
- slug

上流が決まれば下流はほぼ一意に決まる。1問ずつ聞かず、**案を提示して判定してもらう**。構成は文章で説明せず**アスキーアートで見せる**。複数案があるときは、各案をアスキーアートで並べて比較する。

**要求と供給を突き合わせる。** 各レッスン・コースが供給するものと要求するものを表に起こし、供給元のない要求・順序の逆転・受講者像との冗長を検出する。手順は `references/verification.md`。

「曼陀羅を見ない」は**表現上の制約**を見ないという意味で、**内容の依存を考えることを妨げない**。順序は内容から決まる。

---

## ゲート: 曼陀羅ガイドを読む

フェーズ3に入る前に **`references/mandala-guide.md` を読む**。

読む前に曼陀羅の分岐・合流を提案してはならない。

---

## フェーズ3: 曼陀羅に写す

フェーズ2で決めた構成を曼陀羅の依存グラフに落とし、ガイドのチェック項目を確認する。**辺の起点はフェーズ2で作った要求と供給の表から決める** — 要求を満たすコースから辺を張る。

**トレーニング構成が曼陀羅構成に優先する。**

表現できない構成に出会ったら、まず**曼陀羅側の表現を諦める**。構成を変えるのは最後の手段で、変えるときは必ず教育上の理由で選び、ユーザーの承認を得る。曼陀羅の制約のみを理由に構成を変更してはならない。

---

## フェーズ4: 計画書を出力

`references/plan-template.md` の章立てに従って計画書を出力する。時間予算の集計と、決定の根拠および却下した案は省略しない。

**出力先は `contents-work/plans/<yyyymmdd>-<slug>.md`。** slug は計画の対象を短く表す ASCII。既存の計画書を置き換える場合も上書きせず新しい日付で出し、本文の冒頭で前版を参照する。置き場の役割と作法は [`contracts/agent-write-contract.md`](../../../contracts/agent-write-contract.md) に従う。

---

## フェーズ5: 自己レビュー

出力した計画書に `references/verification.md` のレビュー観点を当て、**結果を報告して完了する。**

- **計画書を書き換えない。** 直すか、回し直すかはユーザーが判断する
- 設計原則は「従っているか」ではなく**「逸脱に理由が書かれているか」**を見る。理由のある意図的な逸脱は指摘しない
- 指摘と、確認できた項目の両方を出す

---

## 決定が変わったとき

対話の途中で決定が変わったら、`references/verification.md` の**変更波及マップ**を引いて再チェックする。構成が変わったのに時間予算や曼陀羅を据え置かない。

---

## 既定方針

以下は毎回問わず既定とする。ユーザーが明示的に変えたいと言ったときだけ変更する。

- シリーズ・コース・レッスンの名前は `references/plan-template.md` の「命名規則」に従う
- 1レッスンは 10〜15 分
- 全レッスンに5分以内の「やってみる」演習を入れる（読み物と選択式問題だけにしない）
- コースは学習フェーズで切る（概要 → 環境構築 → 基礎 → 応用）
- 学習形態（独学 / 集合）は**コース単位**で一貫させ、コースの `style` に持たせる
- 公開 URL は slug、永続キーは id を使う（slug は本スキルで決め、id は自動採番される）
- 手順の説明にはスクリーンショットや図を載せる。文章だけにしない
- 小演習には `<details>` で折りたたんだ解答例を1行つける。完成コード一式を渡すのは集合セッションのみ

---

## 制約

- ファイルや UI を直接変更しない。既存コンテンツの変更が必要な場合も、実行せず提案に留める
- 日本語で書く
