## 採点基準をその場で決める

**トンマナの細則を書き置かない。** 書けば、模範解答だけが更新されたときに食い違う。基準は実行のたびに立てる。

| 模範解答（`dx-training-create/references/model-answer/`） | 基準 |
|---|---|
| ある | 模範解答から読み取った文体 ＋ 対象コーパスの自己一貫性 |
| ない | 対象コーパスの自己一貫性のみ |

**模範解答が無くてもエラーにしない。** ですます・語尾・呼称の統一はもともと「揃っているか」の相対判定なので、コーパスの中だけで成立する。模範解答が昇格されれば、次の実行から基準が濃くなる。

**自己一貫性だけでは「全体が同じ方向に外れている」ものは見つからない。** これは既知の限界として受け入れ、見つからなかったことを「問題なし」と書かない。

内容品質（P）と、書いてはいけないもの（K に含める）の基準は `dx-training-create/references/design-principles.md`。**ここに書き写さない。**

## レッスン単位で見る

**1本ずつ、独立した文脈で読む。** まとめて読むと後半のレッスンほど指摘が雑になる。

対象は `dx-training-create` が書いた草稿ではなく、**人が編集したあとの原稿**。空欄の記入・画像挿入・手直しが入っている。「create が精査済みだから見なくてよい」とはならないのはこのため。

### K. トンマナ・ですますの統一

- ですます／である の混在、語尾の癖のばらつき、同じものの呼び分け
- 見出しの付け方、強調の使い方、記号の使い分けの揺れ
- **書いてはいけないものに触れていないか**（基準は `design-principles.md`）。1件でも見つけたら **blocking**

### L. 誤字脱字

表記ゆれを含む。`.meta.json` の `description` と本文の食い違い、半角スペースの紛れ込み、同一物の2通りの書き方。

### M. 文章量

`estimated_minutes` から逆算する（換算の正本は `lib/lesson-meta.ts`）。手を動かす時間がその外側に乗るので、**本文だけで時間を使い切っていたら長すぎる**。

短すぎる側も見る。判断に必要な前提まで削れていないか。

### N. レッスン `.meta.json` の値の妥当性

記入と形式は整合チェックで済んでいる。ここでは中身を見る。

- `estimated_minutes` が分量と釣り合っているか
- `description` がそのレッスンの実際の中身を表しているか。**目次ではなく、読者が得るものが書かれているか**
- `tags` が内容と合っているか

### O. 受講対象との整合

コースの `.meta.json` の `target` と本文が合っているか。前提知識を要求しすぎていないか、逆に既知のことを説明しすぎていないか。

読者の前提そのもの（社内の業務環境で学ぶ社員）は `dx-training-create/references/lesson-template.md` の「受講者の前提」。

### P. 内容品質

基準は `design-principles.md`。全体講評で終わらせず、**初学者が頭から読んだときの反応を本文の順に**出す。俯瞰でまとめると、冒頭の分かりにくさが消える。

### R. 手順型の画像充足

手順型のレッスンで、手順に対して画像が足りているかを見る。**この検査はここにしか置けない**——充足は人が画像を差し込んだあとにしか判定できず、執筆時の自己レビューでは判定できない。

届いていると数えるのは、挿入済みの画像・未生成の画像コメント・`> **社内画像**:` の空欄の3つ。どれも無い手順が続いていたら指摘する。**どこに何枚要るかの基準は `dx-training-create/references/lesson-template.md` の「手順型レッスンの密度」。ここに書き写さない。**

### V. 初出の専門用語

本文から、コースの `target`（受講対象）が知らない前提の語を拾い、説明があるかを見る。**作法の正本は `dx-training-create/references/lesson-template.md` の「専門用語の初出」。ここに書き写さない。**

許容の範囲は3段階で、⚠ **前のコースまで遡って探す**のがこの検査の肝——1本ずつ独立に読む P では絶対に見つからない（前を知らないので全部「説明が無い」に見える）。

| 説明の在り処 | 判定 |
|---|---|
| 当該レッスン | OK |
| 同じコースの前のレッスン | OK |
| 受講順で前のコース | OK。参照の一言が無ければ足す提案を添えてよい |
| どこにも無い | **advisory** で指摘 |

受講順（`order` と `cross_series_prev`）の引き方は `integrity-checks.md` の受講順検査（H）と同じ。**ここに書き写さない。**

- 指摘には**その語を専門用語とみなした理由**を1文添える。判定基準が `target` である以上ぶれるので、人が差し戻せるようにする
- 前のコース全文を読み直さない。**語ごとに前のコース内を検索する**
- ⚠ 心の声ウォークスルー（本文を渡さない）とは別に行う

## コースをまたいで見る（Q / X）

### Q. メタファーの統一

`dx-training-create` は「1つの概念には1つのたとえを固定する」を原則にし、同じシリーズの過去 run からもたとえを引き継ぐ。**破れるのは run をまたいだとき**——別の実行で書かれたレッスンに、同じ概念の別のたとえが入る。

1. コース内（同じシリーズなら全体）の本文から、概念ごとにどのたとえで説明しているかを集める
2. 同じ概念に2つ以上のたとえが当たっていないかを見る
3. たとえが**根拠として使われて**いないかも見る（たとえは理解を助けるが証明にはならない）

指摘には、**どちらに寄せるかの案を添える**。先に書かれた方に揃えるのが既定だが、後の方が良ければそう言う。決めるのは人。

### X. キャッチの通し整合

`catch` は `dx-training-create` が **run 単位**で作る。run はシリーズ1本、ときにコース1本の粒度なので、書く時点では他シリーズのキャッチが視界に入らない。**衝突は全部そろってから初めて見える**——だから create 側では捕まえられず、ここで見る。

**見るのは1点だけ。**

> 受講順で前にあるキャッチが**獲得・完了を宣言した**ものを、後のキャッチが**未獲得の前提**で語っていないか

対象は**レビューの指定範囲によらず `contents/**/.meta.json` の `catch` 全件**。矛盾は相手側にあるので、相手が範囲外だと永久に検出できない。全件でも数十件で1つの文脈に載る——本文検査と違って全件読みが成立するのが、この検査だけの特権。

受講順の引き方は `integrity-checks.md` の受講順検査（H）と同じ。**ここに書き写さない。**

**重さは advisory 固定。** キャッチは受講者の感情のフックで、正しさを競うものではない。blocking にすると、キャッチが「安全側の無難な一言」へ寄る。指摘には**どのキャッチとどのキャッチが、受講順のどの関係で矛盾しているか**と、寄せ方の案を添える。決めるのは人。

**やらないこと。**

| やらないこと | 理由 |
|---|---|
| 語彙の台帳・メタファーの定義ファイルを作る／既存のメタファーを規範として参照する | メタファーを機械に先回りさせると、run ごとの創造性が失われる。**細則を書き置かない**方針（→ 採点基準をその場で決める）とも矛盾する |
| 同じ語が複数のものを指していることだけを理由に指摘する | 語の再利用そのものは問題ではない。`セーブ` は全本文で使い倒されているし、`地図を手に入れる`（DX入門）と `共有保管庫の鍵を手に入れる`（GitHub入門）は同じ動詞でも獲得の対象が別で矛盾しない。**縛るのは語彙ではなく獲得の時制だけ** |
| シリーズとコースの抽象度の勾配を判定する | メタファーそれ自体が高度な抽象化なので、勾配を縛るとメタファーが使えなくなる |

⚠ **境界は通す側に倒す。** `開発環境準備コース「道具をそろえる」` の後に来る `Git環境構築コース「手を動かす準備を整える」` は、二度目の準備に見えて**別の準備**（Git のインストール）である。文面だけからは切れないので、迷ったら advisory にとどめる。

## 英語版の検査

**英語版が存在するときだけ通る。** 公開前レビューが選ばれたときの話で、整合チェックだけの実行では通らない。

### U. 英語版の受講者読み

**サブエージェントへ `contents.en.md` だけを渡す。**

| 渡すもの | 渡さないもの |
|---|---|
| `contents.en.md` の本文 | **原文（`contents.md`）** |
| | **`contracts/translation-contract.md`** |
| | 用語集・訳注の意図・翻訳の経緯 |

⚠ **渡さないものを渡した瞬間、この検査は無効になる。** 原文を知った読者は「原文がこうだからこの英語で正しい」と読めてしまい、不自然さに気づけない。受講者は原文を持たないのだから、検査する側も持たないのが正しいシミュレーションになる。心の声ウォークスルー（`integrity-checks.md`）が本文を渡さないのと同じ作法で、**渡さないことが検査の設計そのもの**。

出させるものは**本文の順に並んだ心の声**。まとめた講評にしない——俯瞰すると、頭から読んだときの引っかかりが消える。

出てきた心の声を指摘に変換する。

- 直訳のまま語順が日本語に引きずられている
- 1文が長すぎて主語と述語が離れている
- 冠詞・前置詞が不自然で読みが止まる
- 同じ概念が本文の中で言い換わっていて同一物と分からない

⚠ **U の指摘は「読みづらさの候補」であって、用語の正解ではない。** 用語集に沿った訳語を「不自然」と言ってくることがある——読者は用語集を知らないので当然の反応。**採否の判断では用語集（Q で見る）が勝つ。** 指摘文にもその旨を添えて、人が取り違えないようにする。

### K / L の訳文への適用

- **K（トンマナ）** — 英文の文体の一貫性。ですます／である の代わりに、語調・人称・命令形の揺れを見る。基準の導出規則は日本語と同じ（→ 採点基準をその場で決める）。**英語用の細則ファイルを作らない**
- **L（誤字脱字）** — スペル・表記ゆれ・大文字小文字の不統一

### V の訳文への適用

日本語と同じ規則を `contents.en.md` に通す。⚠ **この検査では用語集（`translation-contract.md`）を参照してよい**——訳語が用語集どおりかの判断が混ざるため。U（渡さない検査）とは別物として扱う。

### N / O の訳文への適用

- **N** — `description_en` / `catch_en` / `target_en` が中身を表しているか。目次ではなく読者が得るものが書かれているか
- **O** — `target_en` と訳文の難度が合っているか

### changelog.en.md

K / L と同じ観点（文体の一貫・スペル・表記ゆれ）で見る。日付見出し（`## YYYY-MM-DD`）は翻訳しないので、**日付が日本語版とずれていたら訳の事故**として指摘する。エントリの過不足そのものは整合チェックの T が鮮度として拾う。

### 英語では見ないもの

| 項目 | 見ない理由 |
|---|---|
| **M（文章量）** | `estimated_minutes` は**日英で共有する1つの値**であり、英語側の独自換算に根拠が無い。同じ内容でも英語は語数が変わるので、日本語の換算を当てると訳しただけで「長すぎる」と出続ける。極端な冗長さは U が「読みにくい」として拾う |
| **R（画像充足）** | 画像は日英で共通。日本語版の検査で足り、英語版でも見ると同じ不足を2回指摘することになる |

### Q への追加（横断）

Q は「同じ概念に別のたとえが当たっていないか」を run をまたいで見る検査だった。翻訳も**別の実行で訳されたユニット間で一貫性が破れる**という同じ構造なので、ここに足す。

- **用語の英訳ゆれ** — 同じ概念が `repository` と `repo` のように訳し分けられていないか
- **メタと本文の食い違い** — `name_en` / `catch_en` と、本文中でそのコース・レッスンを指す呼称が一致しているか。ずれると受講者は別のものだと思う

⚠ **この検査では用語集（`contracts/translation-contract.md`）を参照してよい。** U と違い、規範との照合が目的だから。指摘には**どちらへ寄せるかの案**を添える（既定は用語集、用語集に無い語は先に訳された方）。決めるのは人。
